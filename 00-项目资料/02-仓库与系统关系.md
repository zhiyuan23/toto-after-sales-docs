#### 让 Codex 切换

你或同事可以直接给 Codex 下列指令，指定单个仓库时只处理该仓库：

> 按 TOTO 文档 `00-项目资料/02-仓库与系统关系.md` 的“小程序远程地址留存与恢复”，把两个小程序的 origin 切换到 GitHub，检查 fetch／push 地址和连接，不提交、不推送，更新文档中的当前状态。

> 按 TOTO 文档 `00-项目资料/02-仓库与系统关系.md` 的“小程序远程地址留存与恢复”，把两个小程序的 origin 切回 Codeup，检查 fetch／push 地址和连接，不提交、不推送，更新文档中的当前状态。

Codex 执行约定：

1. 定位本工作区 `Gaia/mobile/` 下对应独立仓库，读取仓库约束，检查 `git status --short --branch`、`git branch -vv`、`git remote -v`。保留全部已有改动、分支和提交。
2. 根据上表选择目标地址：已有 `origin` 用 `git remote set-url origin <地址>`，没有时用 `git remote add origin <地址>`。不要删除再重建仓库，也不要改全局 Git 配置。
3. 检查 `git remote get-url --all origin` 和 `git remote get-url --push --all origin`，fetch 和 push 都必须仅指向所选平台的对应仓库。若存在单独的 `remote.origin.pushurl`、多个 URL、`remote.pushDefault` 或当前分支的 `pushRemote`，核对后仅在本仓库纠正会导致推到旧平台的配置。常规配置无需额外设置 push URL，默认随 origin URL 切换。
4. 使用 `git ls-remote --symref origin HEAD 'refs/heads/*'` 只读验证连接及分支。失败时如实报告认证或网络问题，不能把“URL 已配置”当作“连接成功”。GitHub 可在同一仓库的 SSH／HTTPS 地址间选择本机已有认证可用的方式；同事需要自己的仓库访问权限，不共享密码、Token 或私钥。
5. 切换地址不等于同步历史。需要比较提交时先 `git fetch --prune origin` 刷新所选平台的远程跟踪引用；切换前留下的 `origin/*` 和上游状态可能属于旧平台，不能直接据此判断领先／落后。检查当前分支与目标同名分支关系；目标分支不存在时明确记录，不擅自改为 `main`，不自动合并、变基、重置或强推。
6. 回读配置，确认分支、HEAD 和工作区未被更改，记录操作日期、平台、验证结果及必要限制。切换指令本身不授权 commit、push、微信上传或发布。

#### 手动切换命令

以下在 **Gaia 工作区根目录**执行，适用于两个仓库已有 `origin` 的情况；若不存在，把对应命令中的 `set-url` 改为 `add`。

切到 GitHub（HTTPS）：

```bash
git -C mobile/gaia-after-sales-uni remote set-url origin https://github.com/zhiyuan23/gaia-after-sales-uni.git
git -C mobile/gaia-customer-service-uni remote set-url origin https://github.com/zhiyuan23/gaia-customer-service-uni.git
```

切回 Codeup：

```bash
git -C mobile/gaia-after-sales-uni remote set-url origin https://codeup.aliyun.com/ehsure/gaia/gaia-after-sales-uni.git
git -C mobile/gaia-customer-service-uni remote set-url origin https://codeup.aliyun.com/ehsure/gaia/gaia-customer-service-uni.git
```

切换后逐仓执行上一节的地址、连接和工作区检查。若配置了独立 push URL，单独 `set-url` 不会改变它，必须先按执行约定第 3 项处理。

需要把本地提交同步到目标平台时，须另外明确要求推送。届时先 fetch 并检查差异：目标同名分支不存在或可以正常快进时，在对应仓库执行 `git push -u origin HEAD`；存在分叉或无共同历史时先说明差异并确定整合方案，不使用强推覆盖。未提交的工作区改动不会随 push 同步。

## 代码保护与现场约束

- `gaia-ui/src/views/common` 是公共子仓库，未经用户单独明确授权不得修改或提交。
- 代理商工作台不是独立应用：沿用 Gaia 登录和 `gaia-ui` 动态菜单；授权门店选择放在业务上下文或页头，不另建登录菜单。
- `gaia-ui` 当前本地 `master` 落后 `origin/master` 17 个提交，并有 `src/views/common` 改动；开始后台开发前先处理分支基线，不能覆盖现有工作。
- `gaia-saas-proj` 当前存在 `.gitignore` 修改和未跟踪 `logs/`；售后接入必须保留这些既有内容，且不得自动提交。
- `gaia-after-sales-uni` 的通用底座整治纳入本次本地提交，验证与限制见[整治 Spec](../specs/2026-09-14-小程序通用底座整治.md)；后续开发前仍须检查实际工作树。
- 两个小程序共同底座和公共配置机制的变更必须在同一任务同步修改并分别验证；应用名称、AppID、版本台账、业务路由和页面保持独立，完整边界以两个仓库同名 `docs/shared-foundation.md` 为准。
- `gaia-after-sales` 当前为本地 `main` 且干净；其最新文档提交不代表任何业务切片已完成。
- 提交、推送、微信上传和发布均不由功能 Spec 或跨仓开发授权自动包含。

## 数据与接口归属原则

- 售后域独立持有商品、分类、代理商、门店、顾客、服务资源、库存、工单及其业务关系和快照，不直接引用主系统业务主档。
- 统一认证权限／租户平台按原方案复用；DWH、出库和追溯核验仅按另行确认的外部接口契约接入，不默认与主系统同步。代码已完成独立化整改，目标环境待迁移与验收，见 [业务数据独立边界与核查](../specs/2026-09-11-业务数据独立边界与已开发功能核查.md)。
- 管理端入口按现有 `/api/**` 体系；小程序入口按 `/wxapi/**` 体系。具体命名空间、身份和权限在单切片 Spec 中确认。
- 如果最终只是门店退换货且不存在独立工单生命周期，应重新评估是否由 `gaia-store` 承载；如果要独立部署售后服务，再评估独立 Web 启动模块。

技术版本和装配方式见[技术架构与技术栈](03-技术架构与技术栈.md)。
