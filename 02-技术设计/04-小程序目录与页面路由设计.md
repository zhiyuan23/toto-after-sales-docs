## 2. 目录与命名原则

1. `src/pages/` 根页面只保留 Tab、登录等启动高频页；产品、预约、网点、问卷等二级流程按业务域配置为分包。
2. 页面路径统一使用小写开头的 camelCase；页面入口统一为 `index.vue`，例如 `pages/serviceOrder/evaluation/index.vue`。
3. Tab 使用用户任务语言；页面目录和代码使用稳定领域语言，不使用“页面一”“模块二”等临时编号。
4. 列表、详情、编辑可以是同一需求入口下的不同路由；弹窗、选择器、媒体预览等优先做组件，不为每个交互创建页面。
5. 页面、API、Store、类型和业务组件采用相同领域词，例如 `product`、`serviceOrder`、`network`，降低跨目录定位成本。
6. 两个现有工程均以 `src/router/definition.ts` 作为页面、标题、Tab 和访问要求的唯一元数据源；新增或改名页面后执行 `pnpm routes:generate` 生成 `src/pages.json`，不得双写派生文件。路由常量、登录拦截和入口追踪关系仍须同步核对。
7. 主包只放启动必需代码；低频流程和较重资源进入分包。公共代码仍在主包，不能通过跨分包相对路径复用页面内部实现。
8. C/W 编号只用于需求追踪，不进入用户可见名称，也不作为目录名称。

### 4.4 `pages.json` 分包规划

| 包 | root | 包含内容 | 加载原则 |
| --- | --- | --- | --- |
| 主包 | — | `home`、`service`、`mine`、`login` | 只保留启动、Tab 和登录必需内容 |
| 产品 | `pages/product` | 注册、购买信息、产品、购买与服务记录 | 从服务或我的进入 |
| 售后 | `pages/serviceOrder` | 预约、故障媒体、评价 | 登录且选择合法产品后进入 |
| 网点 | `pages/network` | 门店/网点、电话、微信和咨询入口 | 可按具体页面决定是否允许游客访问 |
| 问卷 | `pages/survey` | 问卷列表、填写、结果 | 登录后按投放资格进入 |
| 账号 | `pages/account` | 手机绑定、个人资料、地址、偏好、隐私和注销 | 按页面配置登录拦截 |
| 公共 | `pages/common` | 404 等低频公共页面 | 保留现有分包 |

分包由 `pages.json` 显式注册，不能只创建目录。页面实际大小接近平台限制时，再依据构建产物决定独立分包和预下载配置，不提前添加无证据的优化。

## 6. 跨小程序复用边界

| 可统一的约定 | 不应直接复制的内容 |
| --- | --- |
| UniApp 页面命名、`index.vue` 入口、分包方式、请求错误处理、空态和加载态 | 登录身份、Token、角色和数据范围 |
| TOTO 品牌令牌、基础反馈组件、媒体上传交互规范 | 消费者产品数据与服务人员任务数据 |
| 后端统一响应、租户头和接口版本规则（契约确认后） | 工单可操作状态、配件库存权限和企业切换规则 |
| 页面追踪到 C/W 编号及 Spec 的方法 | 微信 AppID、发布配置、密钥和环境私有参数 |

若两个小程序最终采用同一工程模板，应通过明确的公共包或受控同步机制复用通用能力，不通过复制粘贴长期维护两份请求内核和设计系统。是否抽取公共包必须以至少两个真实调用仓库和独立版本治理方案为前提。

## 7. 路由、鉴权与页面状态约束

1. Tab 页面使用 `uni.switchTab`；普通页面使用 `uni.navigateTo`；完成登录或不可返回的结果页按流程使用 `redirectTo` 或 `reLaunch`。
2. 路由常量不得在页面内散落字符串；`src/router/definition.ts` 是页面元数据事实源，`src/pages.json` 仅由 `pnpm routes:generate` 派生。`src/router/index.ts`、路径常量、登录态、匿名白名单和回跳处理使用同一份路由定义，不从派生文件建立第二事实源。
3. 前端登录拦截只改善交互，消费者本人数据、服务人员本人/企业/服务站数据必须由后端强制校验。
4. 扫码、定位、相机、相册、手机号和通知权限按使用时申请；拒绝授权时提供可解释的降级或人工处理路径。
5. 表单草稿、重复提交、弱网重试和媒体续传在对应业务 Spec 中定义；成功页只能由真实接口结果触发。
6. C16、C17 及所有业务规则未确认的入口可以建隐藏路由，但不得跳转到猜测的热线、外链或客服渠道。

### 7.1 开发与验收测试身份

服务人员端账号密码登录、会话恢复、安全回跳、服务人员档案和企业／服务站上下文已在阶段 1 通过专用真实账号验证；阶段 2 又验证恢复后三 Tab 门禁和“我的”上下文展示。阶段 3 的任务只读切片已完成前后端自动化、权限迁移、真实账号接口和微信开发者工具走查；这些证据满足 G3，但不替代 W01／W02 剩余范围的完整功能和最终业务验收。后续业务开发不得退回客户端硬编码身份；最小身份和数据集以[完整开发计划第 12 节](../specs/2026-09-18-服务人员小程序完整开发计划.md#12-测试身份数据与验收矩阵)为准，仍须覆盖主路径、同租户跨人员、多企业切换、停用或跨租户拒绝、配件审批和完工审核职责分离。

该方案只后置“用户如何完成真实登录”，不后置身份边界和数据权限：

1. 小程序与 H5 的业务代码统一从身份上下文取得 `tenantId`、`userId`、`roleType` 及适用的 `customerId`、`servicePersonnelId`、`storeId`、`serviceStationId`，不在页面、API 或领域逻辑中散落硬编码数字 ID。
2. 优先由仅本地／development profile 可用的后端适配器，将白名单开发身份换取为正常会话或 Token，并为每个身份提供当前切片所需的最小固定开发权限集；不允许客户端通过任意 `userId`、`tenantId` 或权限码参数冒充用户或扩大权限。
3. 开发身份开关默认关闭，只能在明确的本地 H5 环境启用；测试、演示、微信和生产构建必须关闭，缺少有效身份时拒绝访问。开发账号标识放在本地私有配置，不提交密码、Token 或数据库主键。
4. 后端从首个业务接口开始统一校验当前身份的操作权限，写入创建人、操作人和业务归属，并对本人、门店、服务站和租户范围做服务端过滤；开发期使用最小固定权限集，正式联调切换为 Gaia 动态角色权限，前端隐藏入口不替代授权。
5. 数据模型从首版保留与真实身份对应的租户、用户、顾客／服务人员、门店／服务站和审计字段；不先用全局共享数据实现功能，再在后期补数据归属。
6. 固定开发身份仅支持功能开发和开发自测，不计“登录与权限”验收通过，也不能作为业务功能最终完成证据。

进入业务切片前须先完成阶段 1 的真实服务人员映射和移动端权限发现；登录账号可用不等于服务人员身份可用。任何仅本地 development 的合成身份都不得进入测试、演示、微信或生产构建，且不能作为登录、权限或业务验收证据。
