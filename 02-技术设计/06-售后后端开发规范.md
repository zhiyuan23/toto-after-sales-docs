# 售后后端开发规范

- 更新：2026-09-08。
- 来源：商品分类、商品档案首版的实现与隔离验证；不是 Gaoge Admin 后端整体迁移。
- 对应 [功能 Spec](../specs/2026-09-08-商品分类与商品档案全栈首版.md)、[源码开发说明](../../../backend/gaia-after-sales/docs/catalog-development.md)、[OpenAPI](../../../backend/gaia-after-sales/docs/catalog.openapi.json)。

## 1. 默认架构

沿用 Gaia 模块化单体、Spring、MyBatis、现有数据库事务和运行宿主。新功能首先查找权威领域主档和已有服务，再决定扩展；不复制主档、不重建登录、租户、路由或权限系统，不为简单列表引入微服务、事件总线和通用 CRUD 框架。

| 层级 | 职责 |
| --- | --- |
| API | HTTP 方法、明确的请求参数/Command、响应包装；不写 SQL 和业务规则 |
| AppService | 用例入口、身份/操作权限、事务、引用/状态校验、审计；任务/接口都复用此层 |
| model | 写入命令与查询响应分开；提交字段白名单；不向客户端暴露共享 Entity |
| service | 实际业务规则及现有领域能力适配；只有确有复用价值才拆接口 |
| mapper + XML | 显式查询、锁、参数化 SQL和更新列；使用宿主租户数据源 |
| common | 已验证的分页边界、版本 token、身份/权限适配；不收纳各模块专属状态机 |

目录按领域组织 `afterSales/<domain>/model|appservice|service|mapper`；接口在 API 模块的同名领域目录，XML 在 `resources/mappers/afterSales`。只有承担实际职责才创建文件，不机械生成空层级或父类。

## 2. 接口与数据格式

- 复用 Gaia `APIResponse<T>` 的 `code/errMsg/data`。成功 code=0；前端必须显式检查非零业务码，因为既有 request 可能 resolve 失败响应。
- 普通分页复用 `PageResponse<T>` 的 `rows/records`；前端 API 适配为 `list/total`，页面不自行兼容多种响应外形。
- page 从 1 开始；pageSize 正整数且上限 100。排序白名单并使用 ID 稳定兜底；筛选参数有长度上限，模糊查询转义 `%`、`_`。完整分类树不套普通行分页。
- BIGINT ID 在 HTTP/前端按字符串处理，禁止 Number 转换。兼容旧列实际容量，不能只根据 Java Long 假设数据库列也是 BIGINT。
- 编辑/状态命令携带 version；缺失或过期返回冲突。业务错误只返回可展示原因，不把 SQL、配置、堆栈或底层异常原文交给用户。
- 当前代码采用 4001 未登录、403 权限、404 不存在、409 冲突、422 校验、503 数据访问失败；保持 Gaia 外层格式。新增错误码先确认现有宿主约定，不全局改变其他模块的错误处理。
- 契约与实现一起提交在源码仓库 docs 下，功能 Spec 链接唯一契约；不要另造不一致的接口台账。

## 3. 权限、租户与事务

身份来自 Gaia Shiro；不信任客户端 userId/tenantId。沿用现有按租户路由数据库，扩展表与对应主档位于同一租户数据源；多租户模式缺有效上下文必须拒绝，不能回落默认租户执行业务。

小程序快速开发期可按[阶段性开发身份方案](04-小程序目录与页面路由设计.md#71-开发阶段的固定测试身份)暂时后置真实微信登录和完整动态角色配置，但后端用例仍必须只从统一身份上下文取得用户、租户、最小操作权限集和业务归属。两个固定开发用户由仅本地／development profile 启用的白名单适配器转换为正常会话或 Token，并提供当前业务切片所需的最小固定开发权限集；适配层之外的 Controller、AppService、Service 和 Mapper 不得感知或分支处理“开发用户”，不得接受客户端任意传入的 `userId/tenantId/权限码` 作为授权依据。

此阶段虽可暂不配置完整的动态角色树，但首版表结构、查询、写入和审计必须保留租户、本人、顾客／服务人员、门店／服务站边界。固定身份只是开发自测设施，进入集成测试或演示准备前须切换真实认证授权，并验证未登录、会话失效、跨用户、跨角色和跨租户访问。

正式环境的售后用例显式读取 Gaia 菜单/API 和操作授权；阶段性本地开发则由统一身份适配层提供切片所需的最小固定权限集。两种情况下未授权均应拒绝，不把“宿主没限制此路径”当作授权。页面只展示后端允许的操作能力；最终状态/引用约束由后端判断并返回原因。查询、创建、编辑、启停分别配置，避免用通配写权限覆盖读取角色。

业务写入、扩展和审计在同一事务内；异常回滚，副作用不得半成功。共享主档只更新白名单列，保留图片、单位、工厂、品牌等其他字段。已有引用默认通过停用保留历史，不能从前端示例推导物理删除规则。

商品主档采用低频 catalog 写锁协调分类结构、启停、商品引用与本模块重复写；版本指纹防止覆盖其他入口修改过的业务字段。此锁不能保证所有历史主档入口的并发唯一性，也不应直接复制到高频工单或库存。后续模块按实际业务冲突范围选锁、唯一约束及事务边界。

审计记录与恢复快照区别说明：当前记录对象、动作、操作者、时间和前后版本指纹，不宣称能恢复任意历史字段。需要完整快照的业务应单独设计。

## 4. 主数据适配与部署

复用 `md_material`、`md_material_type_category`，售后字段保存为 ID 一对一扩展。商品售后启停与共享主档全局 enable 分开，新售后业务要求两者及分类可用。GTIN 调用现有规则；型号唯一由 Gaia 系统配置控制，修改配置前检查已有数据。

主键沿用 Gaia 生成器，按实际表名调用；共享库与独立本地 Redis 联调时必须核对序列高水位，不能从空序列生成已有 ID。当前测试库商品分类引用列仍为 INT，适配显式拒绝超容量引用；扩大容量须主数据域连同列定义/生成配置统一升级，禁止偷偷 ALTER 后被旧自动改表恢复。

迁移显式执行，不能启动自动改表。部署前核对实际表结构、目标数据库、备份、权限、序列和失败恢复；回退应用时保留已产生的扩展/审计数据，不自动 DROP。共享库执行受本项目 local-development.md 的明确约束，准备好脚本再处理授权。

## 5. 验证与推广

后续功能涉及普通列表/表单时复用前端 commonV2 和公共 hooks；后端复用上述分层及明确契约，业务规则各自实现。以测试和实际运行证据决定状态，源码完整或构建通过不等同共享环境业务验收。

必要测试按业务选择：真实 SQL/事务回滚、授权与未授权、跨租户访问、非法引用和状态、重复提交/并发、版本冲突、分页和实际字段保留。隔离测试明确数据源和被模拟的边界；Mock 权限/GTIN 或 H2 不能替代实际账号、共享 MySQL、GTIN 配置和宿主联调。

**本项目当前以桌面管理后台为目标，不要求专项检查移动端或窄屏适配。** 保留组件已有响应式行为，不因移动端专项验收影响业务交付；用户后续另行要求时再增加。

## 宿主代理兼容与运行验证（2026-09-08 补充）

Gaia 宿主同时配置事务 AOP 和 Shiro 的 `DefaultAdvisorAutoProxyCreator`，应用服务可能被包装成 JDK 接口代理。被 Controller 或其他服务注入的售后应用服务应声明明确的业务接口（首版为 `CategoryCatalogService` / `ProductCatalogService`），按接口注入；事务仍放在实现方法上。不要为兼容一个业务切片修改宿主全局代理策略。

集成测试须覆盖宿主的代理组合。当前 `catalog-host-transactions.xml` 是宿主 `config/spring-core.xml` 的测试快照，另配置相同的额外代理创建器；宿主 AOP 规则改变时同步核对测试夹具。此组合下验证上下文初始化、API 调用及事务回滚，不能只在单一 `@EnableTransactionManagement` 测试容器中通过。

后端代码安装和宿主打包后必须重启本机运行进程，再验证已登录请求确实映射到新 Controller。匿名 `4001` 只能证明登录拦截器存在，不能证明新接口已加载；未找到 Controller 的异常可能被旧全局处理包装成业务 `500`。
