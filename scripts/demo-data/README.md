# 手动演示数据脚本

用户确认先采用手动执行，不安装每天自动运行的任务。脚本按北京时间当天补充业务，保留办理历史，使工作台持续有待办、查询和统计持续有历史。

在 TOTO 文档仓库执行：

```bash
# 只读预览；不带参数也是预览
python3 scripts/demo-data.py --preview

# 实际维护测试库中的演示业务
python3 scripts/demo-data.py --apply

# 减少演示规模，最多使用 3 个现有商品唯一码
python3 scripts/demo-data.py --apply --slots 3
```

## 执行前提

- macOS／Linux，Python 3 标准库、JDK 21 和已缓存的项目 MySQL JDBC 驱动。无需安装 PyMySQL、修改应用或数据库结构。
- 按[本地开发与联调](../../local-development.md)配置宿主 `.local/application.properties`，连接固定测试目标 `10.1.1.106:3306 / mysql84 / gaia_wh_init_wzy`，VPN 可访问。脚本拒绝其他目标。
- `--apply` 复用当前工作区的本机宿主 `127.0.0.1:8080`；先检查进程归属，再核对 API 与数据库的实物档案／工单 ID 集合。未启动时按既有开发入口启动，脚本不自动启动、停止或重启服务。
- 默认使用已登记的全局测试账号 `afs_admin`，密码读取[测试账号手册](../../06-项目交付/01-业务指南/售后数据权限测试账号手册.md)。也可通过 `TOTO_DEMO_ACCOUNT`／`TOTO_DEMO_PASSWORD` 环境变量覆盖；不要把密码写进命令参数、提交文件或日志。账号必须已有相应全局读取及登记、分配、完工、审核、库存权限；脚本不补授权。

## 每次做什么

1. 用只读一致性快照检查当前测试库，预览可用商品、旧演示待办和审核策略；执行模式保存完整售后数据与表结构备份。
2. 只管理请求号匹配 `TOTO-DEMO-V1-` 专用规则的购买登记、工单和库存单据。排除已有非演示购买登记、消费者绑定及不可用商品／门店。
3. 首次按现有唯一码创建合成顾客和购买登记，以后复用这组登记。默认上限 8 个唯一码，不足时按实际可用数生成。
4. 将上一演示日的工单按现有接口分站、派人、恢复异常、提交完工和审核办结，历史、原创建时间及原期望日期保留。区域／技能／排班／容量无法满足的旧预约按明确模拟原因取消，不伪造履约或修改基础条件。
5. 为没有活动工单的演示商品补当天新单，优先覆盖待分站、待派人、待完工／缺件、待审核及退回待补。再次执行可补充用户已经办结／取消的单据；已有待办保持，一件商品最多一张活动工单。
6. 服务站配件余额低于 10 时，通过入库单补至 20；旧演示领料申请按原接口审批，当天为适用的现场任务保留最多 2 张待审批领料，一张工单不重复申请。
7. 独立回读并核对基础资料／配置及既有非演示顾客、购买、工单和库存单据逐行保持，输出实际状态计数和跳过原因。

完工附件由脚本生成并上传明确印有 **DEMO DATA / NO REAL SERVICE** 的合成图片，用于软件流程演示；不是实际现场照片、铭牌或客户签名。远程指导按契约不提交现场铭牌。图片上传按平台存储权限执行，存储失败时停止并记录结果。

## 边界与失败处理

- 原有测试数据的清理属于独立初始化动作。本脚本没有清理、删除、改表、重置序列或改写日期的功能；不会自动执行上一轮旧清理 SQL。
- 商品、配件、实物档案、渠道／服务网络、人员技能／排班、消费者绑定、账号权限、知识内容、业务字典及派单／审核／费用政策保持原值。
- 不创建微信身份或消费者绑定，不代替消费者评价、投诉、真实履约和业务验收。收费报价、收退款、调拨、退料、实际配件耗用和反馈不在此脚本范围。
- 超时仍由真实 SLA 计算。手动脚本未运行期间，演示待办仍会老化；演示前执行一次，才会推进旧待办和补充当天业务。
- 人工／智能／AI 配置沿用当前值。自动审核可能将待审核演示单自行办结，脚本保留结果；实际待办类型／数量可能因区域、容量、排班和自动任务与计划不同。
- 业务动作各自使用现有事务、权限、版本及幂等规则。接口失败／回执不明时不自动重试，已完成动作保留。查看记录后再次运行，脚本从数据库关系继续；不要把逐步骤执行理解为整个脚本的一次原子事务。
- 执行记录与敏感快照在已忽略的 `.local/demo-data/`，目录 `700`、文件 `600`。`result.json` 保存备份哈希、完成情况、实际动作、跳过原因和保护数据核对结果。备份供受控人工恢复核对，脚本不提供覆盖后续数据的一键回滚。
- 本机与共享测试应用共用数据库，执行结果会同时可见；不需要发布应用。当前完成隔离验证和共享库首跑接续，生成购买／工单／库存并验证合成图片可读；每次运行仍需按实际回执核对状态。跨日真实页面尚未验收。

## 历史订单与报表数据

日常脚本用于补待办；近三个月的历史业务由独立入口一次性初始化：

```bash
# 只读设计预览，仍以当前主档、人员、技能和排班为准
python3 scripts/demo-history.py --preview

# 固定测试库导入近三个月历史业务；已有历史批次时拒绝重复
python3 scripts/demo-history.py --apply
```

先运行日常脚本并成功上传其合成附件，历史脚本复用 `.local/demo-data/evidence.json`。此外需要已有项目 Gson 和 JDBC 缓存、JDK 21；不安装新依赖。历史脚本检查指定三位人员及其现有站点／技能，保持基础资料，用一个受控数据库事务补齐过去的关联记录、质量事实及旧脚本业务展示文字。当前仅在沈阳现有承接范围生成完结业务，其他地区和清洁类只生成取消结果。原实物唯一码不扩充或借用；为评价归属新增禁用的合成消费者身份，原账号及顾客保持。

2026-10-10 已导入 **1,310 张历史订单（1,197 已办结）、932 条评价、52 条投诉、248 条回访、613 条质量事实**，覆盖 7 月 11 日起近三个月；名称／地址／业务文案自然化，标记仅放在业务编码、专用请求号及 ID 段。日常脚本的后续业务文案也已同步调整，附件继续带合成图片标记。数据与保护证据见[历史数据记录](../../specs/2026-10-10-近三个月历史业务模拟数据.md)。

历史导入不是日常刷新命令。演示前仍执行 `python3 scripts/demo-data.py --apply` 补待办，既有历史保留；日常脚本不会重新生成历史质量快照。查看导入后数据：`python3 scripts/demo-history.py --check-run <执行目录>`。敏感备份、精确 ID／原行和回执保存在 `.local/demo-history/`；本次实际目录及最终检查目录记录于历史数据 Spec。

`--restore-run <执行目录>` 只用于导入后尚无任何后续业务的精确恢复，先全表比对，变化则拒绝；不是随时清库或覆盖操作。后续清理需依据 `plan.json.cleanup_keys` 及当时关系重新核对。历史事务无法连接或回执不明时先检查回执及数据库，不自动再次插入。

实施事实见[功能记录](../../specs/2026-10-10-手动演示数据维护脚本.md)。
