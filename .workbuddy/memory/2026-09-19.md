### 踩过的坑（复用价值高）

1. **夹具必须每轮重跑**：`fixture_w2.py` 先清空 9509191xxx 区间再重建。沿用上轮数据会让草稿 revision、幂等请求号、执行事实残留，产生大批假失败。
2. **库存单据必须一起清理**：`afs_part_inventory_document` 唯一键 `uk_..._request` = `document_type` + `client_request_id`，而 `consumeParts` 的 `client_request_id` 由「工单号 + 请求号」派生。只删工单不删单据 → 下次完工提交撞唯一键 → `503 数据操作未完成`。**这不是业务缺陷**，一度被误判为事务问题。
3. **手工种数据后必须校准主键序列**：`GaiaIdGenerator` 走 Redis `ID_KE_<table>`，计数器小于 `max(id)` 时 fail-closed 抛 503「售后业务主键序列未同步」。夹具用固定高段 ID，所以必须跑 `calibrate_seq.py`。
4. 移动端路由前缀是 `/afterSales/mobile/service-personnel/tasks`，不是 `/service-personnel/tasks`；路径写错会得到 4001 未登录（误导性强）。
5. 列表响应字段是 `data.rows` 而非 `records`／`total`。
6. 单次 Bash 调用 2 分钟会超时被杀（exit 137），长验证一律用后台运行。

### 发现的业务缺陷

`DEF-20260919-01`：同工单用不同请求号重复调用签到／远程开始，服务端无「已有活动执行」判断，`ON DUPLICATE KEY UPDATE` 覆盖 `started_at`、清空 `ended_at` 并追加第二条审计。同请求号的重复调用已被幂等回放正确拦截，完工提交也有回放保护，故仅签到／远程开始受影响。
