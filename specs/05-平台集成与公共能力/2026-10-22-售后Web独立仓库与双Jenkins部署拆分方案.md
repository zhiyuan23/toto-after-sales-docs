## 1. 目标架构与边界

售后从 `gaia-ui/apps/after-sales` 拆为独立 Git 仓库，暂定名 `gaia-after-sales-ui`，建议与主站并列检出在 `frontend/` 下。主站和售后各有一条 Jenkins 构建部署任务，分别生成制品、更新自己的静态资源和回滚自己的发布。正式售后 Web 仓库名／地址仍待后续确定；本次借用 `gaia-after-sales-uni` 的分支仅为原型验证，不能把消费者仓的默认分支改造成 Web。Jenkins 的放置位置与个人验证任务命名已确认，详见第 15 节；任务尚未创建。

```text
frontend/gaia-ui             → 主站 Jenkins Job → 主站制品 → ROOT 中的主站文件
frontend/gaia-after-sales-ui → 售后 Jenkins Job → 售后制品 → ROOT/after-sales

同一浏览器来源：协议、域名、端口一致
  /                    主站
  /after-sales/        售后独立入口
  主站 /afterSales/**  通过同源 iframe 展示售后业务页
  /api/**             现有 Gaia 后端、认证会话、租户及授权
```

这里的主站路由沿用现有 hash 路由配置；`/afterSales/**` 指前端业务路由，不新增服务器目录。售后独立访问继续使用 `/after-sales/#/...`，内嵌使用 `/after-sales/?entry=main&view=<展示视角>#/...` 及现有兼容参数。

| 项目 | 拆分后的要求 |
| --- | --- |
| 源码与版本 | 两个独立 Git 仓库、独立依赖和锁文件；主站构建无需售后源码检出 |
| 构建与部署 | 两个 Job，各自构建／归档／发布；日常发布不要求重新构建另一端 |
| 部署形态 | 保持同源子路径，仍可位于同一个 Tomcat `ROOT`；无需新增独立 Tomcat |
| 发布产物 | 日常改为两个制品；原“一个包包含主子站”不再是每次发布的必要条件。确需完整交付包时按两个固定版本组合，不重建另一端 |
| 登录与租户 | 继续使用 Gaia 服务端会话、现有存储键、请求头和租户协议；不从 URL 或窗口消息传身份凭据 |
| 菜单及权限 | 使用同一套 Gaia 用户、角色、模块和操作授权；业务数据范围仍由后端校验，前端仓库和导航清单不能授予权限 |
| 双入口体验 | 主站导航／iframe 保留；独立入口保留完整布局与原登录、退出流程；语言、主题、弹层和离开保护延续原契约 |
| 本地开发 | 保留一键启动；主子站由两个 Vite 服务提供，通过主站代理保持同源双入口，修改代码支持热更新，无需先构建或复制 dist |
| 非本次范围 | 后端拆服务、业务数据迁移、菜单改名／重新编号、换认证方式、跨域单点登录、公共页面 common 的修改或提交 |

### 1.1 已确认的逻辑，后续实施时保持

| 已确认事项 | 具体含义 | 不能由此推定 |
| --- | --- | --- |
| 两仓独立 | 主站与售后各自管理源码、Git 提交、依赖、锁文件及构建任务 | 消费者小程序源码被售后 Web 取代；共用 default 分支 |
| 同源和权限复用 | 保留原 Gaia 登录／租户／菜单／操作与数据范围，通过同一来源的不同路径访问 | 用相同域名替代后端鉴权；菜单清单或 URL 可以授予权限 |
| 两种访问入口 | 主站菜单里 iframe 内嵌；同时允许直接打开 `/after-sales/#/...` | 另建一套业务页面或账号体系 |
| 独立更新 | 主站更新只构建主站；售后更新只构建售后；两者发布目录和回滚范围分开 | 所有协议、菜单及 API 变化都无需另一端配合 |
| 版本不强行绑号 | 两仓版本号和 Commit 不要求一致；以实际兼容契约及现场组合关联 | 任何新旧版本均可任意组合；两个分支同名就兼容 |
| 本地保留一键、同源、HMR | 一条联调命令管理两个源码开发服务，浏览器统一走 7004 | 本地要先打包售后并把 dist 复制进主站才能热更新 |
| 提交记录分离 | 后续售后业务改动进入售后仓，主站只保留必要装配／集成快照改动 | 无需记录原源码来源，或迁移时可以重写主站共享历史 |

**构建关系必须区分清楚：** 拆分后的日常构建不再要求“先构建售后，再放进 gaia-ui 的 dist”。两个任务分别产出制品，部署阶段把它们放在同一站点的不同归属目录。服务器仍可表现为 `ROOT` 与 `ROOT/after-sales` 的既有结构；需要离线整包时，额外把两份已经归档的固定版本组合成一个交付包。不能为了维持目录外观，又让主站每次拉取售后源码并重新构建。

### 1.2 今天停止后仍保持的现状

现行源码继续是 `gaia-ui/apps/after-sales` 同仓子系统；现行安装、组合构建、开发启动和正式发布入口不因本文自动改语义。`gaia-after-sales-uni` 继续保留原消费者小程序用途，后端、服务人员端、common 以及现有 Jenkins 任务保持原有职责。未来首次实施必须先核对最新分支和未提交改动，不能用今天的旧快照覆盖届时新功能。

### 3.3 本地启动与文档工具

本地开发保留当前路径关系和一键联调能力。两个仓库各自运行 Vite；主站代理将售后服务呈现为同源子路径。生产的产物装配只用于构建／部署，本地日常开发直接运行源码，不先构建、不复制 dist 到主仓，也不以读取另一端源码的方式实现页面复用。

```text
frontend/
├── gaia-ui/              主站 Vite：7004
└── gaia-after-sales-ui/  售后 Vite：9010

浏览器统一访问 http://127.0.0.1:7004
├── /                        → 主站 Vite
├── /after-sales/            → 代理至售后 Vite：9010
└── /api/**                  → 沿原代理及上下文配置访问共享 8080 后端

售后开发 HMR WebSocket       → 直接连接 127.0.0.1:9010 的专用 HMR 通道
```

浏览器访问主站售后菜单时，iframe 使用 `http://127.0.0.1:7004/after-sales/?entry=main...`；独立布局使用 `http://127.0.0.1:7004/after-sales/#/...`。这两个入口的协议、主机名和端口相同，继续复用该来源下的登录会话及前端存储协议。联调统一使用 `127.0.0.1`，避免混用 `localhost` 造成不同浏览器来源。

售后单独开发仍可直接访问 `http://127.0.0.1:9010/after-sales/#/...`，复用原 8080 后端和 Redis；9010 与 7004 属于不同浏览器来源，其前端本地存储分别维护，不能把两者之间无感共享登录状态作为单独启动的默认承诺。验证主子站同源登录时使用上述统一 7004 入口。

#### 3.3.1 一键启动的拟议命令职责

保留既有命令名称并调整脚本内部路径；以下是拆分后的目标行为，尚未修改当前命令实现。

| 命令／入口 | 拆分后的职责 | 对邻仓的要求 |
| --- | --- | --- |
| gaia-ui 的 `yarn dev:full` | 一条命令核对并复用共享后端／Redis，启动或复用主站 7004 和售后 9010，提供同源双入口 | 明确定位并检查售后邻仓及依赖，不在缺失时自动下载仓库或创建第二套环境 |
| gaia-ui 的 `yarn dev:main` | 仅启动主站 Vite；可代理已单独运行的售后服务 | 无售后仓时仍可开发主站；进入售后代理路径时明确报告服务未就绪 |
| 文档仓／主仓现有 `yarn dev:afs` 入口 | 保留售后专用一键启动能力，改为转发到新仓；核对并复用后端，只启动或复用售后 9010 | 不强制启动主站；共享后端准备仍复用文档仓原启动器 |
| 售后仓自身 `pnpm dev` | 只运行售后 Vite，供已有后端环境下的独立前端开发 | 不要求主站源码、依赖或服务存在 |

一键启动优先沿用并列检出的工作区约定；如需自定义检出目录，必须显式提供并验证，不能猜测或接管其他项目。启动前识别已有服务的工作目录、工作区和后端源码状态，健康且匹配时复用，只补缺失部分。不可为保持命令名称而无条件结束两个端口的进程；需要重启本项目服务时继续遵循既有说明与授权规则。

#### 3.3.2 热更新与菜单快照

### 4.1 菜单清单采用版本化快照

主仓建议位置为 `src/views/afterSales/integration/`，包含清单和来源元数据。元数据记录原仓／新仓来源提交、清单 SHA-256、导出格式版本、窗口消息协议版本及验证过的组合版本；具体文件名在实施时按主仓惯例确定。快照由导出工具生成，禁止两边手工分别维护同一菜单。完整清单应覆盖当前主站确实消费的字段，不能只导出名称／路径而漏掉管理员模块、视角、别名、隐藏及退役等信息。

### 4.2 主站安装、构建与验证

- 根 `postinstall` 取消安装售后；主站依赖仍用原 Yarn 锁文件。`scripts/frontends/toolchains.mjs` 不再在模块加载时强制读取售后 `.nvmrc`，否则即使只执行主站命令仍会因缺目录失败。
- 根 `build`、`production`、`factory`、`production:saas`、`factory:saas` 均改为对应主站构建流程；不只是调整其中一个 Jenkins 命令。`build.mjs` 取消售后调用与复制，保留主站失败门禁。
- `verify:dist` 改为主站资源校验，主站不再要求 `dist/after-sales` 存在。将主站需要的现有资源验证算法纳入主仓本地工具并带回归用例，取消对售后验证器的跨仓 import；售后继续维护自身验证入口，不为拆仓新增公共 npm 依赖。
- 根 `after-sales:pnpm` 等只服务旧目录的命令移除或改为明确的开发转发，不能留作主站 CI 隐式依赖。旧安装／聚合构建夹具和对应门禁同步调整。
- `vite.config.ts` 保留本地 9010 代理和既有 API 配置；不能将生产资源重写到主站 `/assets`。与主站其他业务、全局组件或 common 无关的配置不顺带调整。

### 4.3 独立发布的兼容边界

| 变更 | 一般发布范围 | 兼容要求 |
| --- | --- | --- |
| 售后既有页面内部展示、交互修复，契约未变 | 只发布售后 | 已部署主站快照及桥接协议仍可用 |
| 新菜单、路径、别名、导航名称／图标／视角编排变化 | 按影响配套更新主站快照和售后 | 新主站入口指向的子站页面必须已存在；真实菜单授权另按原联动规则处理 |
| 窗口消息、主题、弹层、离开保护协议变化 | 通常两端配套 | 优先采用兼容过渡；需要破坏性变化时记录切换顺序和允许回滚组合 |
| 主站其他业务更新 | 只发布主站 | 集成快照保持且售后目录／入口不变 |
| 后端接口契约变化 | 按原接口发布范围协调 | 独立前端仓库不自动解决后端兼容；不由这两个 Job 自动更新后端 |

现有 iframe URL 使用主站构建标识。拆分后不能假定“售后更新必然带来主站构建号变化”：售后 HTML 必须持续重新校验，哈希资源按内容缓存并保留过渡期旧分块。分别发布时同时验证旧主站标签、新售后入口及旧售后标签的懒加载，不能只测重新打开页面。

### 4.4 版本关联、发布组合与回滚要求

两个仓库各自维护版本号、提交历史和 Jenkins 构建编号，不要求版本号、分支名或发版节奏一致，也不建立每个 Commit 的一对一绑定。关联对象是可追溯的制品、集成契约及环境实际运行组合。

| 层次 | 最小记录 | 规则 |
| --- | --- | --- |
| 应用／制品版本 | 仓库、完整 Commit、应用发布标识、Jenkins Job／构建号、环境构建模式、制品 SHA-256 | 两端分别生成；应用版本号不能代替准确的 Commit 和制品摘要；重发／回滚取原制品，不按同名分支重新构建冒充原版本 |
| 菜单集成快照 | 清单来源 Commit、内容摘要、导出格式版本及其消费约定 | 权威来源在售后，主站固定并提交自己使用的快照；用于展示与路由，不包含账号授权 |
| 窗口桥接契约 | 协议标识／版本、支持的消息与字段、必要的兼容范围 | 覆盖导航、离开保护、语言／主题、弹层及握手；改变既有字段含义或删除消息前核对双方支持能力 |
| 环境发布组合 | 环境、主站制品版本、售后制品版本、当前契约、验证结论及发布编号 | 每次单端发布记录保留的另一端实际版本；完整交付包也固定同一组制品来源 |
| 后端依赖 | 本次功能所需的接口能力及目标环境后端版本／可核对标识 | 接口变化时补充兼容条件，不要求前后端使用相同版本号；前端 Job 不自动升级后端 |

主站菜单快照可以来自较早的售后提交。只要当前售后仍支持该快照引用的功能、路由和桥接协议，主站即可继续使用；清单 SHA 或来源 Commit 不同本身不表示不兼容。售后内部修复无需为了对齐元数据而更新主站。新增只在售后独立入口展示的功能，只有实际影响主站所消费契约时才同步主站快照。

以下仅为组合示例，A／B 是示意标识，不是已有项目版本：

```text
主站 A1 + 售后 B1  → 已验证组合
主站 A1 + 售后 B2  → 售后内部修复，验证原契约仍兼容，只发布售后
主站 A2 + 售后 B2  → 随后更新主站，验证当前组合，只发布主站
```

两个 Jenkins 任务均增加版本关联检查：

1. 构建归档写入自身准确版本及契约信息；读取已固定的快照，不从另一仓的“最新分支”临时生成发布输入。
2. 部署前在站点锁内读取另一端现场版本及契约，对照本次制品兼容条件和必要测试结论。只需要版本／契约信息，不要求重新拉取或构建另一端源码。
3. 当前环境元数据缺失、关键协议不受支持或组合未经必要验证时，先核实现场并补齐兼容证据；不以数字版本更大、清单摘要相同或忽略门禁代替兼容判断。首次拆分要从已核实线上组合建立基线，不能因尚无元数据直接判定兼容。
4. 发布后记录新组合及验证结论，仅更新自身文件和元数据；读取的另一端版本作为本次记录，不覆写另一端的发布记录。
5. 回滚前重新核对现场另一端版本与旧制品的兼容性。旧版本若依赖已退役路由／消息／接口，不能默认单端回滚，须采用验证过的兼容组合和协调顺序。

初期用明确契约版本、变更影响检查和必要场景测试建立已验证组合记录，不预建所有版本的笛卡尔组合表。兼容范围可先限定于实际验证过的契约能力；出现破坏性变更时再补充对应兼容范围、过渡及发布顺序。记录仍归原部署记录入口，测试结论仍归本 Spec，不另建平行版本或进度台账。

| 非构建文件 | 明确主站拥有的 WEB-INF 配置与静态文件清单，保护 `.well-known`、验证文件和其他系统资源 | root 级缓存／代理／web.xml 是共享站点配置，改动时单独核验影响；不得从旧包恢复整个 ROOT.war |
| 并发控制 | 与售后使用同一环境、同一站点发布锁 | 单个 Job 的“禁止并发”只约束自身，不能替代跨 Job／手工发布互斥 |
| 回滚 | 恢复主站文件及其元数据，保留现场售后版本；先核对后续发布 | 不能拿旧整包把售后回滚；主站回滚版本须兼容当前售后协议和清单 |
| 验证与记录 | 检查主站真实入口和必要业务，并比较售后前后摘要 | 记录主站版本、common 实际 SHA、集成快照、保留的售后版本；不得把保留版本记为本次更新 |

两个任务的部署步骤均需版本化管理，避免关键排除和回滚逻辑只存在 Jenkins 网页里。使用现有公司发布工具时，先核对它能否按范围备份／切换／回滚；仅有“排除上传”能力而回滚仍恢复整个 ROOT 时，不满足独立部署条件。

## 7. 共享目录、缓存、并发及回滚

### 7.1 文件归属

| 路径／操作 | 所属及规则 |
| --- | --- |
| `ROOT/after-sales/**` | 售后 Job 独占管理；主站上传、清理、备份恢复均保护此范围 |
| 主站入口、主站 assets 及其余主站构建文件 | 主站 Job 管理；售后发布前后核对这些文件摘要不变 |
| ROOT 级 WEB-INF／缓存策略、反向代理、证书及域名验证文件 | 共享运行配置；列入保护项和独立变更核验，不随售后制品覆盖 |
| `api.war`、展开 API、数据库、服务器 conf | 原后端部署职责；两个前端 Job 默认都不写，不附带小程序上传 |
| `ROOT.war`、自动解压／重部署设置 | 实施前核实实际容器行为；若旧 WAR 可重新展开覆盖目录，先解决发布方式冲突，不能仅依赖目录排除 |

生产目录仍可保持单个 ROOT，但不能靠把非空 ROOT 直接重命名替换来实现主站独立部署，因为这会连带售后、会话所在应用上下文或共享配置。实施时根据容器实际能力确定受控更新方式；不承诺在尚未核实的 Tomcat 配置下绝对无感或原子切换。HTML 最后切换、资源先就绪，尽量缩短不一致窗口。

### 7.2 发布互斥与现场版本

- 两个 Job 使用同一个环境级站点锁，测试站应与既有完整发布入口共用服务器锁 `/yundata/saas_test/.toto-test-deploy.lock`；Demo 另定自己的环境锁，不能跨环境混用。已有 [Lockable Resources 插件](https://www.jenkins.io/doc/pipeline/steps/lockable-resources/)时可使用同名 `lock`，实际插件状态待核实，不自动安装插件。
- 锁覆盖现场版本复核、候选最终合并、备份、切换、验证及失败回滚。耗时构建和预上传可在锁外进行，但使用现场旧资源生成的最终候选必须在锁内重读版本后确认，避免合入过期内容。
- Jenkins 之外的 AI／手工部署入口也必须接入同一互斥机制；存在多个 Jenkins 控制器或无法共用 Job 锁时，采用目标实例统一发布锁，禁止绕过。
- 每个应用拥有自己的版本元数据，包含源码、制品摘要、契约版本和本次发布编号。发布时读取另一端当前版本并检查兼容，任何任务都不能用早先读取的整站状态覆盖另一端的新元数据。
- 回滚同样加锁并核对发布编号。发生后续他人发布时先比较，仅恢复本次拥有的范围；协议不兼容时按已验证组合协调恢复，不能机械单端回退。

### 7.3 缓存与旧资源

保留当前 HTML 重新校验策略，现有主站构建标识只作为原协议的一部分。售后独立发布后，即使主站未变，刷新／重新进入 iframe 也必须能取到新 HTML；正在打开的页面不强制刷新丢草稿。旧哈希／时间戳分块按现有已验证策略保留，延迟清理由实际过渡和留存规则决定，不在每次发布时清空 assets。

备份分别保存两端入口与文件清单。资源清单覆盖新文件、保留旧文件及其完整引用，不能以首页 HTTP 200 或几份预加载资源作为发布成功依据。

### 14.3 必须带入的主站会话与标签修复

触发链路为：售后独立入口登录成功 → Gaia服务端会话有效 → 新开主站页面 → 主站自身 `userInfos` 尚未由主站登录页初始化 → 旧式布局 `roles` 为空 → 菜单／标签候选被过滤 → 标签查找返回 `undefined` 后读取 `meta`。

后续应在售后集成边界内恢复布局状态，而不是给空路由伪造一个已授权标签：

1. 必须先请求并解析当前账号真实 Gaia 菜单。只有后端响应有效、当前账号确有售后授权菜单、已有会话标记和合法登录资料时，才恢复主站的布局展示身份；请求失败或无售后授权时不得执行恢复。
2. 恢复使用原存储协议 `token`、`loginDate`、`afterSales:account`，不从 URL、postMessage 或任意缓存角色获得权限。`token` 在此仅沿用既有前端会话标记／请求头协议，真实身份仍由服务端会话确认。
3. 恢复 `id/userName/photo/time` 等必要布局字段；原型使用 `roles: ['common']` 作为主站现有展示筛选键，`authBtnList: []`。该 `common` 不是后端业务角色，不能用它推断数据范围、操作授权或管理员身份。

## 16. 发布事务、版本组合与复验手册

### 16.1 单端发布应执行的完整事务

1. **锁外构建：** 固定本仓Commit，冻结安装、全部必要检查、环境构建、资源图校验、制品打包与归档；不构建另一端。
2. **锁外上传：** 上传到本次专属暂存目录，核对包SHA与文件清单、相对路径和解包层级；拒绝符号链接、越界路径、重复危险路径及非所属文件。
3. **站点加锁：** 两个Job及既有手工／AI发布均使用同一目标实例锁。53测试站当前完整发布脚本使用 `/yundata/saas_test/.toto-test-deploy.lock`；新任务必须与它协调，不能另起一把只在新任务间有效的锁。
4. **现场重读：** 在锁内确认站点、部署边界、当前主／子版本与协议、运行配置、另一端摘要及是否有后续发布。只检查“自身Job无并发”不够。
5. **候选与备份：** 按应用清单准备候选，合并需保留的旧哈希／时间戳资源，冲突失败；备份本应用将修改／删除的文件、入口与自身元数据。共享配置及另一端只记录保护摘要。
6. **受控切换：** 先落新资源、后切入口。主站只操作自身拥有文件，不能重命名／替换整个非空ROOT；售后只操作 `ROOT/after-sales`。不替换ROOT.war、API或conf，不默认重启Tomcat。
7. **验证：** 校验本应用所有新／保留资源和引用，真实HTTP大小／摘要、入口缓存头、版本组合；对比另一端与共享配置保护摘要。接口和真实登录按第10节场景执行，不把匿名HTTP200当成功。
8. **失败处理：** 切换前失败只标FAILED、现场保持；切换后失败按本次拥有范围恢复，保留另一端现场新版本；无法确认恢复时标NEEDS_ATTENTION，不自动循环重发。断线按发布编号查询。
9. **结束记录：** 写本人应用新版本和已验证组合，只读取／记录另一端版本，不覆盖它的发布元数据；完成记录后释放锁。

回滚也执行同一锁与现场复核。若某次主站发布后售后又更新，主站回滚不能把售后拖回旧版本；但旧主站协议不兼容当前售后时，也不能硬做单端回滚，须选择已验证的组合恢复顺序。

### 16.2 兼容与缓存的具体判断

| 变化或现场情况 | 判断与处理 |
| --- | --- |
