## 1. 目标与完成条件

仅通过微信开发者工具中的两端真实小程序页面，验证维修申请 → 分站 → 派人 → 联系预约 → 服务执行 → 完工提交 → 审核办结 → 消费者查看／评价的闭环，以及适用的异常、取消、退回重派、配件和重提分支。后台操作用于产生小程序需要的分配、审批和审核结果；真实接口／数据回读用于辅助诊断，不替代微信页面执行。本次不安排 H5、Web 页面回归或真机测试。

完成条件：

1. 第一批创建的维修测试单确实进入当前服务人员小程序的本人任务列表；记录工单号、分站与人员分配方式、对应决策和身份回读结果。

3. 首轮完成全部可执行场景及问题登记；阻塞后续场景的明确缺陷先修复、复测解除卡点，再继续首轮。首轮结束后对其余明确问题集中精修，完成必要检查、原用例复测及受影响的小程序场景回归。
4. 留下能继续测试的检查点、测试数据清单及配置变更／恢复记录；形成完整报告。
5. “测试执行结束”与“全流程通过”分别说明。有失败、阻塞或微信开发者工具中的适用场景未验证时，不声明本轮全部通过。真机与其他端不在本轮范围，不作为本轮完成前置，也不据此宣称完整业务验收完成。
6. 按用户追加授权，修复本次流程实际经过页面中明显的异常换行、截断、重叠、字号、间距、对齐和遮挡问题；遵循既有 UI 规范与公共组件，业务契约不变。每次样式修复后在同一角色、同一业务状态复测页面及受影响操作，再续测原流程，保留单据与检查点。公共组件检查受影响页面，共同底座双端等价同步；不扩展全站视觉审查。大范围布局重构或需设计选择的问题记录到现有待办。报告分别列出流程结果、样式修复及验证、剩余问题和未实际验证的平台。

场景描述“改期后继续服务”是测试场景；补齐前置条件、步骤和预期结果后才是可执行测试用例。下表是初始用例集，执行时拆分必要的状态、允许／拒绝子用例，不追求状态组合穷举；所有业务用例均在微信开发者工具完成。

## 3. 环境、身份和智能派单的首批门禁

优先复用当前本地后端和两个微信 development 项目，9010 售后子站仅在流程支撑需要时使用；按 [本地联调](../local-development.md) 核对两端 API 指向、后端包指纹、租户和测试库。微信工具中的当前产物与其他设备／环境不能混用结果。单独 HTTP 200、监听端口或匿名响应不能证明业务代码已生效。

消费者身份从现有消费者项目及正式本人接口核对；服务人员从当前会话及后台主档核对人员 ID、当前企业、主站和租户，不把历史文档账号 ID 当成当前事实。遇登录过期、二维码、验证码或微信工具授权而无法自主完成时，记录卡点并继续可做部分；明确代码缺陷按第6节先修复，不直接跳过依赖环节。

智能派单分两层，作为工单准备须分别核对实际结果，不扩展测试派单配置页面和算法完整矩阵：

1. 总部服务配置中的租户分站策略；
2. FC高歌服务站独立的人员分配策略。

先读取并保留原配置、版本、本站历史待分配队列和相关排班。核对维修技能、目标日 AVAILABLE 排班、人员和站点启用／在职、容量、服务区域及坐标等硬约束。跨午夜按服务器业务日期及所选服务日重新核对，不把今晚和明天的排班混为一谈。

SMART 按候选评分选择，不能仅靠选择智能模式保证一定派给孙志远。通过本次测试地址、服务日期和适用的测试配置建立合法可复现的候选条件，回读实际候选及决策。不能为锁定结果停用其他人员、伪造满意度或绕过资格／容量校验。若无法在不影响其他业务的前提下锁定目标，记录智能选人的实际结果；使用正式退回／人工重派完成履约前置，但明确区分“智能派到本人通过”与“人工兜底后能履约”。

## 6. 修复、跳过和持续执行规则

按批次串行推进微信工具中的两端页面与同一人员任务，避免同时操作两张活动工单；不因流程而增加 Agent 或工作树。执行顺序固定为：**首轮完整测试 → 非阻塞问题集中精修 → 原用例复测及受影响微信场景回归 → 报告**。

### 6.1 首轮：先覆盖，阻塞项即时修复

发现问题先登记并判断是否影响其他环节，按团队规范分配未占用的 `BUG-YYYYMMDD-NN` 编号，写明环境、步骤、实际／预期、严重度、影响用例及证据。

- 阻塞后续环节的明确代码缺陷：立即复现、定位、最小修复，做必要检查，在微信开发者工具复测卡点；解除后从原用例继续。不能仅因修复费时就跳过后续链路，也不靠直接改数据库状态绕过。
- 不阻塞后续环节的问题：保存证据和复现条件，继续首轮其他用例；集中到首轮结束后精修，避免首轮被局部视觉／交互优化打断。
- 数据串写、越权泄漏、重复扣库等问题可能扩大影响时：先暂停受影响动作、修复并验证，保护测试数据后继续其他安全场景。
- 依赖真人、缺失凭据、未确认业务规则、危险配置变更或持续外部故障：调查确认不是可自主修复的代码缺陷后，记录原因、尝试、依赖用例及解除条件，继续不依赖它的场景。共享故障统一诊断，不重复等待。

### 6.2 首轮后：按明确问题集中精修、复测

首轮全部可执行场景处理完后，合并重复问题，按实际证据精确修改。遵循各仓 AGENTS 和对应开发规范；允许修复造成小程序问题的后端支撑缺陷，但不扩大成后台全面测试或重构。公共底座修改双端等价同步，做必要检查；后端修改按标准入口装配／更新本地受管服务，不能用旧进程验证新代码。

每个问题修复后，在微信开发者工具重跑原失败步骤和受影响场景；修改公共能力时复测两端相关用例。复测失败继续定位、修复、复测；非阻塞问题仍不能无理由留到报告。最后重跑一次正常维修闭环，确认集中修复没有破坏主线。

不可消除的外部卡点只能继续其余独立微信场景，不能从中间阶段合成单据后声称消费者→人员闭环通过。测试状态使用：待执行／执行中／通过／失败／阻塞／不适用；修复后保留首轮问题及最终复测结果，并注明“首轮即时修复”或“集中精修”。

每个批次和缺陷复测完成后保存工单号、用例状态、证据索引、下一步及恢复配置；中断后从最后检查点继续。权限审批或缺失信息不能靠等待自动视为批准；无法执行时继续不依赖该条件的工作，最终如实报告。

本任务执行默认保留修复工作区，不自动 commit、push、共享测试环境部署、小程序上传或正式发布。必要的本地构建和受管进程更新属于本地复测。用户随后明确授权部署／提交时，再执行项目对应入口和文档联动要求。
