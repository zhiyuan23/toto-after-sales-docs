# 窜货监控系统通知详细设计

> 当前通知入口、消息接入与加载交互按[2026-10-20 扩展](#notification-center-20261020)执行；第1～9节保留原窜货消息投递、权限、7天有效期及历史发布证据。原版本已发布不表示本次扩展已部署。

- 状态：已开发，测试库迁移、权限配置与测试环境发布完成；待业务角色在线验收
- 日期、版本：2026-09-29 / V1.0
- 应用载体：售后 Web 管理后台
- 角色视角：系统管理员、总部运营
- 业务模块：防窜货 / 窜货明细
- 入口与需求：A36 窜货明细；本期新增售后子系统系统通知能力
- 用户确认记录：2026-09-29。确认只在售后子系统右上角展示；轮询周期 1 分钟；单张卡片展示 5 秒且关闭不代表已读；多条消息提示“另有 N 条疑似窜货消息，查看全部”；仅未读、已读两种状态；收件人为系统管理员和总部运营；上线后只针对新判断结果；消息保留 7 天；到期后从列表和未读数移除。
- 关联材料：[防窜货明细与消费者扫码无购买登记建单](2026-09-28-防窜货明细与消费者扫码无购买登记建单.md)、现有 A36 窜货明细接口和页面。
- 研发任务：已按本设计完成代码、数据库迁移、隐藏权限、测试构建和测试环境发布。本文件中的“验收”以第 9 节记录为准，未将未执行的业务登录场景记为通过。

## 1. 目标与范围

完工审核通过后的异步窜货判断，在产生新的疑似窜货结果时，为符合范围的售后后台用户创建站内通知。用户在售后子系统页头看到铃铛未读数，并在在线期间收到一张短暂的提示卡；卡片和通知列表均可打开对应的疑似窜货明细详情。

本期包含：

1. 以现有异步窜货判断结果为唯一触发源。
2. 系统管理员、总部运营的个人未读/已读通知。
3. 售后子系统页头铃铛、未读数、通知抽屉、单张自动提示卡和精确详情跳转。
4. 每分钟前端轮询和后端 7 天自动清理。
5. 防重复投递、权限校验、失败重试和验收记录。

本期不包含：

1. Gaia 主系统其他页面的铃铛、短信、邮件、企业微信、浏览器推送或 WebSocket。
2. 已处置、复核、处理人、处理结果、催办、撤回和通知偏好。
3. 上线前已有窜货明细的补发。
4. 新增可见侧栏菜单或独立“通知中心”页面。

成功标准：对新产生的疑似结果，符合范围的用户在下次轮询内看见正确未读数；在线页面仅弹出一张 5 秒卡片；从任意通知可打开准确详情；关闭卡片不改已读状态；相同风险不重复加未读；7 天后消息不可再查询且不计入未读。

## 2. 已确认的业务规则

### 2.1 判定、通知与去重

现有流程为：完工审核通过使工单变为 CLOSED，随后进入 afs_anti_diversion_task 异步任务；任务按商品唯一码写入 afs_anti_diversion_detail 的最近一次判断结果。

通知的触发条件是同一窜货明细进入一个新的“疑似”周期：

1. 明细原本不存在或最近一次不是疑似，本次判断为疑似：创建一条通知事件。
2. 明细最近一次仍是疑似，本次再次判断仍为疑似：更新明细，不创建新通知。
3. 明细最近一次为疑似，本次判断不再疑似：更新明细为非疑似，不创建通知。
4. 之后再次由非疑似变为疑似：这是新的疑似周期，可创建一条新通知。

因此，“一条窜货明细一条通知”的含义是同一疑似周期只产生一次通知，而不是每一次任务重跑都增加一条。通知创建与窜货明细更新在同一数据库事务中完成；任务重试、并发执行或重复提交不得形成重复通知。

### 2.2 历史数据与有效期

功能上线时，不为已经存在的 afs_anti_diversion_detail 记录补发通知。迁移会将已有疑似结果标记为已完成通知基线；只有迁移完成后由新的审核判断触发的疑似周期才生成消息。

通知的有效期从创建时间起算 7 × 24 小时。到期时：

1. 接口立即过滤该消息，未读数即时减少，不等待定时清理完成。
2. 清理任务物理删除消息及其个人阅读记录。
3. 窜货明细业务数据不删除，仍按 A36 原有规则保留或更新。

### 2.3 收件人与访问边界

判定完成时，收件人取当前租户内、状态启用、且属于下列任一范围的去重用户集合：

1. 系统管理员：已获得 afsNavigationAdministrator 隐藏导航授权的用户。
2. 总部运营：已获得 afsWorkspaceHeadquarters 隐藏导航授权的用户。

收件人按用户快照写入，不依赖角色名称文本，也不将同一用户因兼具两个角色而重复投递。角色新增只影响后续新消息，不补发历史消息；角色变更不删除已生成的个人通知记录。运行时仍按当前售后通知访问权限校验，已失去售后访问资格的用户不显示铃铛、不能读取通知或通过通知查看业务详情。

通知收件人必须同时具有 A36 窜货明细读取权限；权限配置错误而导致无法打开详情时，后端拒绝投递并使原窜货任务按既有重试机制重试，不能生成“能提醒但不能查看”的消息。

### 2.4 消息内容

消息正文不展示顾客、联系方式或完整安装地址。固定内容为：

| 字段 | 展示规则 |
| --- | --- |
| 通知名称 | 窜货监控异常提醒 |
| 窜货商品 | productName；为空显示“—” |
| 关联经销商/门店 | 优先 registrationStoreName，其次 inboundStoreName，再依次 dealerL3Name、dealerL2Name、dealerL1Name；均为空显示“—” |
| 系统判定窜货原因 | 将值为“是”的校验项以顿号连接：无购买登记、入库门店与登记门店不一致、安装地址不在登记门店销售区域、安装地址不在出库经销商销售区域 |
| 判定时间 | 明细 evaluatedAt |
| 操作 | 详情 |

消息记录保存上述摘要快照，避免后续主档名称变化导致历史提醒的文案漂移。详情弹窗读取关联明细的当前完整数据；若该明细在通知有效期内已经更新为非疑似，弹窗顶部仅提示“该记录当前不在疑似窜货列表中”，不引入处置或复核流程。

## 3. 页面与交互设计

### 3.1 页头铃铛

铃铛仅放在售后独立子系统页头右侧工具区，不改 Gaia 主系统通用页头。前端在系统通知权限接口返回可见后渲染图标。

| 状态 | 表现 |
| --- | --- |
| 未读数为 0 | 普通铃铛，无红色圆点 |
| 未读数 1～99 | 铃铛右上角红色数字徽标 |
| 未读数大于 99 | 显示 99+ |
| 接口加载 | 保留图标位置，不先显示错误数字 |
| 接口失败 | 不弹错误卡片，不影响当前业务页面；下一个轮询周期重试 |

点击铃铛打开通知概览浮层：按创建时间倒序展示最近通知、未读优先；单条显示标题、商品、关联渠道、原因摘要、时间和未读标识。打开浮层本身不改变已读状态。浮层提供“全部已读”和“查看全部”入口。

“查看全部”打开页内右侧通知抽屉，而不是新增导航菜单。抽屉支持“全部/未读”筛选、分页或继续加载，范围仅限最近 7 天未过期消息。点击单条的“详情”后才标记该条已读。

### 3.2 自动提示卡

售后子系统已有 FaNotification 全局提示容器，本期复用它承载窜货通知卡：

1. 完成页面首次通知加载时只建立本次浏览会话基线，不对已存在的未读消息逐条自动弹卡；铃铛红点和通知列表可见。
2. 后续轮询发现本会话未出现过的新通知时，展示最新的一张卡片，持续 5 秒。
3. 同一时刻最多展示一张。卡片存在期间新消息不替换当前卡片、不串行连播，只更新铃铛数和卡片底部的其他消息提示。
4. 当未读数除当前卡片外仍大于 0 时，卡片底部显示“另有 N 条疑似窜货消息，查看全部 →”；点击仅打开通知抽屉，不标记任何消息已读。
5. 关闭按钮、5 秒自动消失和切换页面都不标记已读。
6. 点击卡片中的“详情”后，先调用单条已读接口，再跳转并打开明细详情弹窗；已读接口返回幂等成功后继续跳转。

卡片必须有可见标题、详情文字按钮和关闭按钮；键盘可聚焦详情与关闭操作，红色徽标不能作为未读状态的唯一表达。

### 3.3 详情跳转

详情按钮跳转到现有 afsDiversionDetail 路由，并携带 notificationId 查询参数。窜货明细页面复用 useLinkedDetailQuery：读取 notificationId 后请求通知关联详情，打开既有“疑似窜货明细详情”弹窗；成功打开后清除 URL 参数，避免刷新时反复打开。

通知详情接口以 notificationId 为入口，先校验当前用户是收件人且消息未过期，再校验 A36 读取权限。前端不能只凭 detailId 直接拼接或从列表缓存中猜测详情。

## 4. 接口、数据与权限契约

### 4.1 HTTP 接口

基础路径：/api/afterSales/system-notifications。

| 方法与路径 | 调用端 | 请求与响应 | 错误语义 | 权限 |
| --- | --- | --- | --- | --- |
| GET /permissions | 页头初始化 | 返回 visible、canReadAll；visible 为 false 时不显示铃铛 | 未登录返回既有登录错误 | 已登录会话；服务端按通知访问策略计算 |
| GET / | 页头、浮层、抽屉 | 查询 status=ALL 或 UNREAD、page、pageSize；返回 rows、records、unreadCount | 参数非法为 422；无权为 403 | 仅当前用户自己的未过期收件记录 |
| PUT /{notificationId}/read | 卡片、列表详情动作 | 无请求体；返回 read=true、unreadCount | 不存在、过期或非收件人为 404；无权为 403；重复调用成功 | 当前用户自己的消息 |
| PUT /read-all | 浮层、抽屉 | 无请求体；返回 affectedCount、unreadCount=0 | 无权为 403 | 当前用户自己的全部未过期未读消息 |
| GET /{notificationId}/detail | 窜货明细深链 | 返回 detailId、currentSuspected 和 A36 详情展示字段 | 消息不存在、过期或非收件人为 404；明细无权查看为 403 | 当前用户的消息 + A36 读取权限 |

GET / 的单条 rows 结构至少包含 id、title、productName、relatedChannelName、reasonSummary、detailId、read、createdAt、expiresAt。时间统一使用服务端本地业务时区 ISO 格式；分页 page 从 1 开始，pageSize 最大 50。

读取、标记已读和全部已读均仅更新当前登录用户的 afs_system_notification_recipient 记录；不得根据前端传入的 userId 执行操作。

### 4.2 数据表

#### afs_anti_diversion_detail 扩展字段

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| risk_version | INT UNSIGNED NOT NULL | 同一唯一码从非疑似进入疑似的周期版本，初始为 0 |
| notified_risk_version | INT UNSIGNED NOT NULL | 已成功创建站内通知的最高风险周期版本，初始为 0 |

对迁移前已有的疑似行，初始化 risk_version=1、notified_risk_version=1；对迁移前非疑似行初始化为 0、0。此初始化是“不补发历史消息”的数据库保证。

#### afs_system_notification

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键，由现有 IdGenerator 生成 |
| notification_type | VARCHAR(64) | 固定为 ANTI_DIVERSION_SUSPECTED，为后续其他站内通知预留 |
| detail_id | BIGINT | 关联 afs_anti_diversion_detail.id |
| risk_version | INT UNSIGNED | 对应的疑似周期 |
| title | VARCHAR(100) | 固定标题快照 |
| product_name | VARCHAR(255) | 商品名称快照 |
| related_channel_name | VARCHAR(255) | 关联经销商/门店快照 |
| reason_summary | VARCHAR(500) | 命中原因摘要快照 |
| evaluated_at | DATETIME | 原判断时间 |
| expires_at | DATETIME | 创建时间加 7 天 |
| create_time / update_time | DATETIME | 审计时间 |

唯一索引：notification_type、detail_id、risk_version。该索引与同事务内的明细版本更新共同保证任务重试、重复审核和并发消费不会重复创建通知。

#### afs_system_notification_recipient

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| notification_id | BIGINT | 关联通知 |
| user_id | BIGINT | Gaia 用户 ID 快照 |
| read_at | DATETIME NULL | NULL 为未读，非 NULL 为已读 |
| create_time / update_time | DATETIME | 审计时间 |

唯一索引：notification_id、user_id。查询索引：user_id、read_at、notification_id。通知主表删除时级联删除个人收件记录。

### 4.3 事务、清理与并发

窜货任务处理每个商品候选对象时按以下顺序执行：

1. 更新或插入当前 afs_anti_diversion_detail。
2. 在同一事务中锁定该唯一码明细，取得 risk_version 和 notified_risk_version。
3. 仅当本次为疑似且 risk_version 大于 notified_risk_version 时，创建通知主记录、按当前角色快照创建收件人记录，并将 notified_risk_version 更新为 risk_version。
4. 任一写入失败则回滚本次任务事务，沿用 afs_anti_diversion_task 既有的最多三次重试和失败记录；不得提交明细却静默丢失应有通知。

新增 SystemNotificationCleanupScheduler，每小时执行一次物理清理。接口查询和未读数统计始终附加 expires_at 大于当前时间条件，因此消息在 7 天整点即失效，定时任务最多只影响物理回收时刻，不影响用户可见结果。

## 5. 菜单与权限配置

新增 Gaia 隐藏权限节点，不增加侧栏可见菜单：

| 配置项 | 值 |
| --- | --- |
| module code | afsSystemNotification |
| 名称 | 售后系统通知查看 |
| path | afterSales/systemNotification |
| type / is_hide | 1 / 1 |
| 父节点 | afterSales |
| 读取 API | GET$/api/afterSales/system-notifications/** |
| 已读操作 API | PUT$/api/afterSales/system-notifications/** |

该隐藏节点必须随现有 afsNavigationAdministrator 和 afsWorkspaceHeadquarters 一并授权给目标角色；同时保留 afsDiversionDetail 的读取 API 权限。不得将写入或角色授权逻辑放入售后业务建表 SQL，菜单和角色配置采用独立权限脚本及 Gaia 菜单管理流程。

前端导航清单补充该隐藏能力的稳定 code，但不投影为日常菜单。后端收件人解析器以现有隐藏导航授权和已启用用户为依据，不以角色名称、前端视角切换状态或浏览器缓存为依据。

## 8. 风险与非目标说明

| 问题 | 影响 | 设计处理 |
| --- | --- | --- |
| 审核完成与消息展示并非同一时刻 | 用户可能在审核后最多等待异步任务和 1 分钟轮询 | 保留现有 5 秒窜货任务消费，首期不建设长连接 |
| 角色或菜单配置遗漏 | 用户可能看不到铃铛或无法查看详情 | 收件人解析要求通知范围和 A36 读取权限同时满足；按真实账号验证 |
| 已有数据补发造成噪声 | 开发阶段用户被历史数据淹没 | 迁移设置已通知基线，只从迁移后的新风险周期开始 |
| 地址等敏感字段泄露到页头 | 页头被旁观时暴露更多信息 | 消息摘要不保存、展示完整安装地址；详情仍沿 A36 权限和现有脱敏机制 |
| 7 天内明细状态变化 | 原消息与当前列表不一致 | 消息保存摘要快照；详情展示当前数据并给出轻提示，不新增复核流程 |

## 10. 全角色通知入口、业务提醒与列表优化（2026-10-20）

### 10.1 确认范围与实现边界

- 来源：用户要求每个后台角色都显示通知图标，接入适合提醒的消息，采用后台系统通知列表样式，并修复总部运营每次打开时“两条数据 → 骨架加载 → 相同两条数据”的体验。
- 实现限于 `gaia-ui/apps/after-sales`。工具栏入口不再依赖窜货通知权限；管理员、总部、客服、服务站与门店共享入口，无消息时仍可打开空状态。
- 通知分为系统消息、待办提醒、任务结果。窜货消息仍通过原个人收件接口读取和标记已读，原收件人、详情权限、7天有效期及自动提示规则保持；入口可见不授予原消息权限。
- 业务待办直接复用已授权工作台队列和真实业务接口；不新增工单事件投递、消息表、阅读记录或数据库授权。待办数表示当前业务状态，不是未读数；“全部已读”只处理系统消息，不清除业务待办。
- 任务结果读取当前账号最近10条导入导出任务，保留成功／失败／执行中／等待状态；点击打开既有任务列表抽屉。服务端任务接口按创建用户限制，不读其他人的结果。

### 10.2 接入来源与权限

| 视角／来源 | 当前接入 | 访问与跳转 |
| --- | --- | --- |
| 总部运营 | 待分配服务站、待完工、缺件、待分配人员、待完工审核 | 同时具有当前菜单与对应领域读取授权时查询；链接进入对应业务列表 |
| 客服作业 | 待分配服务站、待分配人员、待完工审核、处理中投诉 | 按原队列与后端数据范围查询；无菜单或无读取权限不请求业务列表 |
| 服务站作业 | 待分配人员、今日期望服务、待完工、缺件、待处理领料／退料 | 配件待办复用本站工作台 `todoOnly` 和 `readable`，不自行扩大服务站范围 |
| 门店业务 | 未申请安装、部分申请安装的购买记录 | 按原顾客档案读取权限和门店数据范围；可办理性仍由目标业务记录及动作决定 |
| 各视角任务结果 | 当前账号最近10条导入导出记录 | 同时要求任务菜单与任务读取权限；无授权不请求任务列表 |
| 系统管理员视角 | 原窜货系统消息及个人任务结果 | 不在系统管理视角额外查询业务队列；切换相应业务视角后展示其待办 |

业务提醒按原工作台队列顺序显示，数量为0时不展示该项；链接进入相应完整业务列表，不宣称已自动应用提醒状态筛选。系统消息、业务待办和个人任务独立维护语义，不把待办或任务伪造为可标记已读的事件消息。

### 10.3 展示与加载契约

- 保留32px工具栏按钮、16px铃铛及原未读圆点／轻晃动效。系统未读或存在业务待办时显示圆点，无障碍名称分别说明未读数和待办数；没有虚构消息数量。
- 以用户补充截图为当前样式依据：概览320px宽、约320px固定高度并受视口最大高度约束，左侧52px竖向图标栏，右侧标题／时间两行列表，底部为全部标记为已读／查看全部。系统消息、待办和任务在数量大于0时显示数字徽标，紧凑概览超过99显示99+，悬停及无障碍标签保留完整数量。概览消息行不加分割线，标题及商品名合成单行省略，悬停可查看完整摘要。完整通知抽屉保持520px宽、文字页签和详细内容。列表内部滚动，保留键盘焦点、禁用／加载状态及明暗主题变量。详见[截图对齐与加载修复](#notification-vertical-fix-20261020)。
- 首次没有已加载结果时显示一段加载提示；已有记录或已确认空结果的后台刷新保留当前内容，只有显式筛选／翻页改变结果范围时清理旧范围。错误保留在通知面板中，允许重试，不替换整个业务页面。
- 铃铛概览只请求未读消息；成功查看后移出概览，全部标记已读后清空概览。查看全部每次默认全部消息，已读仍可在7天有效期内追溯；详情失败不移出。系统概览一分钟内重复打开复用当前结果，并合并并发请求；显式刷新和一分钟轮询可重新读取。新消息提示只对本浏览会话新出现的未读消息生效。
- 待办及任务按分钟刷新，后台不可见时暂停轮询；视角、账号／租户或可用菜单变化立即清空旧提醒并取消请求，旧响应不能写回新上下文。系统消息按账号／租户会话隔离，撤销消息权限时清理当前概览；抽屉关闭、筛选、分页继续使用独立请求代次。
- 系统消息在当前页面复用原业务详情弹窗就地查看，不先跳转列表；详情成功读取后调用原单条已读接口，再关闭通知面板并展示详情。全部已读仍调用原接口。所有消息接入继续由原服务端权限和数据隔离决定，不因前端菜单或图标可见绕过授权。
