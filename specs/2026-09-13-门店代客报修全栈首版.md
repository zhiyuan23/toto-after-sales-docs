# 门店代客报修全栈首版

- 日期：2026-09-13
- 对应入口：D02 门店工作台、D07 顾客购买记录
- 需求依据：DLR-015、FS-018、统一工单状态模型
- 状态：本地基础切片已实现；目标环境迁移、真实门店允许／拒绝账号验证及业务验收待完成

## 1. 业务范围

1. 代理商管理员或门店店员先进入授权数据范围内的已有顾客购买记录，从统一“发起服务”入口选择维修；不建立独立报修菜单或脱离购买记录的快捷报修按钮。
2. 本次可选择一个购买登记下 1～100 个未退回产品实例；任一实例已有活动工单时拒绝重复建单。
3. 门店填写故障描述、联系人、手机号、期望日期／时段和上门地址；故障描述必填，期望日期不得早于当天。
4. 后端固定工单语义为 `orderType=REPAIR`、`intakeChannel=DEALER`、`source=DEALER`、`serviceMode=ONSITE`，客户端不能覆盖这些字段。
5. 提交后创建统一工单、商品关系和首条不可变状态历史，首态为 `PENDING_ACCEPTANCE`，由客服继续受理和分配服务站。
6. 门店不获得分配服务站、跨站改派或派服务人员权限；服务站收到已分配工单后再从本站候选人员中派工。

## 2. API、权限与数据保护

- 新增 `POST /api/afterSales/customer/dealer/repairs`，使用独立 `dealerRepair` 权限，不复用购买记录的普通创建权限。
- 请求只接受登记与实例 ID、联系与地址、期望时间、故障描述、备注和 `clientRequestId`；不接受服务类型、渠道、来源编号或服务方式。
- 读取购买记录、选择产品实例和提交操作继续受租户、组织／门店数据范围约束；联系人、手机号和地址沿用既有加密存储及脱敏返回。
- 同一操作人和 `clientRequestId` 重试返回同一工单；不存在、越权、已退回或存在活动服务的实例均拒绝提交。
- 权限迁移为 `afsDealerCustomer` 增加“代客报修”操作及上述精确 POST API。迁移脚本只为管理员角色建立验证授权，不推断生产门店角色 ID 或组织绑定。

## 3. Web 交互

- 门店工作台和“顾客购买记录”的记录动作区只显示一个“发起服务”；打开后在同一弹窗选择安装或维修。不存在脱离购买记录、无法明确关联商品实例的报修按钮。
- “发起服务”在至少一种服务可办时显示：安装要求 D07 的创建权限及可安装实例，维修要求独立报修读／创建权限及未退回实例；不可办的类型在弹窗内禁用。
- 打开前重新读取购买详情；弹窗先确认购买记录和商品实例，再选择服务类型并展示对应字段，同时明确“提交后由客服受理，门店不分站或派人”。
- 选择安装时调用既有安装申请接口，选择维修时调用本 Spec 的独立报修接口；统一的是用户入口，不合并权限、载荷白名单或后端固定语义。
- 可选择未退回实例；保存成功后关闭弹窗并刷新当前列表／队列，失败保留输入并显示可重试错误。
- 客服的通用服务受理表单保持安装／维修／指导及渠道选择能力，不与门店的严格报修入口混用。

## 4. 主动不实现

- 不支持无购买记录的新顾客报修、顾客身份合并或门店代办产品注册；这些需要独立身份、授权与主档契约。
- 不新增图片／视频上传、故障分类、保内外判定或报价；首版复用现有文本问题描述和资格核验后续流程。
- 不自动选择服务站或服务人员，也不把门店操作权限扩大为客服／服务站职责。
- 不执行目标数据库迁移、不写入真实业务样例，不把管理员验证授权当作正式门店角色验收。
