## 当前契约：2026-09-28 简化流程

- 来源：用户确认消费者只需“处理中／已办结”，要求按简化方案修改现有系统。
- 范围：A24／C19，CS-013／CAPP-017；状态为研发修改与验证，业务验收负责人待分配。下文四阶段内容为当时历史，状态流转与对客边界以本节为准。
- 新建直接 `PROCESSING`（处理中）；后台可多次“记录跟进”（沿用 process 权限及接口），不改变状态；实际处理完成并告知消费者后“办结投诉”（沿用 close 权限及接口）转 `CLOSED`（已办结）。不再强制责任认定和独立回访阶段，不自动联系／通知、不更改原工单或评价。
- process 必填 1～2000 字内部跟进 `content`；close 必填 1～2000 字对客 `resolution`，内部备注可不填。两类内容分别加密，正文、结果、状态、独立时间及不可变历史保持事务一致。版本冲突、幂等重试、修改请求内容拒绝、本人归属、租户与工单范围继续执行。已办结不能追加或修改。
- 消费者提交成功提示“投诉已提交”，处理中提示已收到反馈，已办结直接展示结果和办结时间；不显示内部阶段轨迹和内部备注。继续反馈跳转现有人工客服，不自动重开；办结后同一服务仍可新建独立投诉。
- 后台列表每行仅显示一个主要操作：后端 actions 含 process／close 时显示“处理投诉”，否则有 detail 时显示“查看详情”；处理与查看互斥，不按角色或状态自行推断权限。详情与工作台复用处理表单，主题详情链接保留。处理表单展示投诉正文、关联服务编号、联系偏好和按需展开的历史，选择“继续跟进／办结投诉”，一次保存记录与状态。有跟进权限时默认继续跟进，只有办结权限时直接进入办结；没有对应后端 actions 不显示该选项，重新读取详情后无可执行动作则禁止提交。
- 继续跟进必填内部记录，按钮“保存跟进”；办结必填“处理结果（消费者可见）”，内部备注选填且默认折叠，按钮“确认办结”，明确提示办结后不能修改。两种模式分别保留草稿，切换不会复制或公开内部内容；提交只携带当前模式字段。同内容失败重试沿用请求号，变更动作／提交内容／版本后使用新请求号。历史仅展开时加载，不重复显示历史标题。
- 兼容：旧 OPEN／FOLLOW_UP 返回／筛选为 PROCESSING，下一次写入归一；旧事件原文和旧阶段保留。旧 CLOSED 不复制内部结案内容到公开字段，缺结果时提示联系客服。新增 `resolution_ciphertext`，不批量重写投诉状态或历史。
- 权限：create／process／close 保持独立授权与稳定 ID；responsibility 退役，后端不接受旧动作，权限返回 false，配置停用并移除旧角色关系及勾选缓存；不将旧责任认定权限自动扩为办结权限。客服专员仍默认建档／跟进，办结另授。
- 交付脚本：售后源码 `database/20260928_complaint_simplify.sql`、`20260928_complaint_simplify_permissions.sql` 与同名恢复说明；API 契约同步更新。

## 实施范围和阶段

投诉关联有权访问的真实工单，投诉编号独立生成。列表按主题／工单号和阶段查询。建档记录主题、受理时间和投诉正文；主题供列表检索，不填写电话、地址等敏感信息。正文和各阶段记录加密保存，只在具有对应详情／历史权限且工单范围可见时解密，列表不返回正文。

依据需求中的人工子流程，实施阶段为待认定 → 处理中 → 待回访 → 已结案。责任认定、处理完成、回访结案分别提交阶段结论，操作人和时间由服务端记录；系统不自动判责、不预设责任单位或赔偿规则。此阶段拆分是本次实现方案，尚未经业务验收。

每次动作追加不可变历史。按投诉行锁、版本令牌和请求号防止跳阶段、并发覆盖与重复提交；同一请求号不同内容拒绝。受理时间、创建时间、各阶段时间、结案时间独立保存，前端显示从受理至当前／结案的经过时间。投诉流程不改变原工单状态，不触发通知或费用。

## 权限和数据范围

列表、详情、历史、工单选项、建档与三个阶段操作分别校验 API 权限。数据范围复用工单查询的代理商／门店授权以及租户路由，不复制组织主档、不扩大范围。工单关系在建档后不可更改。没有删除或覆写历史接口。

## 2026-09-25 消费者投诉扩展（C19）

### 入口与投诉对象

消费者投诉的对象是“本人某次服务体验”，不要求消费者选择客服、服务站或服务人员作为责任对象。主入口位于服务记录详情“投诉本次服务”；低分或选择“部分解决／未解决”的评价显示正式投诉提示；“服务 → 投诉记录”和客服渠道页提供补充入口。无关联服务的一般意见仍走人工客服，首版不创建无工单投诉。

提交字段为问题类型、5～2000 字情况说明和电话／微信／均可联系偏好。服务端使用当前消费者会话校验 `account + instance + order` 归属，不能信任前端工单号；同一工单同时只允许一条未结案的消费者投诉。请求号保证重试幂等，相同请求号改内容返回冲突。

### 流程与对客边界

消费者提交后进入既有 A24 `OPEN → PROCESSING → FOLLOW_UP → CLOSED` 流程，对客文案为“待核实 → 处理中 → 待回访 → 已办结”。投诉与原工单、消费者评价相互独立，不自动改变工单状态，不自动判责、赔偿或承诺处理时限。A24 列表和详情区分消费者／客服登记来源，展示对客编号、问题类型和联系偏好；内部责任认定、处理结论和操作人不通过消费者接口返回。

首版不支持投诉附件。既有服务申请媒体上传有服务阶段和用途约束，不复用为投诉附件；后续需单独确认对象归属、内容安全、保留期和访问审计后再增加。
