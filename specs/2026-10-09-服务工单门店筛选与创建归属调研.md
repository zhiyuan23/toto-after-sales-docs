# 服务工单门店筛选与创建归属调研

门店业务的服务工单需要按工单的创建门店隔离，并在首个查询条件提供授权门店单选。现有查询按购买登记门店控制范围，建单来源又由调用接口决定，不能直接满足该要求。已保留共用页面与统一工单表，补齐创建门店快照、按已授权工作视角查询和各建单入口的一致归属。下文现状分析为开发前快照，最终实现及验证结果见实施记录。

## 已确认业务规则

1. 仅门店业务的服务工单显示“门店”查询条件，放在第一位；单门店仍显示下拉框并默认选中，多门店默认不选。
2. 下拉选项只包含当前账号有权访问的门店。多门店未选择时，显示全部授权门店自行创建的工单。
3. “门店自己创建”按建单当时的创建门店认定。同一门店不同员工创建的单均可见，不仅限当前员工本人。
4. 门店列表排除客服和消费者创建的工单，即使这些工单关联了本门店的购买登记。
5. 客服作业和总部运营不显示该筛选，包含门店代客建单、消费者小程序自建和客服创建三类来源。
6. 客服及总部查询当前租户全量工单，不再按购买门店的账号组织范围缩小读取结果；保留租户隔离及接口、岗位授权。全量读取不自动扩大建单、派单、审核等写权限。
7. 创建门店不一定等于购买门店，二者分别保存。创建门店必须由后端核验为账号有权建单的门店，不能从购买门店直接推断。

## 当前实现的问题

### 共用页面未传工作视角和门店

三个视角在 `apps/after-sales/src/features/navigation/manifest.json` 中均引用 `afsWorkOrder`，进入同一个 `WorkOrderListPage.vue`。查询字段目前为综合关键词、联系电话、工单状态和期望日期；`WorkOrderSearch`、`buildOrderQuery` 及后端 `/customer/work-orders` 均没有门店和工作视角参数。切换导航视角本身不会改变后端查询范围。

依据：前端 `WorkOrderListPage.vue:131`、`customer/shared/model.ts:40` 和 `:56`；后端 `CustomerApi.java:56`、`CustomerAppService.java:827`。

### 当前门店表示购买门店

`CustomerMapper.xml` 的 `orderFrom` 将工单关联到购买登记，再根据 `r.store_id` 判断范围；列表门店名称也读取 `r.store_name`。现有工单写入字段没有独立的创建门店。顾客在 A 店购买，之后由消费者或客服申请服务，现有查询仍把该单与 A 店关联。购买登记门店被编辑时，历史工单所显示和用于查询的门店也可能变化。

依据：`CustomerMapper.xml:158-159`、`insertOrder` 和 `updateRegistrationContent`。

### 建单来源由入口决定，无法完整代表创建岗位

| 建单入口 | 当前行为 | 与新要求的关系 |
| --- | --- | --- |
| 服务工单页的“创建工单” | 三个视角使用同一个弹窗，均提交 `/customer/intake/orders`，后端固定记录 CUSTOMER_SERVICE | 门店在该入口建的单也会记成客服单 |
| 顾客购买记录的“发起服务” | 共用页面启用 allow-dealer-service；安装调用 appointments，维修调用 dealer/repairs，后端记录 DEALER | 客服或总部从该入口办理也可能被记成门店单 |
| 消费者小程序建单 | 后端明确记录 CONSUMER | 保留现有消费者身份与本人范围 |

因此不能只加 `source=DEALER` 作为门店筛选，也不能用 `intake_channel=DEALER` 替代创建来源。受理渠道是可以选择的业务字段，表示联系渠道，不是创建人的岗位证明。

依据：`WorkOrderCreateDialog.vue:705`；`customerArchive/index.vue`；`ServiceOrderDialog.vue:297-301`；`CustomerAppService.java:675-694`、`:805`；`ConsumerPurchaseService.java:378`。

### 无门店工单存在范围放行分支

当前工单使用的 `scope` 包含 `r.store_id IS NULL OR ...`。没有购买登记或购买门店的工单会通过该分支；SQL 没有再按当前工作视角排除消费者来源。因此，有工单读取接口权限的门店账号在源码逻辑上可能读到这类工单。具体影响数量需在实施前对目标测试库做只读统计。

此外，列表、详情、购买登记关联工单，以及派单、费用等接口并非全部经过同一个对象范围校验。仅改列表不能完整约束直接访问工单编号和关联子接口。

依据：`CustomerMapper.xml:6`、`:159-165`；`WorkOrderWorkflowMapper.xml` 的独立 `scope`；`OrderFeeManagementAppService.java:23-25`。

## 已确认实现方案

### 页面和筛选

- 继续复用现有服务工单页面，不复制三套页面或重复注册菜单。
- 按已授权的当前 `viewId` 判断是否显示门店字段，而不是按角色名称或账号的最高权限判断。
- 门店字段放在查询数组第一位，展示“门店编码 / 名称”，支持单选和搜索。
- 首次查询前加载授权门店。单门店初始选中，重置恢复该默认值；多门店初始及重置均为空，空值表示全部授权门店自建单。
- 无授权门店时返回空列表并给出明确提示。选项加载失败时显示可重试错误，不能退化成全量查询。
- 切换视角时清除门店、分页、定位详情和旧列表，取消或丢弃旧响应；即使共用路由未变化，也重新应用上下文。
- 复用 `EsSearch` 的字段默认值和 `useListPage` 的搜索、清空及过期响应保护，不修改通用组件来推断业务范围。

### 后端查询和门店选项

保持统一领域接口，请求头 `X-After-Sales-Workspace` 表达 `dealer|serviceDesk|headquarters` 等当前工作视角，门店查询增加 `storeId`。请求头只表达请求的视角，服务端仍核验当前登录账号的有效视角授权与接口权限。

门店视角的查询条件为：当前租户内、来源为门店创建、创建门店在账号授权范围内；选定门店时再取与所选门店的交集。不允许缺省参数、伪造客服视角、越权门店或空门店分支绕过限制。旧调用方的缺省策略应采用安全的账号授权推断，多视角无法唯一确定时拒绝歧义请求，不能默认全量。

客服及总部读取当前租户全量工单，包括三类已确认来源，不再由购买门店组织范围限制读取。创建、派单、审核等写权限继续独立判断，获得全量查询不代表获得全量操作权限。API 来源的处理保留现有规则，单独核对，不凭本次三类来源描述静默删除既有 API 工单。

建议增加轻量 `GET /customer/work-orders/store-options`，只返回当前账号有权查询的门店。沿用售后自有 `afs_store`、`afs_dealer` 与 Gaia 组织授权的映射；读取门店选项依附服务工单读取能力，避免要求账号额外拥有购买登记或门店管理权限。

工单查询选项包含仍有权限的停用门店，可查历史；建单仍要求启用门店。专用选项接口与购买记录的既有门店选项独立，避免改变购买模块。

### 固定创建归属

建议在统一工单表增加 `created_store_id`、`created_store_code`、`created_store_name`，记录建单时的创建门店及快照。保留既有 `source` 和 `create_user`，不以员工当前组织或购买记录的后续归属重新计算创建门店。购买门店与创建门店保留各自含义，不覆盖原购买事实。

所有后台建单入口使用同一归属解析：服务端校验当前视角、创建操作和门店归属，门店业务记录 DEALER 及明确创建门店，客服／总部代建记录 CUSTOMER_SERVICE；消费者继续由消费者会话记录 CONSUMER。前端不能直接指定可信来源值。

创建门店与购买门店可以不同，建单时必须单独确定创建门店。建议建单弹窗增加创建门店：单门店默认选中；多门店优先带入列表已选门店、允许改选，列表未选时要求选择后才能提交，不能默认取第一家。该交互已确认。

跨购买门店办理沿用购买记录读取权限。本次不扩大按手机号检索未授权购买商品的范围。

创建请求幂等还应校验视角和创建门店，防止同一个请求号切换上下文后重放到另一门店。原事务、商品可服务条件、费用初始化和自动分派保持一致。

候选索引为来源、创建门店、创建时间和工单主键的组合；迁移时按目标库现有结构、数据量和执行计划确定。使用宿主租户路由，不新增跨租户全量查询。

### 历史工单处理

先只读统计现有来源、创建入口和账号、关联购买登记、无登记工单及可证明的原始门店，形成可确认的回填清单。

已经明确从门店专用入口创建、且能证明原始创建门店的工单可按证据回填。现有 CUSTOMER_SERVICE 工单可能包含门店从共用弹窗建的单；现有 DEALER 工单也可能包含客服从购买记录入口创建的单。不能仅凭现在的员工岗位、受理渠道或现在的购买门店批量更改来源和归属。

无法证明归属的历史单需要业务核对；未确认时保持原始事实，在客服／总部的合法读取范围内继续可见，不自动纳入门店自建列表。迁移与回填分开准备回退方案，并回读验证。

### 对象权限与关联入口

统一工单可见性判断，覆盖列表及数量、详情及定位链接、沟通和附件、费用，以及页面开放的工单动作。购买登记关联工单和工作台跳转必须核对是否能绕过门店自建范围。

优先增加明确的工单范围解析和按上下文查询，避免直接改动被其他领域复用的通用购买登记 `scope`。客服／总部全量读取也不得扩大门店建单、服务站履约或消费者本人数据权限。

## 实施范围和验证

主要改动位于 `gaia-ui/apps/after-sales` 和 `gaia-after-sales`；宿主用于装配验证。通常无需复制主系统 legacy 页面，也不需要为三个视角新建服务工单菜单。新增精确读取 API 或创建契约时，核对并更新 Gaia 操作配置；业务迁移不混入菜单及角色授权 SQL。

关键验收场景：

1. 一个授权门店默认选中；多门店默认未选、展示授权门店自建单合集；选 A 后只显示 A 店自建单，重置恢复约定默认。
2. 同店不同员工建单均可见；消费者／客服为 A 店顾客创建的工单在门店视角不可见。
3. 未授权门店、零门店账号、无登记消费者工单、伪造工作视角、缺省上下文和跨租户请求不越权。
4. 同一多岗位账号在门店与客服／总部切换，列表、总数、筛选和详情同步切换，旧请求结果不回填。
5. 从服务工单及购买记录入口创建安装、维修、指导单，来源和创建门店均正确；消费者建单不受影响。
6. 购买登记门店被编辑或员工调店后，历史创建门店不变；原门店其他有权员工仍按创建门店读取。
7. 详情、沟通、附件、费用和关联跳转按相同对象范围拒绝不可见工单；写操作仍单独验证权限。
8. 客服／总部无需门店筛选，能读取当前租户内各购买门店和无购买门店的三类来源工单；写权限独立校验。当前服务工单排除 PENDING_VERIFICATION，本次继续排除待核验状态，已确认。

## 已确认的补充边界

1. 建单时如何选择创建门店：建议弹窗增加必填创建门店，单门店默认选中，多门店带入列表已选值并允许改选；列表未选时必须选择后才能提交。
2. 跨店购买商品的检索范围：沿用购买记录读取权限。
3. 无法证明创建门店的历史工单：建议暂不纳入门店自建列表，客服／总部仍可查询，人工确认后再回填。
4. 已停用门店的历史查询：建议账号仍有该店权限时可筛选并查看历史工单，但不能选择该店创建新单。
5. 门店信息的页面展示：现有列明确为“购买代理商”“购买门店”，增加“创建门店”。
6. 全量查询的状态范围：保留待核验工单 PENDING_VERIFICATION 的既有排除规则。

用户已逐项确认上述建议；仅门店业务建单选择创建门店，总部、客服、消费者建单不选。代理商列明确显示“购买代理商”。当前已进入实施，验证与部署结果在下文追加，研发验证不代替业务验收。
