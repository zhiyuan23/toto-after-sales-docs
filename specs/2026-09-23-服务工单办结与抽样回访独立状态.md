# 服务工单办结与抽样回访独立状态

- 日期：2026-09-23
- 依据：用户确认从实际售后服务出发，设计并实施工单终态与工单外抽样回访。
- 范围：服务工单主状态、已办结判定、再次服务、报表与派单口径、消费者／服务人员／Web 状态展示，以及人工抽样回访。

## 1. 业务决定

完工审核是本次服务是否已履约的责任确认。审核通过时，工单由 `PENDING_REVIEW` 直接进入唯一正常终态 `CLOSED`，界面名称统一为「已办结」。同一事务写入审核决定、工单状态、状态历史和办结时间；审核退回仍回 `PENDING_COMPLETION`，保留原版本，补充后重提。`CANCELLED` 是未完成服务的终止结果，不计已办结。

回访是工单办结后的质量抽查，不是所有工单的必经阶段，也不决定工单能否办结。客服可在已办结工单中人工抽样，创建与原工单一对一关联的回访任务；未抽中的工单没有「待回访」。回访任务独立经历「待回访 → 已完成／未接通」；联系记录、满意度和问题描述留痕，回访不会写回工单主状态。一次有效结果只能登记一次，重复或过期提交拒绝。未接通为抽样任务的终结结果，不伪造满意度。

消费者自发评价与客服抽样回访是不同事实。抽样回访的满意度用于已有派单评分时，必须以有效已完成回访及明确满意／不满意为样本；无样本继续按现有缺样本规则处理。抽样回访发现未解决问题，应关联投诉或按再次服务规则新建工单；不直接复开已办结工单、不删除原服务及审核证据。费用／结算仍是独立单据或事项，未确认其业务范围前不作为所有工单的关闭前置。

## 2. 主状态与边界

```text
待核验申请（仅服务受理） → 待分站 → 待分配人员 → 待完工 → 待审核
                                                        ↘ 退回待补 → 待审核
待审核 + 审核通过 → 已办结（CLOSED）
处理中 + 合法取消 → 已取消（CANCELLED）
已办结 + 被抽样 → 独立回访任务（不改变工单状态）
```

- `PENDING_DISPATCH` 实际含义是尚待分配承接服务站，`PENDING_ASSIGNMENT` 是已分站、待分配服务人员。已预约、缺件、改期、断联与审核退回是业务事实／任务标签，不额外占用正常主状态终点。
- `PENDING_FOLLOW_UP`、`COMPLETED` 与 `PENDING_HANDOVER` 只作历史兼容，不再由新业务写入。对历史记录保持原值可读；只有核实了有效审核通过记录，才可按受控迁移将历史 `PENDING_FOLLOW_UP` 办结并补状态历史，不能把未知旧单一律改名。
- 已办结／已取消不占用同一商品的活动工单名额。二者都不能经旧异常快照直接复开；再次服务创建新单并关联历史。
- 运营报表中的「已办结」只统计 `CLOSED`，完工审核通过量应以审核事实计；不能再把遗留 `COMPLETED` 与 `CLOSED` 混为当前关闭数量。师傅「今日完工」按审核通过时间统计，不按已取消或当前更新时刻推断。

## 3. 实施与验收

1. 后端将审核通过改为 `CLOSED`，确保并发版本、权限、事务和历史一致；回访使用独立任务与授权接口，抽样只允许已办结工单，单工单至多一条任务。
2. 统一活动工单、已办结报表、服务站／人员满意度、人员今日完工、SLA 与页面过滤口径。历史状态只读兼容，迁移脚本提供预检和回退。
3. Web 在已办结工单提供受权抽样及回访办理入口；师傅看到「已办结」，消费者按三阶段展示「服务完成」而非「等待回访」，未抽中时不显示虚构待办。
4. 验证审核通过、退回重提、重复审核、无权／跨范围、重复抽样、未接通、有效回访、再次服务、统计及历史兼容。源码验证、测试数据库迁移和共享环境业务验收分别记录。

本 Spec 是 2026-09-23 新确认业务口径，覆盖此前「审核通过 → 待回访 → 已关闭」的主线设想；不追认历史旧单已被实际回访或结算。

2026-09-24 用户确认消费者服务进度简化为「服务安排 → 服务处理 → 服务完成」。师傅提交完工后消费者显示服务完成，后台仍待审核；审核退回明确区分仅补资料与继续服务。取消、缺件、改期、联系未果等在三阶段内展示真实情况，不把取消视为成功完成。 以本文后续三阶段契约为准。

消费者首页摘要、服务页、产品服务记录和进度详情共用同一映射。主阶段固定为「服务安排、服务处理、服务完成」，当前进展和下一步用独立说明展示；远程指导沿用相同阶段。三阶段不新增或改写后端主状态。

| 业务事实 | 消费者阶段 | 具体展示与边界 |
| --- | --- | --- |
| 待核验、受理、分站、派人、发布／接单兼容状态 | 服务安排 | 申请已收到／正在核实／正在安排服务；期望时间不能当作预约 |
| 已派人但无服务开始事实 | 服务安排 | 联系确认方式和时间；不能因 `PENDING_COMPLETION` 就声称师傅已经开始 |
| 已确认预约，尚未开始服务 | 服务安排 | 服务时间已确认；确认事实取正式预约历史／明确预约状态 |
| 已实际开始现场／远程服务 | 服务处理 | 服务人员正在处理／正在提供远程服务 |
| 完工已提交、待审核 | 服务完成 | 本次服务已完成；服务记录正在确认，暂无需消费者操作；不是工单办结，也不等于消费者认可问题解决 |
| 审核退回 `MATERIAL_ONLY` | 服务完成 | 师傅补充记录，不要求消费者重新走流程 |
| 审核退回 `CONTINUE_SERVICE` | 服务处理 | 本次服务需继续处理，服务人员联系确认后续安排；重提后恢复完成展示 |
| 历史退回无明确类型 | 服务处理，待跟进 | 服务进度待确认；不能从备注、照片缺失等文本猜测是否已完成 |
| 缺件、改期、联系未果、问题跟进 | 已开始服务则服务处理，否则服务安排 | 突出等待配件／时间调整中／等待与您联系／问题跟进，给出下一步；异常优先于旧审核完成事实 |
| 拒单后重新安排人员 | 服务安排 | 正在重新安排人员，不把人员拒单说成消费者申请被拒绝 |
| 已取消 | 在已发生的安排／处理阶段终止 | 明确本次服务已取消；当前节点显示已取消、后续未进行，完成节点不打勾；历史记录仍可打开 |
| 审核通过 `CLOSED` | 服务完成 | 服务记录已确认；内部唯一正常终态不变 |
| 历史 `COMPLETED`／`PENDING_FOLLOW_UP`／`PENDING_HANDOVER` | 依审核事实判断 | 最新提交有通过审核可展示完成，否则历史进度待确认；不伪造回访或改写旧单 |
| 未识别状态 | 保守显示进度待确认 | 不泄露原始枚举、不自动标完成；可刷新或联系客服 |

### 接口与审核操作

消费者摘要接口增加白名单事实：`serviceStarted`、`appointmentConfirmed`、`exceptionCode`、`completionReviewDecision`、`completionRejectionType`。后三项不携带内部审核原因、人员身份、精确坐标、签名或证据地址。列表、产品服务列表、单条详情和建单回执复用相同查询投影与本人可见范围。审核决定必须属于**最新完工提交版本**，重提后不得沿用旧退回。

A21 退回必选「仅补充资料」或「需要继续服务」，分别提交 `rejectionType=MATERIAL_ONLY/CONTINUE_SERVICE`；后端校验、审核记录、状态历史和工单迁移处于原事务中，权限和版本门禁不变。缺少或未知类型返回 422，审核通过不需要类型。继续服务自动将 `SERVICE_RESULT` 纳入必补项，复用师傅现有定向补充与重提入口，要求记录继续服务后的结果；不新建发布、接单或交单环节。

新增迁移为 `gaia-after-sales/database/20260924_consumer_service_progress.sql`，只在 `afs_completion_review` 增加 `rejection_type VARCHAR(30) NOT NULL DEFAULT ''`；旧记录不自动分类。发布顺序为迁移、后端、Web 与消费者端；旧版 Web 无类型的退回请求需升级后重试。回退应用保留分类列和审核证据，详见源码同目录 `.rollback.md`。

消费者展示完成不释放活动工单占用、不开放额外评价资格，不改变结算或报表；这些继续取后端正式规则。固定三阶段是正常进度，取消是中途终止，不能为了“只有三个阶段”伪装为服务成功。
