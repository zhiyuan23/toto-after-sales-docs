本文件是项目说明的共同内容大纲，供后续查看、调整和优化，再据此制作 PPT、演示网页或其他展示材料。当前为讨论初稿，先确定讲述顺序和内容重点，暂不固定页数、展示形式或最终讲稿。

网页汇报已按本大纲整理为 [21 屏完整演讲版](网页演示/项目汇报/index.html)，支持手动展开、目录跳转、讲解备注与嵌入工单动画；[内容与修改说明](网页演示/项目汇报/README.md)记录模块映射和后续调整位置。

## 1. 项目来源与建设思路

**回答：项目从哪里来，如何开始建设？**

本次项目以 **TOTO 现有售后服务系统及实际业务中的原始需求**为起点，保留真实业务依据，重新梳理售后服务全流程。

- **需求来源：** TOTO 现有售后系统与实际业务，涵盖业务角色、售后环节和业务规则。
- **建设思路：** 保留业务依据，重新梳理全流程，从真实业务出发明确改进方向。

建议展示：用 TOTO 作为需求来源的视觉重点，旁边简短展示“保留业务依据，重新梳理全流程”。本章不再展示平台结果或产品演进图；简短讲述后进入第二章的业务痛点与建设方向，蓝鲸数字与复用价值由第三章承接。

## 2. 业务痛点与建设方向

**回答：原有业务有哪些问题，这次分别要改变什么？**

将业务痛点与建设目标放在同一页对应讲述，避免分别介绍时重复表达自动化、数据联动和好用。

| 原有问题 | 建设方向 |
| --- | --- |
| **信息分散、跨环节查询多** | **数据完整联动：** 打通商品、客户、工单、服务资源、配件与结果，让信息随工单流转，进展、责任和历史可追踪 |
| **人工衔接、重复操作多** | **流程自动化：** 通过标准化流程、状态联动和智能分配，让系统参与流转，减少人工协调与重复操作 |
| **UI 设计与交互体验有待提升** | **视觉与交互升级：** 从页面布局、字体、配色到按钮、卡片与交互细节统一设计，让页面更美观、操作更直观 |

讲解时可补充：商品登记到服务申请、调度、履约、审核及评价回访形成关联；消费者已购产品与后续服务体验相连接。具体流程与页面留到后续功能和亮点章节展开。

产品体验追求：**功能完整与使用体验并重，从“能够使用”走向“清晰、自然、高效地使用”。** 对同类 SaaS 产品的观察用于启发设计；随着技术、业务模式、用户审美和使用习惯的发展，企业软件也需要持续改善体验。

建议展示：按“数据完整联动 → 流程自动化 → 视觉与交互升级”的顺序，三行“原有问题 → 建设方向”逐行先出现问题、再出现对应的改变。旧系统及同类产品的具体对比，选取实际页面与同一任务说明，避免笼统评价。

## 3. 蓝鲸数字平台与产品能力

**回答：最终形成什么产品，平台如何承载，怎样形成复用价值？**

本项目基于 **蓝鲸数字平台**进行开发，将售后服务系统作为平台内的业务系统承载。本章专门展示平台与售后系统的包含关系，以及三项产品能力方向：

- **可配置：** 适配不同品牌的业务差异。

以 TOTO 业务验证共性能力，逐步形成可复用的售后服务产品。多客户适配与扩展按产品演进方向介绍；共性业务的具体功能留到后续章节展开。

## 4. 系统全景与角色分工

**回答：谁使用系统，每个人负责什么？**

项目按 **三个应用、四个后台业务视角、两类小程序使用者** 介绍。六类业务角色是讲解分组，不代表权限体系只有六个岗位；四个业务视角属于同一 Web 后台。

| 业务角色 | 使用入口 | 核心任务及交接 |
| --- | --- | --- |
| 总部运营 | Web 后台·总部运营视角 | 维护基础资料与服务规则，掌握整体运营情况，为各岗位提供业务支撑 |
| 客服 | Web 后台·客服作业视角 | 建单、沟通协调及异常处理；具备相应授权的人员负责分站和完工审核 |
| 服务站管理员 | Web 后台·服务站作业视角 | 接收本站工单、安排服务人员、管理本站服务资源 |
| 门店 | Web 后台·门店业务视角 | 维护购买登记，协助消费者发起服务，为后续服务提供产品与购买资料 |
| 服务人员 | 服务人员小程序 | 查看任务、确认预约、执行服务、提交完工材料 |
| 消费者 | 消费者小程序 | 管理产品、申请服务、查看进度、评价服务 |

系统管理员作为账号、权限和系统配置的支撑岗位补充说明。客服主管／专员、代理商管理员／门店店员等具体岗位及权限差异，按完整权限矩阵解释。

角色介绍先讲职责和交接，具体操作随主流程展开，完整菜单与操作步骤由角色手册承接。

## 5. 服务主线总览

**回答：一次服务从产品准备到办结，完整经过哪些环节？**

选取“消费者为已登记产品申请维修”作为贯穿案例，再简要说明安装、远程指导等服务类型。

**产品登记与绑定 → 消费者申请服务并建单 → 分配服务站 → 服务站安排师傅 → 确认预约 → 执行服务 → 提交完工 → 完工审核 → 工单办结。**

总览页先展示六个主要环节：**产品准备 → 申请建单 → 资源调度 → 预约履约 → 完工审核 → 工单办结**。再简短补充每个环节的主要动作，不在本页展开岗位交接与异常分支；跨角色协同由下一章独立演示。需要保持以下业务口径：

- 已有可用产品时直接选择产品申请，无需重复登记。
- 当前可信商品来源的消费者申请直接建单；客服人工受理不能表述为每张工单必经步骤。其他渠道和资格核验按对应业务契约说明。
- 服务站与服务人员采用两级分配；人工、智能及 AI 策略按适用场景展开。
- 服务人员提交完工后进入审核，通过后办结；抽样回访和消费者评价独立开展。
- 改期、缺件、补充完工资料、两级退回与重新分配等，用简短分支说明，避免打断正常主线。
- 线下收费是现有流程的条件扩展。需要介绍时，说明师傅登记费用、客户口头确认及线下收款的设计，以及默认全免费链路的兼容方式；按开发计划表达，不作为已实现能力演示。

建议展示：一张横向的完整业务主线图，先让六个环节整体可见，再按讲解需要补充主要动作；避免只展示“产品到建单”的局部入口。主线和异常细节以[售后全流程总览](../../05-业务流程/00-售后全流程总览.md)及对应 Spec 为依据。

过渡：**完整主线已经清楚，接下来通过同一张工单，看看各角色如何交接。**

## 7. 主流程中的关键能力

**回答：哪些能力让工单流转更顺畅？**

- 产品资料复用：自动关联、扫码绑定及已有资料复用，减少重复填写。
- 两级调度：明确服务站责任与人员执行责任，支持后续退回及重新分配。
- 智能与 AI 分配：先限定合格候选，算法依据距离、容量等指标计算；AI 结合配置策略和候选信息辅助选择。保留人工办理和异常处理入口。
- 完工材料与审核留痕：服务结果、审核意见、退回补充和版本记录可追踪；智能及 AI 审核按其适用范围、配置和验收情况介绍。

本部分侧重能力怎样工作，智能化与业务价值部分侧重带来的业务价值，不重复演示同一操作。

建议展示：关键节点局部图、策略选择及处理结果。算法参数、接口和技术细节可放入补充材料。

### 8.1 产品与渠道：防窜货

- 关联商品出库、门店购买、商品注册、预约与上门服务资料，展示产品流向。
- 对照销售区域、购买渠道与使用地区，通过异常筛选和关联记录辅助人工核验。
- 保留数据来源、时间及处置依据；异常线索不直接等于窜货结论。

“核验依据”卡片按当前程序展示四项简短说明：有无购买登记、入库门店与登记门店是否一致、安装地址是否在登记门店销售区域、是否在最下级出库经销商销售区域。它们是四项判断，不是四个顺序办理步骤；上方四块仍为资料关联示意。服务工单完工审核通过后异步判断，任一项异常标为疑似，缺少适用资料时保留未判断。依据：[当前判断契约](../../specs/2026-09-28-防窜货明细与消费者扫码无购买登记建单.md#校验项)。

### 8.2 服务权益：保修、延保与预留活动

- **现有功能**：商品保修政策、单件产品保修核实、延保申请与人工审核、保障范围和期限展示；消费者与工单按权限引用权益结果。
- **预留功能：延保活动（尚未开发）**。未来可围绕活动配置、参与条件、参与入口与权益衔接展开；这些是后续方向，活动规则另行确认。
- 现有办理可记录活动或合同依据，但不代表已有活动管理或自动发放能力。实际保障与真实政策依据一致，不将延保直接解释为全部维修免费。

## 9. 产品亮点之一：视觉与交互

**回答：系统怎样让不同角色更容易完成工作？**

- 视觉呈现：统一设计风格、清晰的信息层级和稳定的状态表达，兼顾品牌呈现与业务阅读。
- 后台操作：各角色工作台集中主要待办，常用操作就近办理，减少寻找入口和页面跳转。
- 服务人员端：通过卡片突出任务、地址、预约及下一步操作，方便现场处理。
- 消费者端：围绕“我的产品—申请服务—服务记录”组织体验；品牌产品中心作为进一步完善的方向说明。

与 TOTO 原系统、同类 SaaS 的对比，选取有来源的具体页面和同一任务，比较信息查找、操作次数、页面切换和反馈清晰度。不将“竞品视觉与交互普遍较差”作为未经核实的结论，也不把“工作台集中主要任务”扩大为全部功能均可在工作台完成。

建议展示：同一任务的页面与操作路径对照，以及后台工作台、服务人员卡片、消费者产品页。

## 10. 产品亮点之二：智能化与业务价值

**回答：智能化怎样改善调度、消费者咨询和上门服务准备？**

智能化亮点围绕三个场景展开：**智能分配服务资源、消费者智能售后助手、服务工单配件建议。** 以下按完整项目方案说明能力与价值。

### 10.1. 智能分配：辅助选择服务站与服务人员

- 在合格候选范围内，结合服务区域、距离、人员容量等条件进行智能计算，或通过 AI 结合配置策略辅助选择。
- 将服务站分配与站内人员分配衔接起来，减少人工逐项查询和协调，使服务需求更快进入执行环节。

### 10.2. 消费者智能售后助手：基于商品知识提供处理建议

- **知识来源：** 后台在“商品档案 → 常见问题与故障处理”维护各型号的常见问题、故障现象、检索关键词和处理方法，形成与具体商品关联的知识库，并控制哪些内容允许消费者查看。
- **AI 接入方案：** 通过服务端配置 AI API Key 接入模型，结合消费者选择的本人产品、描述的问题及适用的对客知识，辅助匹配知识并组织易懂的回答。
- **使用场景：** 消费者选择产品并描述问题，助手依据该产品的知识提供处理建议；问题仍未解决时，可带着问题摘要继续申请维修或联系人工客服。
- **业务价值：** 把品牌与售后人员维护的产品经验转化为消费者自助服务，减少常见问题的重复咨询，让后续人工处理获得更完整的问题线索。

### 10.3. 服务工单配件建议：提示上门需要准备哪些配件

- **知识来源：** 同样复用商品档案的“常见问题与故障处理”，由后台维护故障对应的处理方法、所需配件及建议数量，形成“商品—问题／故障—处理方法—配件”的关联知识。
- **工单内提示：** 服务人员从当前工单进入本单产品服务指南，结合工单商品及问题线索查找适用故障，带出处理方法和建议准备的配件，便于上门前了解需要带什么。
- **操作衔接：** 服务人员核对故障与处理条件，结合本人及本站可用库存确认配件和数量，统一带入工单“本次使用配件”，库存不足时单独申请缺少部分；现场处理与实际用料由人员确认。
- **业务价值：** 提前准备适用配件，减少到场后发现缺件、再次领料和二次上门的情况，提高服务准备的充分性与履约效率。

两端由同一商品知识维护入口支撑，按角色提供不同内容：消费者获得允许对客的处理建议，服务人员获得内部处理方法和关联配件。一份产品经验持续积累，同时服务自助咨询与专业履约；消费者问答使用 AI 接入方案，人员配件建议依据已维护的故障与配件关联带出。

### 10.4. 智能化带来的业务价值

| 传统处理方式 | 系统能力 | 预期价值 |
| --- | --- | --- |
| 人工查询并逐项选择服务资源 | 候选筛选、智能计算及 AI 分配 | 减少调度工作量，加快任务分配 |
| 常见产品问题反复依赖人工解答 | 基于商品知识库与 AI 接入方案的消费者智能助手 | 支持自助处理，减少重复咨询，保留后续服务的问题线索 |
| 服务人员临时查找故障经验，到场后才发现需要配件 | 工单关联商品故障知识，带出处理方法、配件及建议数量 | 提高上门准备充分性，减少缺件与二次上门 |
| 通过人工沟通反复询问进展 | 集中待办、状态记录和过程追踪 | 减少沟通与查找成本 |
| 重复填写产品和购买资料 | 自动关联与资料复用 | 降低消费者申请门槛 |
| 逐项核对完工材料 | 适用范围内的规则与 AI 辅助审核 | 减轻重复核对工作，支持质量管理 |

价值分别落到品牌的运营投入、服务组织的处理效率和消费者的响应体验。成本下降、响应提速先作为预期价值；有实际数据后，再用派单耗时、人工介入比例、首次响应时间及返工情况等指标支撑，不预填改善百分比。

建议展示：智能分站与派人结果、商品档案中的常见问题及配件维护、消费者问答、工单中的配件建议。用“后台维护一条商品知识 → 消费者获得处理建议 → 服务人员查看相关故障与配件”的示例，讲清知识维护如何同时支撑两端；取得实际数据后补充指标图表。方案依据见[消费者智能助手与商品知识](../../specs/2026-09-21-消费者AI助手商品与服务站知识问答.md)及[服务人员产品服务指南与配件建议](../../specs/2026-10-03-服务人员产品服务指南与配件建议.md)。
