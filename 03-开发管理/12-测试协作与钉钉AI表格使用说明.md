# 测试协作与钉钉 AI 表格使用说明

确认日期：2026-10-18。适用于 Web 管理后台、消费者小程序和“TOTO客服助手”服务人员小程序。协作方式已由用户确认；本文配套的字段、视图和首批用例是可调整的初始配置，不表示测试已经启动或通过。

## 1. 在哪里看，在哪里更新

| 内容 | 权威位置 | 维护责任 |
| --- | --- | --- |
| 需求、业务规则、权限、功能契约 | 本仓库需求、技术设计和对应 Spec | 产品／开发维护，测试人员查阅 |
| 已实现范围及剩余工作 | 三个应用开发进度明细 | 开发维护 |
| 实际部署及两端微信上传 | [部署台账](09-测试服务器部署.md) | 发布执行人维护 |
| 用例、每轮执行、测试进度、缺陷和复测 | 钉钉 AI 表格 | 测试人员主维护，开发补充缺陷处理和可复测版本 |
| 阶段测试结论、业务验收及必要证据 | 对应 Spec／问题、应用进度及项目总览 | 测试提供结论，开发／项目负责人按里程碑归档 |

测试人员在真实测试应用中执行操作，在钉钉记录结果；不要求拉业务源码、启动服务、编辑 Markdown 或提交 Git。需要 AI 帮助时，可只检出文档仓库。项目不增加测试管理菜单、业务接口、独立 HTML 或实时同步程序；Git 中不逐条镜像钉钉实时状态。

钉钉表格是测试执行事实源，不替代需求基线。测试发现规则不清时提出待确认事项，由产品／开发确认后更新原需求或 Spec，不能直接把期望写成新业务规则。

| --- | --- |

| 表格结构及首批用例 | [准备说明与导入文件](测试协作/2026-10-18-首批测试用例准备说明.md) |
| Web | [共享测试站独立售后入口](http://10.1.1.53:8011/after-sales/)；需内网／相应网络访问，启动前核对可登录及版本 |
| 消费者小程序／TOTO客服助手 | 微信 test 开发版本；由项目负责人按平台要求配置测试人员可访问的版本及成员权限，不把 UPLOADED 当作已设置体验版 |
| 文档 | [README](../README.md)、[业务流程](../05-业务流程/00-售后全流程总览.md)、[角色手册](../06-项目交付/02-角色手册/00-手册索引.md)，具体规则进入关联需求／Spec |
| 账号、数据及人员 | 均待分配／准备；账号由项目负责人发放，密码不写入表格或文档。专用账号至少覆盖允许／拒绝角色、两个数据范围、消费者和服务人员 |
| 轮次及版本 | 初始候选轮次为 `R1-20261018`，状态“待启动”；启动人填写实际范围、执行人、目标环境和实际版本后再测试 |

启动前逐条确认：目标功能已发布；角色允许／拒绝关系已明确；测试数据和关联单据就绪；前置用例已完成；测试人员能读取文档和目标应用。评审通过的用例在用例库改为“可执行”。完成准备后将“提测核对”改为“已核对”、“本轮范围”改为“计划”、“轮次状态”改为“进行中”。未满足的候选保留待核对，实际遭遇的阻塞记录原因及解除条件。

初始版本参照[2026-10-17 发布记录](09-测试服务器部署.md#release-20261017-permissions)，不是对当前线上版本的实时探测。两端均显示 0.1.1，不能只靠版本号判断制品，必须同时记上传日期及源码／发布标识。后续发布变更时登记实际测试版本，受影响范围安排复测；新建轮次时保留旧轮次。

## 3. 测试人员每天怎样操作

1. 打开“我的待测”，核对轮次、版本、岗位、数据和前置条件；按优先级及用例依赖执行，不强制按编号顺序。
2. 打开记录详情，按“操作步骤”操作实际 Web／小程序，逐项对照“预期结果”。角色切换使用独立会话；不能用管理员结果代替普通岗位结果。
3. 所有预期均满足后选择“通过”，填写实际版本、简短实际结果、执行人和时间；普通通过无需逐条截图。
4. 发现偏差选择“失败”，在缺陷表查重后登记同一 `BUG-*` 编号，填写复现步骤、预期／实际、环境和严重程度；执行记录填关联缺陷。不能把功能尚未部署或账号未发放记为产品缺陷。
5. 无法执行选择“阻塞”，填写具体原因、解除条件、协调责任人及时间；不把阻塞算通过或擅自移出已经确认的本轮范围。
6. 从“失败与待复测”继续验证。开发先更新同一缺陷的处理说明、修复版本及“待验证”；确认该版本在目标环境生效后，再建立下一次执行记录并复测。

一条用例有多个检查点时，全部通过才选通过。失败后可复测的独立检查点应拆成子用例，沿用原编号并追加稳定后缀；不靠一条笼统的“主流程通过”覆盖未执行分支。

### 状态与复测历史

用例库的状态为“待评审／可执行／暂缓／退役”；执行状态为“未执行／执行中／通过／失败／阻塞／待复测”。缺陷继续使用[协作规范](08-团队文档协作与提交同步规范.md#33-问题与优化状态)中的“待确认→已确认→待处理→处理中→待验证→已关闭”，验证失败回到处理中，另保留阻塞、暂缓、拒绝和重复。

每次执行具有唯一执行编号，业务键为“轮次＋用例编号＋尝试次数”。首次尝试为 1，复测递增；复测不能覆盖原失败的实际结果、版本和证据。复制原执行记录后：递增尝试次数、分配新执行编号、保留用例版本及步骤快照、清空实际结果／实际版本／证据／执行时间，填本次实际信息；新记录标记“是否最新＝是”，旧记录改为“否”。同轮同用例只能有一条最新记录；未能同步完成这两处更新时，先修正再查看汇总。

关闭缺陷前核对关联失败用例及必要回归。一个缺陷可关联多条执行记录；开发填写“已修复”不等于测试已验证。轮次结束后锁定或限制历史记录编辑，保留可追溯修订。

## 4. 表结构、视图与进度

采用一个 Base、三张表，字段及枚举的完整配置见[结构文件](测试协作/钉钉AI表格结构.json)：

| 表 | 主要内容 | 初始数据 |
| --- | --- | --- |
| 用例库 | 稳定编号、用例版本、主应用、入口、优先级、岗位、前置条件、步骤、预期结果、需求／Spec、解除条件 | 60 条，均待评审，其中 48 条首轮候选、12 条条件成熟后安排 |
| 测试执行 | 用例快照、轮次、范围、提测核对、执行人、结果、实际环境／版本、数据标识、缺陷、证据及尝试次数 | 48 条候选，均待启动、待核对、未执行；不是已确认的 48 条计划 |
| 缺陷 | 沿用 BUG 编号、应用／入口、复现及预期／实际、严重程度、负责人、处理、修复版本、复测结论 | 空表，不导入虚构示例缺陷 |

用例库修改后，不回写已执行记录中的快照；新执行使用已评审的新版本。用例新增和调整由测试人员负责，与需求冲突时先确认。导入文件只作初始模板和来源快照，日常更新在钉钉，不反复覆盖导入文件。

| 视图 | 配置 |
| --- | --- |
| 提测准备 | 测试执行表，本轮候选或提测核对≠已核对；启动人处理版本、数据、账号和责任分配 |
| 我的待测 | 当前轮次、范围＝计划、提测核对＝已核对、是否最新＝是、执行人＝当前用户，状态为未执行／执行中；按优先级排序 |
| 失败与待复测 | 当前轮次、范围＝计划、是否最新＝是，状态为失败／待复测；显示关联缺陷与修复版本 |
| 阻塞事项 | 当前轮次、范围＝计划、是否最新＝是、状态＝阻塞；按协调责任人分组 |
| 本轮进度 | 当前轮次、范围＝计划、是否最新＝是；按主应用／模块分组统计六种执行状态 |
| 历史执行 | 全部执行记录，按轮次、用例编号、尝试次数查看；不套“是否最新”筛选 |

每条用例只归一个主应用；跨端用例通过“协作应用”表达参与端，不另建第四个应用，不按入口数计算用例进度。

进度分母为启动时确认的本轮计划用例数，包括已纳入计划但阻塞的用例。候选不纳入分母；调整计划需记录原因和决定人，不能为提高比例删除失败或阻塞。当前通过比例＝最新结果为通过的计划用例数／计划用例数；计划为 0 时显示“待启动”，不显示 100%。六种最新执行状态之和应等于计划数，多次尝试不重复计数；可另看累计执行历史，但不混入本轮进度。

仪表盘只是同表视图；导入 XLSX／CSV 不会自动建立钉钉人员、单选、权限、视图、关联或仪表盘。配置完成并用两个测试账号实测后才视为建表可用。不能用状态历史功能代替独立的执行记录。

## 5. 缺陷、证据和权限

沿用现有 `BUG-YYYYMMDD-NN`，创建前查表格和[项目待办](07-后续开发与交互优化待办.md)，已有编号继续使用。初期由测试负责人集中分配当日序号，避免多人冲突。需求不明确时先在同一记录写“待确认”，关联原文；新增需求按现有 `CR-*` 规则处理。

缺陷表的字段满足协作规范要求。开发在表格处理日常缺陷；需要长期保留的修复原因、回归及验收结论归相应 Spec，保留同一 BUG 编号和表格记录链接，不另开一份实时缺陷台账。跨模块事项按原规范维护，权威位置和状态来源需明确。

测试人员可编辑用例及本人执行记录、提出缺陷；开发维护缺陷处理及修复版本；测试负责人管理轮次、范围、分配和复测结论，项目负责人确认最终业务验收。人员字段需在钉钉映射真实成员，不能把“待分配”映射成虚构账号。首次建表以组织内部成员访问为默认，按账号实际验证查看／编辑权限；行列权限若现有权益不支持，由测试负责人集中维护范围及历史记录。

不在表中放密码、Token、Cookie、私钥、真实顾客完整手机号／地址。使用专用合成测试数据，记录业务单号；测试结束保留必要复测数据，不擅自清库、修改真实角色、全局策略或他人单据。需要后台数据、并发工具或迁移时交开发准备，不要求测试人员直接执行 SQL。配置类用例在约定窗口、专用对象中执行并恢复配置，不打断其他测试。

普通通过记录简短结论即可；失败保留足够复现的脱敏截图／短摘录，文件放组织授权存储并链接。Git 长期留存遵循[证据留存规则](08-团队文档协作与提交同步规范.md#evidence-retention)，不把整张表、全量附件或原始日志反复导入仓库。

## 6. 怎样用 AI 问项目

测试人员有本仓库读取权限，并将当前文档仓库提供给 AI 后，可以直接提问。只给予权限不会自动让 AI 读到文档；先确认它能读取 README 和目标 Spec，并核对仓库更新时间。读取钉钉测试记录还需要独立的钉钉授权。

可以这样问：

> 这是 TOTO 售后服务文档仓库。先读 README、开发进度和部署记录，再读与 C07 相关的需求及 Spec。说明当前测试版本可测范围、前置数据、正常和异常用例，并标出来源及待确认项。不要把研发验证当成业务验收，也不要修改需求。

> 根据 W06 领料需求，帮我检查这条用例的步骤和预期是否遗漏库存、审批、撤销及跨范围限制。已有执行结果保持原样，不推断测试通过。

AI 辅助定位规则、整理用例和分析复现，实际执行与结果由测试人员核对。冲突时优先核实事实时点：已确认 Spec 决定目标行为，部署台账决定本轮版本边界，旧原型、旧验收表及研发报告不能覆盖新确认规则。

## 7. 里程碑如何回到项目文档

日常实时进度留在钉钉；项目总览和三个应用明细提供统一测试入口。首轮启动、阶段结束、重大阻塞、最终验收时，归档轮次、实际环境／发布版本、范围、统计时点、结果摘要、未关闭缺陷和证据链接。最终验收仍由约定责任人确认，测试通过、开发提交和应用发布分别记录；用例数不加入现有 97 个入口的分母。

本次仅建立协作说明和初始导入包，未创建线上表格、未执行测试、未修改业务验收计数，未配置定时同步、Git 提交／推送或应用发布。
