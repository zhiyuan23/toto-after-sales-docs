# 团队文档协作与提交同步规范

- 生效日期：2026-09-10
- 适用人员：产品、项目负责人、开发人员、测试人员和参与 TOTO 项目的 AI Agent
- 适用范围：`docs/toto` 及其关联的前端、后端和移动端仓库
- 目标：让需求、实现、问题、验证和验收结论可追踪，避免代码与文档分离或多人更新时互相覆盖

## 1. 权威来源

| 信息类型 | 权威来源 | 约束 |
| --- | --- | --- |
| 已确认业务范围与规则 | `01-功能需求/` 和已确认功能 Spec | 测试反馈、待办或源码不能自动改写业务规则 |
| 当前已实现行为 | 当前源码、配置和迁移 | 与旧文档冲突时先核实时间点，再更新过时记录 |
| 项目与入口进度 | `03-开发管理/00-开发进度与下一步.md` 及四份功能端明细 | 页面壳、构建通过或代码提交不等于业务完成 |
| 单个切片实现与验证 | `specs/` 下对应功能 Spec | 记录实现范围、验证证据、未验证边界和遗留项 |
| 横向优化与技术债 | `03-开发管理/09-后续开发与交互优化待办.md` | 不替代功能 Spec 或最终验收记录 |
| 缺陷与优化建议 | 对应功能 Spec 的问题区，或后续待办 | 未完成分诊前保持“待确认” |

同一事实只维护一个权威正文，其他页面只保留摘要和链接，不复制多份独立台账。

## 2. 事项字段与编号

新增问题、优化或技术债至少包含以下字段：

| 字段 | 要求 |
| --- | --- |
| 编号 | 稳定且不复用：`REQ-` 需求、`OPT-` 优化、`BUG-` 缺陷、`TECH-` 技术债、`DOC-` 文档问题；已有功能编号和 `UI-` 编号继续沿用 |
| 类型与模块 | 标明所属功能端、模块和页面／接口 |
| 标题与描述 | 描述可观察的现状，不把推测写成事实 |
| 来源 | 提出人或来源材料；AI 整理时保留原始提出者 |
| 日期 | 首次提出日期和最后更新时间，格式 `YYYY-MM-DD` |
| 优先级 | `P0` 阻塞／安全／数据风险，`P1` 近期必要，`P2` 一般优化，`P3` 储备 |
| 状态 | 使用本规范的统一状态，不自创近义状态 |
| 负责人 | 未分配写“待分配”，不通过猜测指定人员 |
| 验收标准 | 可观察、可复现；缺陷至少说明预期结果 |
| 证据与关联 | Spec、截图、日志、接口、代码提交、测试记录或关联编号 |

缺陷还必须记录环境、前置条件、复现步骤、实际结果和严重程度；涉及敏感信息时只记录脱敏证据，不写账号口令、密钥或完整个人信息。

## 3. 状态流转

统一使用以下状态：

```text
待确认 → 已确认 → 待开发 → 开发中 → 待测试 → 已完成
                       └──────→ 阻塞
待确认／已确认 ────────→ 暂缓／拒绝／重复
待测试 ───────────────→ 开发中（测试未通过）
```

- “已确认”表示范围、优先级和验收标准已经由有权角色确认。
- “待测试”表示开发实现及研发验证完成，但不代表测试或业务验收通过。
- “已完成”必须附真实环境或约定验收范围内的证据；只有构建、单元测试或代码提交时不得使用。
- “阻塞、暂缓、拒绝、重复”必须写原因；重复项需链接保留的主事项。
- 已关闭事项不删除，后续回归问题新建编号并关联原事项。

## 4. 角色责任

### 产品或项目负责人

- 确认业务范围、优先级、验收标准以及是否纳入版本。
- 决定建议是否升级为正式需求，处理跨模块规则冲突。
- 未核验研发和测试证据前，不提前标记最终完成。

### 开发人员

- 开始实现时把已确认事项更新为“开发中”。
- 完成后记录实现范围、代码位置、迁移、权限、兼容性、自测结果和未验证边界。
- 只在研发验证完成后更新为“待测试”，不得代替测试或业务人员完成最终验收。
- 修复缺陷时更新原事项并关联提交，不另建内容相同的记录。

### 测试人员

- 可以新增缺陷和体验优化，初始状态为“待确认”；已确认测试范围内的缺陷可以直接进入“已确认”。
- 提交缺陷时给出环境、复现步骤、实际结果、预期结果、严重程度和脱敏证据。
- 验证通过或不通过时更新同一事项；不直接修改业务需求正文来表达问题。

### AI Agent

- 可以依据当前任务整理、补全和同步文档，但不得把建议推断为已确认需求，也不得把研发验证改写为业务验收。
- 必须保留其他成员已有内容；存在冲突时新增“待确认”说明或报告冲突，不静默覆盖。
- 每次功能、缺陷或交互修改完成后主动执行文档影响检查，不等待用户提醒。

## 5. 功能修改后的文档同步

代码或配置发生用户可见行为、接口、数据结构、权限、流程、部署方式或验收状态变化时，按需更新：

1. 对应功能 Spec：实现范围、契约、验证证据和遗留项。
2. 对应功能端明细：入口状态和证据链接。
3. 开发进度总览：模块合计、当前阶段、下一步和更新记录。
4. 功能需求或技术设计：仅在已确认范围／方案变化时更新。
5. 后续待办：新增或关闭横向优化、技术债和缺契约事项。
6. 业务阅读摘要：只有面向业务人员的状态或流程发生变化时同步。

纯格式化、注释、无行为变化的内部重构或仅补充测试，通常可以声明“无文档影响”，但必须写明理由。不得制造无意义的更新时间或空白记录来通过检查。

## 6. Git 提交触发与授权

在当前代码／文档任务语境下，以下表达均触发完整 Git 提交流程：

- “提交代码”“提交修改”“提交功能”；
- “提交当前改动”“提交本次改动”“提交到 Git”；
- “commit”；
- 单独说“提交”，且上下文明确指向当前工作区改动。

表单提交、接口提交、审核提交、完工提交等业务术语不触发 Git 操作。`push`、发布、上传、数据库执行和共享历史改写仍需分别明确授权。

一次提交触发授权覆盖当前任务直接关联的代码仓库，以及因此需要同步的 TOTO 文档仓库。执行顺序为：

1. 检查各仓库分支、远端状态和未提交改动，识别团队并发内容。
2. 运行文档影响检查并完成必要更新。
3. 运行与风险相称的代码和文档验证。
4. 只暂存当前任务的关联文档，然后提交代码仓库。
5. 分别提交其他关联代码仓库，最后单独提交文档仓库。
6. 汇报各仓库提交哈希、验证结果、未提交内容和未推送状态。

任何一个仓库无法安全区分本任务与他人改动时，不得扩大暂存范围；报告冲突并继续处理不受影响的仓库。

## 7. 提交信息中的文档影响

代码提交正文末尾使用以下记录：

```text
Docs-Impact: updated
Docs-Refs: specs/2026-09-10-示例.md, 03-开发管理/04-统一管理后台开发进度.md
```

确无文档影响时使用：

```text
Docs-Impact: none
Docs-Reason: 仅内部重构，不改变接口、数据、权限和用户行为
```

文档仓库使用独立中文提交，例如：

```text
docs(toto): 同步派单功能实现与验证记录
```

`Docs-Impact: none` 不能用于规避缺失的 Spec、迁移说明、权限变化或验收证据。

## 8. 自动检查与团队接入

- 手动或 Agent 检查：`node scripts/check-doc-impact.mjs --working-tree --all`。
- 提交前检查：`node scripts/check-doc-impact.mjs --staged --all`。
- 安装本地共享 Hook：`bash scripts/install-git-hooks.sh`。脚本不会覆盖仓库已有 Hook。
- 合理的无文档影响提交可使用 `TOTO_DOCS_IMPACT_NONE_REASON='具体原因' git commit ...`；原因至少 8 个字符，并仍需在提交正文写入 `Docs-Impact: none`。
- CI 接入时应在同一工作区检出代码仓库和 `docs/toto`，执行相同的 `--staged` 检查。当前各仓库未发现统一 CI 定义，因此本规范只提供稳定检查入口，不虚构流水线配置。

自动检查只能发现“是否有文档证据”，不能判断业务结论是否正确；内容准确性仍由评审和验收负责。

## 9. 并发编辑与评审

- 修改前查看 `git status` 和目标段落，修改后查看局部 diff。
- 更新已有事项时按稳定编号修改原条目，不重复创建。
- 不整理、重排或顺带修正与当前任务无关的内容。
- 同一段落存在并发修改时，保留双方事实并显式标记待确认，不以最后写入者覆盖前一结论。
- 提交和评审按逻辑意图拆分；文档格式调整不得与业务结论变化混在同一个难以审阅的提交中。
