# 团队文档协作与提交同步规范

- 生效日期：2026-09-10
- 适用人员：产品、项目负责人、开发人员、测试人员和参与 TOTO 项目的 AI Agent
- 适用范围：`docs/toto` 及其关联的前端、后端和移动端仓库
- 目标：用同一套项目颗粒度维护需求、技术、实现、问题和验收，避免把应用、角色、菜单、需求和研发切片混成一层

## 1. 项目统一信息模型

### 1.1 应用载体

项目按实际运行产品统一为 **3 个应用载体**：

| 应用载体 | 代码或计划仓库 | 入口编号 | 当前入口组 |
| --- | --- | --- | ---: |
| Web 管理后台 | `gaia-ui/apps/after-sales` | `Axx`、`Dxx` | 63 |
| 消费者小程序 | `gaia-after-sales-uni` | `Cxx` | 17 |
| 服务人员小程序 | 计划仓库待最终确认 | `Wxx` | 16 |

`Axx` 与 `Dxx` 是历史需求来源形成的编号命名空间，不代表两个系统。原“统一管理后台”和“代理商工作台”均属于同一个 Web 管理后台；后者统一称为“门店业务视角”。“TOTO 客服助手”只有计划名称时不计入应用、入口或进度。

### 1.2 Web 后台角色视角

Web 管理后台使用同一登录、路由、接口、权限和租户体系，根据角色展示 4 个工作视角：

| 工作视角 | 主要角色 | 说明 |
| --- | --- | --- |
| 总部运营 | 系统管理员、TOTO 总部管理／运营人员 | 主数据、全局查询、运营与治理 |
| 客服作业 | 客服主管、客服专员 | 受理、工单、派单、异常、审核和回访 |
| 服务站作业 | 服务站管理员 | 本站工单、人员、排班、配件和质量 |
| 门店业务 | 代理商管理员、门店店员 | 门店上下文、顾客登记、查询和预约 |

工作视角只是导航和授权呈现维度，不是应用端、业务域或独立进度总量。同一菜单可以出现在多个视角，但只计一个菜单和一个入口组。

### 1.3 文档颗粒度

所有文档使用以下层级，不跨级混算：

```text
项目
└── 应用载体（Web 后台／消费者小程序／服务人员小程序）
    ├── 角色视角（仅 Web 后台）
    └── 业务域／模块
        └── 入口组（Axx／Dxx／Cxx／Wxx）
            ├── 需求点（ADM-*／DLR-*／CAPP-*／WAPP-* 等）
            ├── 研发切片（FS-*，由功能 Spec 承载）
            └── 问题或优化（BUG-*／OPT-*／TECH-*／DOC-*）
```

| 层级 | 回答的问题 | 不应承载 |
| --- | --- | --- |
| 项目 | 范围、应用、里程碑和总进度 | 页面字段和实现日志 |
| 应用载体 | 运行在哪里、面向谁 | 把角色视角算成新应用 |
| 角色视角 | 谁能看到和办理什么 | 独立功能数量和重复入口 |
| 业务域／模块 | 管理什么业务能力 | 具体代码文件流水账 |
| 入口组 | 用户从哪里进入一组功能 | 把列表、详情、弹窗重复计数 |
| 需求点 | 必须实现什么行为 | 当前实现状态 |
| 研发切片／Spec | 本次实现哪些契约、如何验证 | 新建一套平行需求基线 |
| 问题／优化 | 哪个偏差或改进需要处理 | 未确认业务规则 |

### 1.4 数字口径

| 指标 | 当前权威来源 | 用途 |
| --- | --- | --- |
| 需求编号数 | `01-功能需求/09-AI开发需求索引.md` | 追踪业务需求，不含 `FS-*` 研发任务 |
| 入口组数 | `01-功能需求/08-页面清单.md` | 统计可验收业务入口；当前为 96 |
| Web 菜单数 | `04-业务阅读/05-后台菜单与角色权限手册.md` | 统计去重后的可见菜单；当前规划为 49 |
| 已有真实实现 | `03-开发管理/00-开发进度与下一步.md` | 表示真实代码／接口及研发验证，不等于业务验收 |
| 最终验收完成 | 开发进度总览及对应验收证据 | 表示约定范围已在目标环境通过验收 |

不同指标不得相加或互相替代。数字只在权威来源计算，其他文档引用时写来源链接和核对日期，不独立维护副本。

## 2. 权威来源与文档职责

| 文档 | 唯一职责 | 更新条件 |
| --- | --- | --- |
| `README.md` | 项目导航、阅读顺序和权威来源索引 | 文档结构或入口变化 |
| `01-功能需求/00-功能纵览.md` | 项目范围、3 个应用载体、业务闭环和需求规模 | 已确认范围或规模变化 |
| `01-功能需求/02-角色权限与总体架构.md` | 组织、角色、权限模型和应用架构 | 角色或权限原则变化 |
| `01-功能需求/08-页面清单.md` | 96 个入口组及模块归属 | 新增、合并、拆分或取消入口 |
| `01-功能需求/09-AI开发需求索引.md` | 需求编号到原文、入口和 `FS-*` 的追踪 | 需求或研发切片映射变化 |
| `02-技术设计/` | 架构、数据、接口、权限和非功能约束 | 已确认技术契约变化 |
| `specs/` | 单个研发切片的范围、契约、实现和验收证据 | 切片确认、实施、验证或验收变化 |
| `03-开发管理/00-开发进度与下一步.md` | 项目级进度、里程碑、阻塞和下一步 | 入口状态、里程碑或阻塞变化 |
| 应用进度明细 | 逐入口状态和证据 | 对应入口状态变化 |
| `03-开发管理/09-后续开发与交互优化待办.md` | 跨模块优化、技术债和待补契约 | 新增、处理或关闭事项 |
| `04-业务阅读/` | 面向业务人员解释已确认业务 | 业务流程或稳定结论变化；不独立维护进度数字 |

Web 后台进度统一维护在 [`04-Web管理后台开发进度.md`](04-Web管理后台开发进度.md)：A、D 编号入口和四个工作视角均在同一文档展开。总览只统计一个 Web 管理后台，跨角色复用入口不得重复计数；角色菜单可见数、需求入口数和开发完成数必须分开表达。

项目仓库内文档、当前源码和配置构成本项目执行事实源。不得把外部知识库、个人电脑绝对路径或聊天记录写成团队成员才能访问的唯一依据；原始证据需要保留时，应在项目内登记可追踪的相对路径和核对结论。

## 3. 三套状态各管一层

### 3.1 入口和项目进度状态

仅用于开发进度总览及应用进度明细：

| 状态 | 使用条件 |
| --- | --- |
| 未开始 | 入口尚无有效实现 |
| 开发中 | 已开始实现，但未达到可验收条件 |
| 待验收 | 开发与研发验证完成，等待约定环境或业务验收 |
| 已完成 | 适用范围、权限、数据和关键场景均验收通过并有证据 |
| 阻塞 | 被明确外部条件阻断，必须记录原因和解除条件 |

“已有真实实现”和“最终验收完成”是统计维度，不是新增状态。

### 3.2 Spec 状态

仅用于单个研发切片：`草稿 → 待确认 → 已确认 → 开发中 → 待验收 → 已验收`，另可使用“暂缓”。Spec 的“已验收”不自动代表其关联的整个入口已完成，除非该入口全部适用范围均被覆盖。

### 3.3 问题与优化状态

仅用于缺陷、优化和技术债：

```text
待确认 → 已确认 → 待处理 → 处理中 → 待验证 → 已关闭
                       └────→ 阻塞
待确认／已确认 ─────────────→ 暂缓／拒绝／重复
待验证 ─────────────────────→ 处理中（验证未通过）
```

三套状态不得混用。例如测试人员提交的新缺陷写“待确认”，不能把功能入口状态改成“待确认”；研发自测通过后问题可进入“待验证”，但入口只能根据整体范围保持“开发中”或进入“待验收”。

## 4. 编号、字段与记录位置

### 4.1 编号

- 已有需求编号（`ADM-*`、`DLR-*`、`CAPP-*`、`WAPP-*` 等）、入口编号（`Axx`、`Dxx`、`Cxx`、`Wxx`）和研发任务编号（`FS-*`）继续沿用，不另建平行的 `REQ-*` 编号体系。
- 新的未确认需求先使用 `CR-YYYYMMDD-NN`；确认后并入已有需求编号或由需求负责人分配正式领域编号。
- 缺陷使用 `BUG-YYYYMMDD-NN`，体验优化使用 `OPT-YYYYMMDD-NN`，技术债使用 `TECH-YYYYMMDD-NN`，文档问题使用 `DOC-YYYYMMDD-NN`。
- 编号稳定、不复用；重复或关闭事项仍保留原编号。

### 4.2 必填字段

| 字段 | 要求 |
| --- | --- |
| 编号、类型和标题 | 唯一定位事项，标题描述可观察的问题或目标 |
| 应用载体 | Web 后台／消费者小程序／服务人员小程序 |
| 角色视角 | 仅 Web 后台填写；无关时写“跨视角”或“不适用” |
| 模块与入口 | 业务模块及 `Axx／Dxx／Cxx／Wxx`；未知时写“待定位” |
| 关联需求／Spec | 关联正式需求编号和唯一 Spec；没有时说明原因 |
| 来源与日期 | 提出人或材料、首次提出日期、最后更新时间 |
| 优先级与状态 | 使用本规范对应层级的枚举 |
| 负责人 | 未分配写“待分配”，不猜测人员 |
| 验收／验证标准 | 可观察、可复现，不以“代码已提交”代替 |
| 证据与结论 | 脱敏截图、日志、测试、提交或验收记录 |

缺陷还必须记录环境、前置条件、复现步骤、实际结果、预期结果和严重程度。简单文字或格式问题可以缩减字段，但至少保留编号、位置、期望、状态和提出人。

## 5. 角色责任

### 产品或项目负责人

- 确认业务范围、优先级、验收标准以及是否纳入里程碑。
- 决定建议是否升级为正式需求，处理跨模块规则冲突。
- 维护需求和入口范围，不在进度文档临时增加业务规则。

### 开发人员

- 开始实现时更新对应 Spec 和入口状态。
- 完成后记录代码、接口、数据迁移、权限、兼容性、自测结果和未验证边界。
- 研发验证完成后可把 Spec 更新为“待验收”、问题更新为“待验证”；不得代替测试或业务人员完成最终验收。

### 测试人员

- 在问题台账或对应 Spec 中新增缺陷和优化，不直接修改需求正文表达问题。
- 给出环境、复现步骤、实际结果、预期结果、严重程度和脱敏证据。
- 验证通过或不通过时更新同一编号，不另建重复问题。

### AI Agent

- 可以依据当前任务整理、补全和同步文档，但不得把建议推断为已确认需求，也不得把研发验证改写为业务验收。
- 必须保留其他成员已有内容；存在冲突时报告冲突或新增“待确认”说明，不静默覆盖。
- 每次功能、缺陷或交互修改完成后主动执行文档影响检查，不等待用户提醒。

## 6. 变更与文档同步矩阵

| 变更类型 | 必须检查 | 按条件更新 |
| --- | --- | --- |
| 新增或改变业务行为 | 对应需求、Spec、入口进度 | 页面清单、需求索引、业务阅读 |
| 接口、数据、状态机或权限变化 | Spec、技术设计、测试证据 | 风险、迁移与上线说明 |
| 仅完成既定实现 | Spec 实施记录、入口进度 | 项目总览和里程碑 |
| 测试发现缺陷 | 问题台账或对应 Spec | 入口进度；只有阻塞整体范围时更新 |
| 体验优化或技术债 | 后续待办 | 技术设计；形成通用约束时更新 |
| 纯重构、格式或补测试 | 文档影响声明 | 行为、契约和进度不变时无需修改正文 |

同步顺序：先更新事实最细、最权威的文档，再更新上层摘要；即 `需求／技术契约 → Spec／问题 → 入口进度 → 项目总览`。业务阅读页只引用稳定结论，不复制实时进度数字。

## 7. Git 提交触发与授权

在当前代码／文档任务语境下，以下表达均触发完整 Git 提交流程：

- “提交代码”“提交修改”“提交功能”；
- “提交当前改动”“提交本次改动”“提交到 Git”；
- “commit”；
- 单独说“提交”，且上下文明确指向当前工作区改动。

表单提交、接口提交、审核提交、完工提交等业务术语不触发 Git 操作。`push`、发布、上传、数据库执行和共享历史改写仍需分别明确授权。

一次提交触发授权覆盖当前任务直接关联的代码仓库，以及因此需要同步的 TOTO 文档仓库。执行顺序为：

1. 检查各仓库分支、远端状态和未提交改动，识别团队并发内容。
2. 运行文档影响检查并完成必要更新。
3. 运行与风险相称的代码和文档验证。
4. 只暂存当前任务的关联文档，然后提交代码仓库。
5. 分别提交其他关联代码仓库，最后单独提交文档仓库。
6. 汇报各仓库提交哈希、验证结果、未提交内容和未推送状态。

任何一个仓库无法安全区分本任务与他人改动时，不得扩大暂存范围；报告冲突并继续处理不受影响的仓库。

## 8. 提交信息中的文档影响

代码提交正文末尾使用以下记录：

```text
Docs-Impact: updated
Docs-Refs: specs/2026-09-10-示例.md, 03-开发管理/04-Web管理后台开发进度.md
```

确无文档影响时使用：

```text
Docs-Impact: none
Docs-Reason: 仅内部重构，不改变接口、数据、权限和用户行为
```

文档仓库使用独立中文提交，例如：

```text
docs(toto): 同步派单功能实现与验证记录
```

`Docs-Impact: none` 不能用于规避缺失的 Spec、迁移说明、权限变化或验收证据。

## 9. 自动检查与团队接入

- 手动或 Agent 检查：`node scripts/check-doc-impact.mjs --working-tree --all`。
- 提交前检查：`node scripts/check-doc-impact.mjs --staged --all`。
- 安装本地共享 Hook：`bash scripts/install-git-hooks.sh`。脚本不会覆盖仓库已有 Hook。
- 合理的无文档影响提交可使用 `TOTO_DOCS_IMPACT_NONE_REASON='具体原因' git commit ...`；原因至少 8 个字符，并仍需在提交正文写入 `Docs-Impact: none`。
- CI 接入时应在同一工作区检出代码仓库和 `docs/toto`，执行相同的 `--staged` 检查。当前各仓库未发现统一 CI 定义，因此本规范只提供稳定检查入口，不虚构流水线配置。

自动检查只能发现“是否有文档证据”，不能判断业务结论是否正确；内容准确性仍由评审和验收负责。

## 10. 并发编辑与评审

- 修改前查看 `git status` 和目标段落，修改后查看局部 diff。
- 更新已有事项时按稳定编号修改原条目，不重复创建。
- 不整理、重排或顺带修正与当前任务无关的内容。
- 同一段落存在并发修改时，保留双方事实并显式标记待确认，不以最后写入者覆盖前一结论。
- 提交和评审按逻辑意图拆分；文档格式调整不得与业务结论变化混在同一个难以审阅的提交中。
