## 后续说“部署”时的执行方式

在本项目任务语境中，用户说“部署”或“更新测试环境”且未指定环境／范围时，目标为上表测试服务器，**默认构建并发布完整的 TOTO Web 前后端，不按当次改动文件缩小发布范围**。Web／后端验证成功后，依次重新构建并上传消费者、服务人员两个小程序的 TOTO/test 微信开发版本。两次上传包含在更新授权中；提交审核、正式发布仍需单独明确要求。用户明确只更新 Web／后端时使用 `--web-only`。

| 范围 | 默认处理 |
| --- | --- |
| 售后后端 `backend/gaia-after-sales` | 构建当前售后后端工程；将测试机实际使用的 `core`／`api` 等依赖制品纳入宿主发布。独立 `gaia-after-sales-web` 是否运行，以目标机现状为准。 |
| Gaia 聚合宿主 `backend/gaia-saas-proj` | 构建测试机实际运行的 Web 宿主及其依赖；确认该机使用 WAR 还是可执行 JAR 后，发布完整宿主产物及所需售后依赖。其他未运行的 BI、Job、H5 宿主模块不因位于同一 Maven 仓库而部署。 |
| Web 前端 `frontend/gaia-ui` | 使用项目统一生产构建，生成主站与 `apps/after-sales` 售后子站组成的完整 `dist`，校验后整体发布，而非仅替换 `/after-sales/`。 |
| 两个小程序 `mobile/gaia-after-sales-uni`、`mobile/gaia-customer-service-uni` | 完整检查后，在 Web／后端发布验证成功时复用各自上传实现，重新构建并上传 TOTO/test 微信开发版本。 |

先检查涉及的代码仓库状态、部署脚本、实际依赖版本和目标机当前运行形态，确定 WAR／JAR、前端资源及实际目录；保留其他人的未提交改动和服务器现有配置。`gaia-ui/push.sh` 当前上传目标是 `192.168.100.180`，**不能直接运行其上传步骤**；可参考其构建流程，但发布目标必须核对为本页的测试服务器。凭据从本地忽略文件读取，终端命令、日志及反馈只展示脱敏信息。

部署时按对应功能 Spec 的顺序准备制品和必要备份，执行目标环境适用的发布与重启，再验证进程、HTTP 入口、相关 API 和本次功能的授权路径；失败时依据备份回退并说明结果。正常功能开发所需的测试库迁移、对应权限配置和可追踪测试数据遵循 [AGENTS.md](../AGENTS.md#测试环境部署) 的持续授权及预检、回读要求；清库、大范围破坏性或跨功能批量修改及生产环境操作仍须单独明确授权。仅持有测试服务器登录信息不代表已授权部署；发布证据写入当次功能 Spec，研发核验与业务验收分别记录。

已有测试环境发布记录可供核对目标形态：[售后 JAR 与子应用替换](../specs/2026-09-18-服务人员三类自动分配策略.md#6-共享测试环境发布与验证2026-09-18)、[WAR 与静态包发布](../specs/2026-09-19-实时工单看板与排班站点默认.md#测试记录)。它们是历史记录，执行时以当前服务器和源码为准。

## 正式部署脚本

入口为 [`scripts/deploy-test.mjs`](../scripts/deploy-test.mjs)，辅助文件在 [`scripts/deploy-test/`](../scripts/deploy-test)。支持当前 macOS／Linux 工作区布局，复用现有 Maven、JDK 21、主站／子站指定 Node 和 corepack/pnpm；另需 Python 3.9+、OpenSSH 和 Expect。服务器需要 Python 3.9+、Bash 和 `flock`，与已核对测试机一致；脚本不自动安装工具。

用户继续说“更新测试环境”即可。Codex 获得发布授权后直接调用部署模式，脚本会内置预检，不必先重复调用 `--check`。单独检查环境、开发脚本或查发布结果时使用对应只读模式：

```bash
# 只读预检：源码状态、工具链、服务器指纹、运行形态、测试库与备份空间。
node scripts/deploy-test.mjs --check

# 完整更新：Web／后端发布验证通过后，依次构建并上传两个小程序。
node scripts/deploy-test.mjs --deploy

# 用户明确只更新 Web／后端时，跳过两端检查和上传。
node scripts/deploy-test.mjs --deploy --web-only
```
