# TOTO售后服务 AI开发执行规范

版本：V1.0  
更新日期：2026-09-07  
文档状态：需求基线草案  

本文件规定 AI 任务上下文、任务模板、实现顺序、代码约束、评审和文档维护。

当前工作顺序为**先建立已知菜单入口，再按依赖开发业务**。[开发进度与下一步](00-开发进度与下一步.md)是唯一进度入口；[页面清单](../01-功能需求/08-页面清单.md)保留菜单定义，[AI 需求索引](../01-功能需求/09-AI开发需求索引.md)保留需求定位及任务依赖。本规范下面的业务实施步骤不适用于仅建设占位入口的任务。

[返回功能纵览](../01-功能需求/00-功能纵览.md)

## 24 AI 开发执行规范

### 24.1 AI 每次任务必须提供的上下文

AI 从项目文档与源码自行获取以下上下文，不要求用户重复提供可查明的信息；仅无法推断且影响结果的缺口需要询问：

1. 本文档版本和相关功能编号。
2. 当前仓库结构和适用的 `AGENTS.md`。
3. 相关领域模型、状态机和业务规则编号。
4. 已确认的页面或原型。
5. OpenAPI 契约、错误码和权限要求。
6. 本任务允许修改的目录和禁止修改的内容。
7. 验收场景和必须运行的测试。

### 24.2 单任务模板

```text
目标：实现 [功能编号和名称]
菜单入口：[Axx / Dxx / Cxx / Wxx]
任务类型：[菜单骨架 MNU-xx / 业务切片 FS-xxx]

业务依据：
- 需求：[本文件章节或功能编号]
- 规则：[BR 编号]
- 状态：[相关状态及允许迁移]

范围：
- 必须实现：
- 不在本任务：
- 允许修改目录：

接口和数据：
- OpenAPI 路径：
- 主要实体：
- 权限和数据范围：
- 幂等或并发要求：

验收：
- 场景：
- 自动化测试：
- 需要运行的 lint、typecheck、test 命令：

交付：
- 代码
- 数据库迁移
- 接口文档
- 测试
- 必要的变更说明
```

### 24.3 推荐开发顺序

菜单阶段按页面清单批量建立已知入口、路由、占位页、导航及必要权限验证，不生成未确认业务逻辑。之后每个业务切片按以下顺序完成：

1. 明确需求编号和验收场景。
2. 定义领域对象、枚举、状态和数据库约束。
3. 更新 OpenAPI 契约和共享类型。
4. 实现后端用例、权限、事务和审计。
5. 编写单元和集成测试。
6. 实现前端页面或小程序交互。
7. 补充端到端测试和错误场景。
8. 执行代码评审、测试和文档检查。

### 24.4 AI 代码约束

- 不自行发明未确认的业务规则。缺失规则登记明确待办；菜单可占位，不新增假业务 API 或用配置默认值绕过待确认规则。
- 不把状态修改实现为通用 CRUD。所有状态动作进入状态机。
- 不在前端复制关键业务判断，后端返回可执行动作和原因。
- 不绕过数据权限获取跨门店、跨服务站或跨用户数据。
- 不在日志、测试快照和错误信息中暴露真实敏感数据。
- 不为未来假设过度拆分微服务或增加无实际用途的抽象。
- 每个数据库迁移支持回滚或提供明确的数据恢复方案。
- 外部依赖通过适配器和契约测试隔离，测试环境使用可控模拟。
- 每次实现只覆盖一个可验收纵向切片，避免一次生成大量不可验证代码。

### 24.5 AI 评审清单

每次合并前让独立 AI Agent 或人工检查：

- 是否完整覆盖指定功能编号和验收场景。
- 是否违反工单状态机或产生非法状态跳转。
- 是否存在越权、IDOR、敏感数据泄露和批量导出风险。
- 是否正确处理幂等、并发、事务、重试和外部失败。
- 是否记录审计、状态历史和库存流水。
- 是否遗漏错误提示、空状态、弱网和重复提交。
- 自动化测试是否验证业务结果，而不只是代码行。
- 文档、OpenAPI 和数据库迁移是否同步。

## 25 项目文档清单

本需求基线确认后，项目中应持续维护：

| 文档 | 内容 | 责任人 |
| --- | --- | --- |
| 产品需求规格 | 本文档及变更记录 | 产品负责人 |
| 字段字典 | 页面、接口、数据库字段定义和敏感等级 | 产品和后端 |
| 权限矩阵 | 角色、功能、数据范围和字段权限 | 产品和安全 |
| 状态机 | 状态、动作、条件、原因和通知 | 产品和后端 |
| API 契约 | OpenAPI、错误码、幂等和回调 | 后端负责人 |
| 数据映射 | DWH、追溯、旧系统和新系统字段 | 数据负责人 |
| 架构决策记录 | 重要技术选择和替代方案 | 架构负责人 |
| 测试计划 | 测试范围、环境、数据和退出标准 | 测试负责人 |
| 迁移方案 | 迁移、对账、切换和回退 | 数据和项目负责人 |
| 运维手册 | 部署、监控、告警、备份和故障处理 | 运维负责人 |

## 26 需求变更规则

- 需求变更必须关联本文件功能编号或新增编号。
- 变更记录包含原因、影响端、数据影响、接口影响、排期影响和验收变化。
- 已进入开发的 P0 变更由产品、技术和测试共同评估。
- 影响状态机、码关系、库存、权限或隐私的变更必须单独评审。
- 未确认项转为已确认时，更新本文档版本并同步 OpenAPI、原型和测试。

## 27 首次启动建议

以下是原需求草案的启动建议，当前实际队列按唯一进度文档执行。其中客服规则、接口和迁移问题在依赖它们的业务切片前解决，不作为全部菜单占位建设的前置条件：

1. 现场补调研客服中心管理后台，收集真实工单和异常案例。
2. 召开状态机工作坊，确定每个动作、责任人、原因和通知。
3. 完成角色权限与数据范围矩阵。
4. 确认 DWH 和追溯接口，拿到样例数据和错误码。
5. 盘点旧系统数据量、重复率和迁移年限。
6. 产出购买登记、安装预约、维修、指导、派单、完工和评价原型。
7. 用本文 UAT-001 至 UAT-015 逐条走查原型。
8. 冻结 P0 范围后建立仓库、CI、环境和基础架构。

当前按“菜单入口、身份主档、跨端业务闭环”持续交付；原始 Epic 分组仅供历史参考。完成后更新唯一进度文档的模块、已完成内容、证据链接及下一步，不把入口完成等同于业务验收。

## 28 进度维护边界

- `03-开发管理/00-开发进度与下一步.md`：唯一维护当前模块状态、完成数量、计划和下一步。
- `01-功能需求/08-页面清单.md`：维护入口定义及模块对应；`09-AI开发需求索引.md`：维护需求追踪和依赖。两者不维护另一份进度。
- 对应 Spec：维护具体已实现入口、需求、验证结果、遗留及验收人；进度文档引用证据。不要求为每个简单动作新增 Spec，已有任务文档可以承接记录。
- 汇总菜单已建数时只计已验证入口；汇总功能完成数时只计已验收业务。按页面清单的模块对应关系去重统计，部分完成写明具体内容；新增范围同步调整分母。
