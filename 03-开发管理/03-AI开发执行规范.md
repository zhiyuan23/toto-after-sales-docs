# TOTO售后服务 AI开发执行规范

版本：V1.0  
更新日期：2026-09-08  
文档状态：需求基线草案  

本文件规定 AI 任务上下文、任务模板、实现顺序、代码约束、评审和文档维护。

当前工作顺序为**先建立已知菜单入口，再按依赖开发业务**。[开发进度总览](00-开发进度与下一步.md)是统一进度入口，并链接各功能端入口级明细；Web 端以 [`gaia-ui` 目录与菜单设计](../02-技术设计/03-gaia-ui目录与菜单设计.md)确定名称、路径和角色，小程序端以[小程序目录与页面路由设计](../02-技术设计/04-小程序目录与页面路由设计.md)确定 Tab、主包、业务分包和建议路由。[页面清单](../01-功能需求/08-页面清单.md)保留需求入口定义，[AI 需求索引](../01-功能需求/09-AI开发需求索引.md)保留需求定位及任务依赖。

## 24 AI 开发执行规范

### 24.1 AI 每次任务必须提供的上下文

AI 从项目文档与源码自行获取以下上下文，不要求用户重复提供可查明的信息；仅无法推断且影响结果的缺口需要询问：

1. 本文档版本和相关功能编号。
2. 当前仓库结构和适用的 `AGENTS.md`。
3. 相关领域模型、状态机和业务规则编号。
4. 已确认的页面或原型；Web 售后功能同时读取 [UI 样式规范](../02-技术设计/05-gaia-ui售后服务UI样式规范.md)和 [commonV2 组件说明](../../../frontend/gaia-ui/src/components/commonV2/README.md)，以新版组件作为默认实现基线。
5. OpenAPI 契约、错误码和权限要求。
6. 本任务允许修改的目录和禁止修改的内容。
7. 验收场景和必须运行的测试。

### 24.3 推荐开发顺序

菜单阶段按页面清单批量建立已知入口、路由、占位页、导航及必要权限验证，不生成未确认业务逻辑。之后每个业务切片按以下顺序完成：

1. 明确需求编号和验收场景。
2. 定义领域对象、枚举、状态和数据库约束。
3. 更新 OpenAPI 契约和共享类型。
4. 实现后端用例、权限、事务和审计。
5. 编写单元和集成测试。
6. 实现前端页面或小程序交互。
7. 补充端到端测试和错误场景。
8. 执行代码评审、测试和文档检查。

### 24.4 AI 代码约束

- `gaia-ui` 售后功能开发默认使用独立目录 `src/components/commonV2/`，遵循下方 Web UI 实现约束及 [UI 样式规范](../02-技术设计/05-gaia-ui售后服务UI样式规范.md)，不再沿用旧版嵌套筛选卡／表格卡方案。
- 不自行发明未确认的业务规则。缺失规则登记明确待办；菜单可占位，不新增假业务 API 或用配置默认值绕过待确认规则。
- 不把状态修改实现为通用 CRUD。所有状态动作进入状态机。
- 不在前端复制关键业务判断，后端返回可执行动作和原因。
- 不绕过数据权限获取跨门店、跨服务站或跨用户数据。
- 不在日志、测试快照和错误信息中暴露真实敏感数据。
- 不为未来假设过度拆分微服务或增加无实际用途的抽象。
- 每个数据库迁移支持回滚或提供明确的数据恢复方案。
- 外部依赖通过适配器和契约测试隔离，测试环境使用可控模拟。
- 每次实现只覆盖一个可验收纵向切片，避免一次生成大量不可验证代码。

#### Web UI 实现约束

以下约束适用于 `gaia-ui` 的售后管理端与代理商工作台；不要求将无关业务模块或小程序改为同一组件体系。

1. **整体白卡与组件入口。** 所有功能页，包括看板、流程、配置和隐藏／上下文页，使用 `CommonPageMain`。从 `/@/components/commonV2` 导入组件和类型，确保同时加载局部样式。标准列表在同一整体卡片内组织筛选、工具栏、表格和分页；`CommonCard` 只用于具有独立业务含义的子分区。
2. **筛选与虚线。** 使用 `CommonSearch` 的字段配置及默认横向标签、两项展开和按钮布局。虚线由组件内置，页面不重复添加分隔线或再套筛选卡。页面持有筛选草稿与已应用快照，筛选／重置回第 1 页，翻页使用已应用条件；一次操作只发一次查询。
3. **表格和分页。** 使用 `CommonListToolbar`、`CommonTable` 与其可选分页，列表状态默认复用 `useListPage`。调用方提供业务列、已授权动作和真实分页数据；查询、排序、上下文变化后清理选择。公共方法负责已应用条件快照、旧响应隔离、删除后的页码修正和加载失败状态，页面不得用额外 watch 重复查询。未接接口时不得伪造总数、可执行动作或业务完成状态。
4. **表单与操作。** 表单弹窗使用 `CommonFormDialog`，行操作复用 `CommonRowActions`，普通删除使用 `confirmDelete(name)` 确认对象。业务页负责初始化、校验、请求、提交中状态、失败保留及成功关闭；权限和状态迁移仍按后端契约执行。
5. **隔离与扩展。** 所有通用样式保持 `.common-v2` / `--cv2-*` 作用域；业务表单的下拉、日期等浮层显式设置 `popper-class="common-v2 common-v2-popper"`，确认框使用 `customClass: 'common-v2 cv2-confirm'`。禁止通过全局 `.el-*` 覆盖、修改全局主题或 `src/views/common` 达成页面效果。组件缺少实际需要的可复用能力时，在 `commonV2` 中最小扩展并同步说明；业务专有交互留在业务页，不另建一套 CRUD 外观。
6. **视觉依据与验证。** 具体尺寸与样式以项目 UI 规范及组件源码为准，来源是已核对的 Compass 商品页，无需每次开发重复访问外部底座。用户明确的新要求优先；常规适配可直接实施。修改组件时运行 `node --test scripts/common-v2.test.mjs`，按影响范围执行 lint、类型检查、构建及页面交互验证，检查桌面页面与浮层隔离；当前不做移动端/窄屏专项检查。

#### 公共方法与功能目录复用

后续售后功能涉及列表查询、分页、刷新、新增／编辑弹窗时，使用已在[商品档案范例](../../../frontend/gaia-ui/src/views/afterSales/catalog/product/README.md)验证的组合。公共逻辑位于 `src/hooks/commonV2/`，完整接口见[公共方法说明](../../../frontend/gaia-ui/src/hooks/commonV2/README.md)。

| 层级 | 默认职责与复用要求 |
| --- | --- |
| `components/commonV2` | 视觉组件、样式与浮层隔离 |
| `hooks/commonV2/useListPage` | 筛选草稿／快照、页码、列表、loading/error、刷新、过期响应隔离、删除后分页修正；不自动请求、不推断 API |
| `hooks/commonV2/useCrudDialog` | 新增／编辑模式、独立表单模型、dirty、互斥提交、失败保留及成功关闭；校验与请求由调用方传入 |
| 功能 `index.vue` | 页面装配、业务上下文、事件协调及操作后刷新 |
| 功能 `components/` | 专属表单和复杂业务交互；不复制通用视觉组件 |
| 功能 `model/` | `types.ts` 定义模型，`defaults.ts` 创建独立默认值，`mapper.ts` 处理筛选归一化、详情回填和提交字段白名单 |
| 功能 `schemas/` | 筛选、表格配置；确有状态或可复用表单配置时再增加相应文件 |
| `api/afterSales/` | 使用 Gaia 原有 request，按真实契约处理请求字段、业务错误码、响应形状和 AbortSignal；统一向列表方法返回 `{ list, total }` |

- 不改变现有菜单路径，不为简单功能机械拆分文件，也不建立空 API、空 schema 或第二套 CRUD 框架。相同公共能力应扩展已有 hooks，并补充真实行为测试。
- `CommonSearch` 的 search/reset 和 `CommonTable` 的 pageChange 分别连接公共方法；一次动作只查询一次。保存／删除成功后调用 refresh，不同时触发 watch 或重复加载。
- 表单通过默认值工厂及 mapper 建立副本，不能直接编辑列表行；校验和保存放入 `submit` 回调，返回 false 保留校验失败态，抛错保留表单。未保存确认由 beforeClose 与 dirty 配合实现。
- 租户／组织／门店上下文变化时先清理旧列表、选择、详情和表单，再在新权限确认后加载；请求序号隔离不能替代后端权限和数据隔离。审批、派单、完工、库存流转仍按业务状态机执行，只复用适用的列表和表单能力。
- 商品分类/商品档案正式页面已接入真实 API；原内存示例只保留在 examples 中供测试，无正式开启入口。后续功能复用真实 API 适配和字段白名单，不复制示例数据或合成测试身份。共享库/真实菜单角色未联调不能标为业务已完成。
- 修改上述公共方法时运行 `node --test scripts/common-v2-hooks.test.mjs scripts/common-v2.test.mjs`，再按影响完成定向 lint、类型检查、构建和关键页面回归。新增页面直接使用 CommonPageMain 时，保持售后入口覆盖检查有效，不再要求所有正式功能都经过占位 FeaturePage。

#### 后端开发默认规范

后续功能默认遵循 [售后后端开发规范](../02-技术设计/06-售后后端开发规范.md)，以[商品分类/商品档案全栈首版](../specs/2026-09-08-商品分类与商品档案全栈首版.md)为当前范例：

- API/AppService/model/service/mapper 各司其职；公共分页、版本和身份适配按需复用，不复制整个 CRUD 父类体系。
- APIResponse 外层、PageResponse 的 rows/records、字符串 ID、类型化 Command、版本冲突及错误语义保持一致；前端 API 层显式检查 code 并适配 list/total。
- 复用权威主档，售后扩展独立；共享列白名单写入，保留其他领域字段。实际 SQL 列类型、主键生成器表名和 Redis 高水位必须核对。
- 用例入口显式校验登录、权限和租户；缺授权拒绝。事务覆盖写入、扩展和审计，分类/商品引用与启停规则在后端校验。
- 对应功能交付 OpenAPI、显式迁移和恢复说明、权限配置清单、真实 SQL 与事务/权限/并发测试。迁移和实际菜单授权准备完成后，再按项目当前环境约束执行，不能用隔离数据冒充共享环境联调。
- 当前仅要求桌面管理后台验收，不做移动端/窄屏专项样式检查；保留既有响应式能力。

#### 小程序阶段性身份与权限策略

小程序功能开发默认遵循[开发阶段的固定测试身份](../02-技术设计/04-小程序目录与页面路由设计.md#71-开发阶段的固定测试身份)：

- H5 日常调试可将微信登录、手机号绑定、Token 刷新和完整动态角色配置后置，使用消费者端、服务人员端各一个白名单固定开发身份及其最小固定开发权限集推进主要功能。
- 只后置登录接入，不后置统一身份上下文、数据归属、后端授权和审计字段。不信任客户端 `userId/tenantId`，不把固定 ID 写入业务代码，不以前端隐藏代替服务端校验。
- 开发身份通道仅允许本地 H5/development profile，默认关闭且非本地构建失败关闭。具体账号、别名、开关和会话实现必须在首个相关 Spec 中根据当时源码确认，不自行发明接口。
- 固定身份只能作为开发自测证据。功能进入集成测试或演示准备前，必须接入真实登录和权限，补验未登录、失效会话、跨用户、跨角色和跨租户访问；未完成时不得标记业务验收完成。

### 24.5 AI 评审清单

每次合并前让独立 AI Agent 或人工检查：

- 是否完整覆盖指定功能编号和验收场景。
- 是否违反工单状态机或产生非法状态跳转。
- 是否存在越权、IDOR、敏感数据泄露和批量导出风险。
- 是否正确处理幂等、并发、事务、重试和外部失败。
- 是否记录审计、状态历史和库存流水。
- 是否遗漏错误提示、空状态、弱网和重复提交。
- Web 售后页面是否采用 `commonV2` 整体白卡、横向筛选和内置虚线，复用表格／分页／弹窗且没有嵌套重复列表卡片或全局样式泄漏。
- 筛选、重置、翻页是否各触发一次查询，提交状态和真实权限是否正确，新增通用能力是否同步组件说明并完成必要回归。
- 涉及列表／弹窗的功能是否复用公共 hooks，职责是否按 index/components/model/schemas 分开，是否误将商品档案内存示例或示例规则作为真实业务实现。
- 自动化测试是否验证业务结果，而不只是代码行。
- 文档、OpenAPI 和数据库迁移是否同步。

## 26 需求变更规则

- 需求变更必须关联本文件功能编号或新增编号。
- 变更记录包含原因、影响端、数据影响、接口影响、排期影响和验收变化。
- 已进入开发的 P0 变更由产品、技术和测试共同评估。
- 影响状态机、码关系、库存、权限或隐私的变更必须单独评审。
- 未确认项转为已确认时，更新本文档版本并同步 OpenAPI、原型和测试。

## 27 首次启动建议

以下是原需求草案的启动建议，当前实际队列按开发进度总览和功能端明细执行。其中客服规则、接口和迁移问题在依赖它们的业务切片前解决，不作为全部菜单占位建设的前置条件：

1. 现场补调研客服中心管理后台，收集真实工单和异常案例。
2. 召开状态机工作坊，确定每个动作、责任人、原因和通知。
3. 完成角色权限与数据范围矩阵。
4. 确认 DWH 和追溯接口，拿到样例数据和错误码。
5. 盘点旧系统数据量、重复率和迁移年限。
6. 产出购买登记、安装预约、维修、指导、派单、完工和评价原型。
7. 用本文 UAT-001 至 UAT-015 逐条走查原型。
8. 冻结 P0 范围后建立仓库、CI、环境和基础架构。

## 28 进度维护边界

- `03-开发管理/00-开发进度与下一步.md`：唯一维护当前模块状态、完成数量、计划和下一步。
- `01-功能需求/08-页面清单.md`：维护入口定义及模块对应；`09-AI开发需求索引.md`：维护需求追踪和依赖。两者不维护另一份进度。
- 对应 Spec：维护具体已实现入口、需求、验证结果、遗留及验收人；进度文档引用证据。不要求为每个简单动作新增 Spec，已有任务文档可以承接记录。
- 汇总菜单已建数时只计已验证入口；汇总功能完成数时只计已验收业务。按页面清单的模块对应关系去重统计，部分完成写明具体内容；新增范围同步调整分母。
