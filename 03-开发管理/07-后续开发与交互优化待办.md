### CR-20260916-01：消费者小程序 AI 智能客服／AI 售后助手

- 类型／优先级／状态：新增产品方向／P1／交互原型已确认，实施契约待细化。
- 应用／角色／模块与入口：消费者小程序／消费者／AI 智能售后／C18；首页作为主入口，与 C07 售后申请、C09 客服渠道及统一工单域衔接。
- 关联需求／Spec：已分配 CAPP-016，关联 CAPP-001、CAPP-006／007、CAPP-009、CAPP-011／012 及 FS-035／036；真实实施前仍需形成独立功能 Spec。
- 来源／日期／负责人：用户提出的《TOTO 售后服务｜AI 智能客服待办方案》；首次提出及最后更新 2026-09-16；产品、技术、运营及安全负责人待分配。
- 当前边界：首页 52px 悬浮入口、一轮回答、自助解决、安全分流、对话摘要、维修申请预填及摘要复制的页面原型已设计。现有 A23 服务知识库与 Web 统一工单可提供基础，但消费者安全查询、C07 提交和在线客服会话转接尚未实现，因此原型不直接建单、不显示已转人工。

#### 产品目标与定位

AI 智能客服作为消费者小程序的售后自助入口，优先回答常见、简单、重复性问题，对问题做初步识别和分流。目标不是取代人工客服，而是让简单问题尽量自助解决，把需要专业判断、正式服务或人工协调的问题无缝转入后续流程。预期价值包括降低重复咨询量、缩短响应时间、提供 7×24 小时基础服务、减少不必要工单，并提高真正需要建单时的信息完整度。

#### 候选使用场景

1. **产品使用咨询**：产品操作、功能开启、遥控器使用、清洁维护和日常注意事项。
2. **售后政策咨询**：保修期限、当前产品保修状态、安装或上门服务收费规则、服务流程和申请方式。
3. **常见故障排查**：针对遥控器无反应、无法启动、常见故障码或异常现象进行安全范围内的多轮引导；判断需要专业维修时立即停止自助指导并进入报修流程。
4. **售后进度查询**：在授权与业务接口具备后，回答本人工单状态、服务站分配、维修人员安排和上门时间等问题。

#### 候选业务流程

```text
消费者进入 AI 售后助手
  → 描述问题
  → AI 识别问题类型与风险等级
     → 简单问题：基于企业知识库回答 → 确认解决 → 结束
     → 可安全排查：给出一轮已发布指引 → 解决后结束，或生成摘要 → 带入 C07 维修申请复核
     → 超出能力／消费者要求人工：生成可复制摘要 → 打开 C09 已配置客服渠道
```

人工客服入口必须保留。当前没有在线会话转接接口，首版采用“复制摘要 + 已配置电话／微信客服渠道”；只有后续形成真实会话标识、队列和消息传递契约后，才可显示“已转人工”。摘要至少包含产品信息、问题描述、已进行的排查、当前判断和消费者诉求。

#### 与 AI 智能建单的衔接

当对话已确认需要维修时，首版只把产品及型号、故障现象、已执行的检查和知识编号写入 C07 问题描述；联系人、服务地址和期望时间仍在现有步骤中由消费者核对。不得因 AI 判断自动创建正式工单。长期目标链路为：

**AI 智能客服 → 问题排查 → 确认需服务 → AI 智能建单 → 智能分站／推荐师傅 → 维修履约 → AI 智能完工审核 → 回访／评价／关单。**

#### 知识与业务数据

- 优先使用企业自有售后知识库，候选来源包括产品说明书、使用指南、FAQ、故障代码、常见故障方案、安装说明、清洁维护说明、质保与服务政策、收费标准和售后流程；不以大模型自身知识代替企业规则。
- 在本人授权、数据范围和接口契约完成后，可按需读取消费者资料、已绑定产品、型号、购买／安装时间、质保状态、本人工单与进度、服务站和维修人员的对外可见信息；不得绕过本人范围、租户隔离或现有业务权限。

#### 安全分级与人工兜底

| 等级 | 场景 | 处理原则 |
| --- | --- | --- |
| L1 | 简单咨询 | 在可追溯的企业知识范围内直接回答 |
| L2 | 常见故障 | 只引导无需拆机、不涉及水路／电路等风险的简单检查 |
| L3 | 专业维修问题 | 停止继续操作指导，建议进入售后工单流程 |
| L4 | AI 无法判断或超出能力 | 明确说明限制，生成摘要并进入已配置人工客服渠道 |

涉及专业维修、水路、电路、拆机或其他人身／财产风险的操作不允许由 AI 引导消费者执行。人工接管、紧急提示和建单兜底不得依赖模型能够正确自判断。

<a id="document-review-20260910-1-复盘结论"></a>
## 1. 复盘结论

当前文档已经覆盖业务需求、技术设计、菜单权限、开发进度、Spec 和验收证据，内容完整度较高。主要问题不是“没有文档”，而是早期按原系统来源拆分后，逐步演变出了多套交叉维度：

- 把一个 Web 管理后台按“统一管理后台／代理商工作台”写成两个功能端；
- 把应用、角色视角、菜单入口、需求点和研发切片放在同一层统计；
- 同一进度数字在总览、明细和业务阅读摘要中重复维护；
- 119 个需求编号、96 个入口组、49 个菜单、研发切片数和最终验收数并列出现，但缺少统一指标字典；
- 独立文档保留了合并版的章节编号、元数据和绝对路径，不利于团队阅读和迁移。

目标模型统一为：**3 个应用载体、Web 后台 4 个角色视角、业务模块、入口组、需求点、研发切片和问题事项七层结构**。具体定义见[团队文档协作与提交同步规范](08-团队文档协作与提交同步规范.md)。

本次扫描共覆盖需求、设计、开发管理、业务阅读和 Spec 目录中的 62 份 Markdown；其中 19 份包含本机绝对路径，15 份保留 `llm-wiki` 元数据，`02-技术设计` 下存在重复的 `05`、`06` 文件前缀。这些内容不一定错误，但需要按本清单逐步转为团队可移植的项目内引用。

## 5. 迁移顺序

1. **统一术语和规范**：明确 3 个应用载体、4 个 Web 角色视角和七层颗粒度；本次已完成。
2. **统一总入口**：修正 README、功能纵览、角色架构、页面清单和业务功能结构中的“4 个功能端”表述。
3. **统一 Web 进度**：总览只保留一个 Web 管理后台汇总；A、D 入口明细合并到一份 Web 进度文档，顶部以模块总览和角色访问视图提供导航。
4. **重算并校验数字**：统一需求编号、入口组、菜单、已有实现和最终验收五类指标；脚本化检查合计。
5. **清理重复进度**：业务阅读页取消独立实时计数，只引用总览。
6. **补齐索引和台账**：增加 Spec 索引，扩展问题与优化台账，补当前里程碑卡片。
7. **最后处理命名和编号**：在链接校验可自动化后重命名文件、章节和重复前缀，避免先改名造成大面积断链。
