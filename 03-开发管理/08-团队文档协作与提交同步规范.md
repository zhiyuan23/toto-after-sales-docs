# 团队文档协作与提交同步规范

- 生效日期：2026-09-10
- 适用人员：产品、项目负责人、开发人员、测试人员和参与 TOTO 项目的 AI Agent
- 适用范围：`docs/toto` 及其关联的前端、后端和移动端仓库
- 目标：用同一套项目颗粒度维护需求、技术、实现、问题和验收，避免把应用、角色、菜单、需求和研发切片混成一层

## 1. 项目统一信息模型

### 1.1 应用载体

项目按实际运行产品统一为 **3 个应用载体**：

| 应用载体 | 代码或计划仓库 | 入口编号 | 当前入口组 |
| --- | --- | --- | ---: |
| Web 管理后台 | `gaia-ui/apps/after-sales` | `Axx`、`Dxx` | 63 |
| 消费者小程序 | `gaia-after-sales-uni` | `Cxx` | 18 |
| 服务人员小程序 | `gaia-customer-service-uni` | `Wxx` | 16 |

`Axx` 与 `Dxx` 是历史需求来源形成的编号命名空间，不代表两个系统。原“统一管理后台”和“代理商工作台”均属于同一个 Web 管理后台；后者统一称为“门店业务视角”。“TOTO 客服助手”是服务人员小程序名称，不另计应用、入口或进度。

### 1.2 Web 后台角色视角

Web 管理后台使用同一登录、路由、接口、权限和租户体系，根据角色展示 4 个工作视角：

| 工作视角 | 主要角色 | 说明 |
| --- | --- | --- |
| 总部运营 | 系统管理员、TOTO 总部管理／运营人员 | 主数据、全局查询、运营与治理 |
| 客服作业 | 客服主管、客服专员 | 受理、工单、派单、异常、审核和回访 |
| 服务站作业 | 服务站管理员 | 本站工单、人员、排班、配件和质量 |
| 门店业务 | 代理商管理员、门店店员 | 门店上下文、顾客登记、查询和预约 |

工作视角只是导航和授权呈现维度，不是应用端、业务域或独立进度总量。同一菜单可以出现在多个视角，但只计一个菜单和一个入口组。

### 1.3 文档颗粒度

所有文档使用以下层级，不跨级混算：

```text
项目
└── 应用载体（Web 后台／消费者小程序／服务人员小程序）
    ├── 角色视角（仅 Web 后台）
    └── 业务域／模块
        └── 入口组（Axx／Dxx／Cxx／Wxx）
            ├── 需求点（ADM-*／DLR-*／CAPP-*／WAPP-* 等）
            ├── 研发切片（FS-*，由功能 Spec 承载）
            └── 问题或优化（BUG-*／OPT-*／TECH-*／DOC-*）
```

| 层级 | 回答的问题 | 不应承载 |
| --- | --- | --- |
| 项目 | 范围、应用、里程碑和总进度 | 页面字段和实现日志 |
| 应用载体 | 运行在哪里、面向谁 | 把角色视角算成新应用 |
| 角色视角 | 谁能看到和办理什么 | 独立功能数量和重复入口 |
| 业务域／模块 | 管理什么业务能力 | 具体代码文件流水账 |
| 入口组 | 用户从哪里进入一组功能 | 把列表、详情、弹窗重复计数 |
| 需求点 | 必须实现什么行为 | 当前实现状态 |
| 研发切片／Spec | 本次实现哪些契约、如何验证 | 新建一套平行需求基线 |
| 问题／优化 | 哪个偏差或改进需要处理 | 未确认业务规则 |

### 1.4 数字口径

| 指标 | 当前权威来源 | 用途 |
| --- | --- | --- |
| 需求编号数 | `01-功能需求/09-AI开发需求索引.md` | 追踪业务需求，不含 `FS-*` 研发任务 |
| 入口组数 | `01-功能需求/08-页面清单.md` | 维护有效入口及历史编号；删除／合并按已确认范围处理，不在规范内复制数量 |
| Web 菜单数 | `02-技术设计/09-后台菜单与岗位权限矩阵.md` | 维护注册、侧栏与上下文菜单范围；不在规范内复制数量 |
| 已有真实实现 | 三个应用进度明细的逐入口记录；总览汇总 | 表示真实代码／接口及研发验证，不等于业务验收 |
| 最终验收完成 | 应用进度明细及对应验收证据；总览汇总 | 表示约定范围已在目标环境通过验收 |

不同指标不得相加或互相替代。数字只在权威来源计算，其他文档引用时写来源链接和核对日期，不独立维护副本。

| `99-归档/` 中的文档整理与迁移记录 | 历史迁移及清单快照，不承担日常导航 | 仅补充对应整理事实；不要求随日常文档变更维护历史清单 |

Web 后台进度统一维护在 [`04-Web管理后台开发进度.md`](04-Web管理后台开发进度.md)：A、D 编号入口和四个工作视角均在同一文档展开。总览只统计一个 Web 管理后台，跨角色复用入口不得重复计数；角色菜单可见数、需求入口数和开发完成数必须分开表达。

文档新增、移动、改名、合并或删除时，先检索并直接修正所有现存引用方的文件路径与章节锚点，再检查链接有效性。README 和任务相关文档应直达需求、规范、功能契约或证据；已知位置直接读取，未知位置按目录与编号检索，不要求通过全量清单或迁移对照查找。历史原文可保留旧路径文字用于追溯，但可点击链接应指向实际承接位置。

日常进度仅保留一份总览和 Web、消费者、服务人员三份应用明细。总览不复制全部模块表、研发切片表和逐次更新日志；开发顺序不另建实时进度摘要，特定批次的剩余任务不作为长期台账。实现／验证过程写对应 Spec，旧记录归档；功能状态变化时先维护应用明细，再更新总览。当前菜单注册数只在技术设计维护，不能重复加入进度分母。

项目仓库内文档、当前源码和配置构成本项目执行事实源。不得把外部知识库、个人电脑绝对路径或聊天记录写成团队成员才能访问的唯一依据；原始证据需要保留时，应在项目内登记可追踪的相对路径和核对结论。

## 3. 三套状态各管一层

### 3.1 入口和项目进度状态

仅用于开发进度总览及应用进度明细：

| 状态 | 使用条件 |
| --- | --- |
| 未开始 | 入口尚无有效实现 |
| 开发中 | 已开始实现，但未达到可验收条件 |
| 待验收 | 开发与研发验证完成，等待约定环境或业务验收 |
| 已完成 | 适用范围、权限、数据和关键场景均验收通过并有证据 |
| 阻塞 | 被明确外部条件阻断，必须记录原因和解除条件 |

“已有真实实现”和“最终验收完成”是统计维度，不是新增状态。真实实现必须已接入真实业务数据或 API，并有对应研发验证；只读／基础切片可计入，但需明确剩余边界。最终验收要求入口全部适用范围的数据、接口、页面、权限及关键场景在约定真实环境通过。工程底座单列，不加入业务入口计数。

日常汇总只展示有效入口、已有真实实现和最终验收。历史“入口进度／菜单状态”包含页面架构和真实角色验证的不同口径，保留原证据供追溯，不再作为并列进度数字；页面壳、静态路由、占位菜单、文档原型和仅构建通过均不计真实实现。真实允许／拒绝角色未验证时，在剩余工作或共同验收边界中明确记录。

### 3.2 Spec 状态

仅用于单个研发切片：`草稿 → 待确认 → 已确认 → 开发中 → 待验收 → 已验收`，另可使用“暂缓”。Spec 的“已验收”不自动代表其关联的整个入口已完成，除非该入口全部适用范围均被覆盖。

### 3.3 问题与优化状态

仅用于缺陷、优化和技术债：

```text
待确认 → 已确认 → 待处理 → 处理中 → 待验证 → 已关闭
                       └────→ 阻塞
待确认／已确认 ─────────────→ 暂缓／拒绝／重复
待验证 ─────────────────────→ 处理中（验证未通过）
```

三套状态不得混用。例如测试人员提交的新缺陷写“待确认”，不能把功能入口状态改成“待确认”；研发自测通过后问题可进入“待验证”，但入口只能根据整体范围保持“开发中”或进入“待验收”。

## 4. 编号、字段与记录位置

### 4.1 编号

- 已有需求编号（`ADM-*`、`DLR-*`、`CAPP-*`、`WAPP-*` 等）、入口编号（`Axx`、`Dxx`、`Cxx`、`Wxx`）和研发任务编号（`FS-*`）继续沿用，不另建平行的 `REQ-*` 编号体系。
- 新的未确认需求先使用 `CR-YYYYMMDD-NN`；确认后并入已有需求编号或由需求负责人分配正式领域编号。
- 缺陷使用 `BUG-YYYYMMDD-NN`，体验优化使用 `OPT-YYYYMMDD-NN`，技术债使用 `TECH-YYYYMMDD-NN`，文档问题使用 `DOC-YYYYMMDD-NN`。
- 编号稳定、不复用；重复或关闭事项仍保留原编号。

### 4.2 必填字段

| 字段 | 要求 |
| --- | --- |
| 编号、类型和标题 | 唯一定位事项，标题描述可观察的问题或目标 |
| 应用载体 | Web 后台／消费者小程序／服务人员小程序 |
| 角色视角 | 仅 Web 后台填写；无关时写“跨视角”或“不适用” |
| 模块与入口 | 业务模块及 `Axx／Dxx／Cxx／Wxx`；未知时写“待定位” |
| 关联需求／Spec | 关联正式需求编号和唯一 Spec；没有时说明原因 |
| 来源与日期 | 提出人或材料、首次提出日期、最后更新时间 |
| 优先级与状态 | 使用本规范对应层级的枚举 |
| 负责人 | 未分配写“待分配”，不猜测人员 |
| 验收／验证标准 | 可观察、可复现，不以“代码已提交”代替 |
| 证据与结论 | 脱敏截图、日志、测试、提交或验收记录 |

缺陷还必须记录环境、前置条件、复现步骤、实际结果、预期结果和严重程度。简单文字或格式问题可以缩减字段，但至少保留编号、位置、期望、状态和提出人。

## 5. 角色责任

### 产品或项目负责人

- 确认业务范围、优先级、验收标准以及是否纳入里程碑。
- 决定建议是否升级为正式需求，处理跨模块规则冲突。
- 维护需求和入口范围，不在进度文档临时增加业务规则。

### 开发人员

- 开始实现时更新对应 Spec 和入口状态。
- 完成后记录代码、接口、数据迁移、权限、兼容性、自测结果和未验证边界。
- 研发验证完成后可把 Spec 更新为“待验收”、问题更新为“待验证”；不得代替测试或业务人员完成最终验收。

### 测试人员

- 在问题台账或对应 Spec 中新增缺陷和优化，不直接修改需求正文表达问题。
- 给出环境、复现步骤、实际结果、预期结果、严重程度和脱敏证据。
- 验证通过或不通过时更新同一编号，不另建重复问题。

### AI Agent

- 可以依据当前任务整理、补全和同步文档，但不得把建议推断为已确认需求，也不得把研发验证改写为业务验收。
- 必须保留其他成员已有内容；存在冲突时报告冲突或新增“待确认”说明，不静默覆盖。
- 每次功能、缺陷或交互修改完成后主动执行文档影响检查，不等待用户提醒。

## 6. 变更与文档同步矩阵

| 变更类型 | 必须检查 | 按条件更新 |
| --- | --- | --- |
| 新增或改变业务行为 | 对应需求、Spec、入口进度 | 页面清单、需求索引、业务流程与指南 |
| 接口、数据、状态机或权限变化 | Spec、技术设计、测试证据 | 风险、迁移与上线说明 |
| 仅完成既定实现 | Spec 实施记录、入口进度 | 项目总览和里程碑 |
| 测试发现缺陷 | 问题台账或对应 Spec | 入口进度；只有阻塞整体范围时更新 |
| 体验优化或技术债 | 后续待办 | 技术设计；形成通用约束时更新 |
| 纯重构、格式或补测试 | 文档影响声明 | 行为、契约和进度不变时无需修改正文 |

同步顺序：先更新事实最细、最权威的文档，再更新上层摘要；即 `需求／技术契约 → Spec／问题 → 入口进度 → 项目总览`。业务指南只引用稳定结论，不复制实时进度数字；流程目录维护步骤与交接，讨论稿保留待确认标记。

### 6.1 证据留存与提交规则（2026-09-27）

本规则适用于 TOTO 文档及关联代码仓库，供研发、测试和 AI Agent 在生成材料和提交时共同执行。**验证按风险充分进行，Git 只保留能支持长期维护、复现或验收的最小证据。** 截图数量不代表验证覆盖率；没有提交截图也不等于没有做视觉检查。用户明确指定某份材料需要留存时按其要求处理。

#### 哪些应提交，哪些默认留在本地

| 材料／场景 | 默认处理 | 保留条件与说明 |
| --- | --- | --- |
| 源码、测试、迁移脚本、确认的契约及必要规范 | 提交 | 与当前功能直接相关，按已有职责归档 |
| 验证结论 | 简短文字提交 | 优先补到已有 Spec／问题条目；记录范围、环境／平台、命令或复现步骤、结果及待验边界，无须每次新增文件 |
| 文案、间距、颜色、图标、圆角等局部微调 | 默认不提交截图 | 只有文字和测试难以说明的视觉缺陷、验收争议或不可稳定复现状态才保留代表图 |
| 新页面、关键流程或重要布局调整 | 通常 1～2 张最终关键状态图 | 每张对应不同验收点；同组件跨页复用取代表页，不逐页截图入库 |
| 修改前后对照、深浅色、不同尺寸／平台 | 按确有差异保留 | 对照图仅在前后差异本身需要长期说明时保留；不能为凑全组合而提交。项目未要求的端或尺寸不额外扩张验收 |
| 失败复现、权限允许／拒绝、异常恢复 | 按需要保留最小证据 | 优先可重复执行的测试；图片只能证明显示状态，不能代替服务端权限或业务正确性验证 |
| 原始测试／构建／运行日志、控制台全文 | 本地忽略 | 文档记录命令、结果、失败项和关键错误短摘录，不复制完整输出，不把日志改成 `.txt`／`.md` 绕过规则 |
| 设计生成稿、未选方案、阶段预览、重复截图、临时对比拼图 | 本地忽略 | 最终被确认且确为实施唯一基线的设计文件可作为正式原型保存；尝试过或被文档链接过不构成留存理由 |
| HAR／浏览器 trace、录屏、测试报告站点、压缩包、临时下载／导出、数据库备份 | 本地忽略 | 必要结论、可复现步骤及迁移／回退脚本入库；确需保存无法替代的故障证据时采用下述例外 |
| 产品实际使用的图片、图标、字体、文档原型资源 | 按源码／正式文档资源提交 | 不属于验证截图，禁止用全局 `*.png`／`*.jpg` 忽略规则误伤 |
| 自动化测试真实依赖的快照基准图、最小脱敏 fixture | 按测试源码提交 | 必须能指明消费它的测试；测试运行产生的 actual／diff／report 仍默认本地忽略 |
| 部署、迁移、验收的关键结果 | 提交精简记录 | 保留制品／提交标识、执行范围、回读结果和回退位置；不提交整份部署日志、凭据、数据库备份或业务数据转储 |

#### 截图和摘要怎样保存

- 同一功能通常不超过 2 张截图；确需更多时直接在已有证据说明中逐张写明不同的验收点和不可替代性，不另外建立截图审批表。单张宜不超过 500 KiB，优先截图时限制区域、使用工具支持的压缩或合适格式；这些是复核尺度，不以损失可读性为代价硬性裁切。
- 仅保存足以解释问题的区域，保留必要状态上下文；检查姓名、手机、地址、账号、令牌、Cookie 和内部敏感信息。无法安全脱敏的原始材料不能以普通例外入库。
- 人工验证截图集中放在文档仓库 `specs/evidence/<日期-功能>/`，由同一功能 Spec 或说明使用相对链接引用；不要在代码仓库、总览和多份证据目录重复复制。代码仓库中的运行资源、正式原型资源和测试基准继续按原有目录保存。
- 临时材料生成时就写到本项目已忽略的 `.local/verification-artifacts/<日期-功能>/` 或系统临时目录；不要先堆进 `specs/evidence/` 再默认 `git add`。现有 `.local/` 忽略规则已覆盖，不需逐图追加忽略项。
- 摘要保留实际检查结果、必要失败名称、与基线的比较及未验证范围。多个阶段反复运行同一检查时，通常只保留最终结论及有意义的变化，不复制每轮输出。
- 文档链接不是保留资格。移出过程材料时同步删除或改写链接，把必要结论保留在团队可读的文字中；不得留下断链，也不得要求其他成员必须访问个人电脑才能理解结论。

#### 提交执行与例外

1. 查看已修改、已暂存及未跟踪文件；区分功能源码、正式文档、必要证据与过程产物。“提交全部修改”默认指可交付的项目内容，不包含上述默认忽略的材料。
2. 先按本节筛选、脱敏、去重和更新链接，再按功能显式暂存文件。不得靠 `git add .`／`git add -A` 代替筛选；需要验证但不需留存的材料可以继续在本地使用。
3. 运行 `node scripts/check-doc-impact.mjs --staged --all`。只有截图／日志／数据文件的变更不能充当“文档已同步”；需要关联 Markdown 结论，或有根据的无文档影响声明。
4. 特殊故障确需提交原始格式时，在**同仓本次暂存的 Markdown** 中逐文件声明 `Evidence-Keep: 仓库相对路径 | 不可由摘要或测试替代的具体理由`，并写明关联问题、脱敏情况和后续保留条件；理由至少 8 个字符。已有授权范围内由执行者判断，无须为普通留存决定重复请求用户确认。禁止通配目录、空泛的“留作证据”或改扩展名规避规则。
5. 交付只简述保留／排除的材料及验证边界；过程文件本地归档不等于推送，Git commit 也不等于 push。未推送时不得说远程已更新。

自动检查对改动中路径位于 `evidence/`、`screenshots/`、`test-results/`、`playwright-report/` 的原始日志、抓包、trace、录屏和归档文件执行默认阻断；有效的逐文件例外会提示人工复核。图片数量及大小只提示复核，不自动断言截图必要，也不判断是否完成脱敏。目录外的过程产物和伪装扩展名仍由执行者按同一规则筛选，不能把检查通过当作全量内容审计。

本规则从后续任务及提交开始执行。已有已提交文件不自动批量删除、迁移或重写历史；需要清理时作为单独任务，保留关键结论并修正引用。普通删除只改变当前版本，不能移除 Git 历史中的旧对象；清理远程历史另需明确授权。

### 6.2 Git 提交后的版本信息自动维护（2026-10-05）

项目版本信息统一维护在[版本信息](10-版本信息.md)，由 **AI Agent 在 Git 提交流程中自动判断、整理和更新**，无需人工填写、选择版本号或逐条确认。默认按日期查看每天谁提交了哪些新增、修复和优化，再通过版本链接追溯完整范围及提交证据；当前实现与验收仍查应用进度及 Spec，实际部署查部署记录。

#### 判断依据与维护责任

- 优先阅读本任务提交范围内的文档差异：功能 Spec 的实现／验证记录、问题条目的原因与修复结论，以及应用进度的能力变化。这些文档通常已汇总业务意图及实际结果，适合作为版本摘要的主要来源；不从当前整份文档复制历史能力。
- 文档描述含糊、缺失，或与提交范围不一致时，核对关联代码提交差异、测试及迁移，确认实际行为后再生成摘要。源码与配置决定已实现行为，已确认 Spec 决定目标行为；提交标题仅作线索，不能作为唯一依据。
- AI Agent 负责识别变更类型、过滤细微调整、去重、分配版本号、填写日期与提交来源，并检查事实和链接。常规维护不要求人审核每条摘要；确有无法查明的业务规则冲突时，按既有规则记录边界或待确认，不编造结论。
- 提交人直接读取 Git Committer 名称（`%cn`），用 `<sub>名称</sub>` 小标识显示，放在每日记录及日期索引表格的最后一列，不展示邮箱。Git Author（`%an`）与 Committer 不同时，另附作者名称；同日多人分别标注，摘要只覆盖各自实际提交范围。该标识用于查找 Git 来源，不推断实际操作者或业务负责人。
- 本节约定的是 Agent 随任务提交执行的自动维护流程；未安装独立后台监听器或语义分析 Git Hook，不把普通 Git 提交命令声称为已具备自动分析能力。Agent 接手已提交任务时，按本任务实际提交范围补查。

#### 哪些变更纳入版本

| 变更类型 | 是否记录 | 摘要要求 |
| --- | --- | --- |
| 大功能模块或重要业务流程新增 | 必须记录 | 说明角色、能力及本次形成的业务结果 |
| 小功能新增或已有功能扩展 | 记录 | 说明新增操作或使用场景，不因范围较小省略 |
| 问题修复 | 记录 | 说明用户原先遇到什么问题、现在如何恢复正常；权限、数据、异常和稳定性修复同样记录 |
| 有意义的优化 | 记录 | 说明流程、操作效率、性能、可用性或体验的实际改善 |
| 位置、间距、字号、颜色、图标等细微调整 | 通常跳过 | 若解决遮挡、不可点击、内容不可读等实际问题，按修复／优化记录 |
| 纯重构、格式、仅补测试、文档整理或版本台账自身维护 | 通常跳过 | 未改变实际行为或可用性时不生成版本；内部改动确实解决稳定性／性能问题时按修复／优化记录 |

- 纳入范围必须有真实实现、相应研发验证结论和已成功的代码提交。分阶段实施时，只记录本次实际形成的能力及未完成边界，不能把部分实现写成整个模块完成；方案、原型、菜单壳或仅构建通过不纳入。
- 一轮任务提交中的新增、修复和优化合并成一个新版本，按变更类型分行；同一能力的前后端、多仓库和多次提交合并描述，不按端或提交重复升版。后续任务形成的实质改动追加新版本，不回填为旧版本的新能力。
- 重复执行检查时按仓库、提交哈希和已记录的变更范围去重；历史回填已有核查截止快照时，从快照之后的新提交补查，不重新给已记录能力分配版本号。版本文档自身的提交不再次触发版本。仅修正已有条目的错字、日期或来源时，注明更正，不分配新版本号。

#### 版本号、日期与顺序

- 使用项目级版本号 `v主版本.功能版本.修订版本`，与小程序包版本、构建号、Git tag 和服务器发布编号分别维护，不自动修改这些配置或创建 tag。
- 第一条正式记录使用 `v0.1.0`。此后大模块或重要业务流程新增递增功能位并将修订位归零，如 `v0.1.3 → v0.2.0`；小功能、修复与优化递增修订位，如 `v0.1.0 → v0.1.1 → v0.1.2`。同轮同时含大模块和修复／优化时按较高等级升版，合并记录。正式大版本切换按项目明确确认的里程碑处理，不因日期或提交次数自动切换。
- **修改日期**使用北京时间（Asia/Shanghai）`YYYY-MM-DD`，表示该版本纳入范围的代码提交完成日期；跨仓跨日时取最后一个必要代码提交的日期。补记历史条目时仍使用原提交日期，并另写补记日期；纠错写更正日期和原因，不把文档编辑日期冒充功能修改日期。
- **每日记录日期**从各提交的 Committer 时间（`%ct`）换算为北京时间，按日期从早到晚排列并维护日期索引。同人、同日、同版本的跨仓实质变更可归并；多人或跨日分别记录，不把跨日版本的全部变更归到版本结束日，也不用推送、部署或文档编辑日期代替实际提交日期。
- 版本范围与证据按编号递增追加，已分配版本号不重排、不复用；每日记录追加或归入对应日期，并链接相应版本。同一天可以有多个版本，不要求每天生成版本；历史日期更正时调整对应日期条目，保留原版本号。
- 不默认回填历史或把当前全部能力标为首版。用户授权历史回填时，核对原提交及同期文档，标明实际日期、补记日期、核查截止快照与来源；追溯分配的版本号不冒充当时的发布号。早期可按工程搭建和大模块归并，近期按任务或同日相关变更细化；跨日归并取范围内最后一个必要代码提交日期，列明涵盖日期。工程搭建基线可单列，但不能把骨架或原型计为已实现业务。已有版本号不重排，回填完成后继续从最新版本递增，版本台账不收录当前未提交改动。
- 早期跨日版本仍按实际日期与提交人拆分每日摘要，保留原版本范围；每日摘要用于定位，不复制完整版本到每个人名下。文档来源也注明实际提交日期与提交人，与功能代码来源分别列出。

#### 提交时怎样执行

1. 文档影响检查时，Agent 读取本任务文档差异并按需核对代码，识别应记录的新增、修复与优化，过滤细微调整及重复内容；按模板准备摘要和来源，未提交的代码不写成正式版本。
2. 用户授权提交后，按既有跨仓顺序提交关联代码。涉及版本更新时，代码提交的 `Docs-Refs` 一并引用 `03-开发管理/10-版本信息.md`；无需为了版本记录另行修改无关仓库。
3. 关联代码提交成功后，Agent 读取各仓库实际提交哈希、Committer 时间和名称，按需核对 Author，自动分配版本号，补齐每日记录、日期索引及版本范围与来源，复核范围、验证和未部署／未验收边界，再将最终版本文档显式暂存，随本任务文档一起提交。文档摘要优先取本轮拟提交的已核实内容，文档提交后再检查其与实际提交一致。
4. 若本任务代码和文档均已提交后才识别出漏记，Agent 依据已提交的文档差异补查代码，自动补记并单独提交版本文档；本任务原提交授权包含这种必要的版本同步，无须再次询问。仅补记记录可引用已存在的文档提交哈希；承载条目自身的提交哈希无需填写，不改写原提交。任务没有 Git 提交授权时可整理工作区记录，不擅自 commit；代码未提交成功的范围不登记为正式版本。
5. 交付说明新增版本号及主要变更；全部属于细微调整时不更新版本。版本信息维护不扩大 push、部署或业务验收授权。

#### 统一格式与事实边界

Agent 按[版本信息模板](10-版本信息.md#version-template)维护两部分：每日记录填写实际日期、提交人小标识、本人变更摘要、版本链接和代表提交；版本范围填写版本号、修改日期、参与提交人、版本主题、变更类型、模块、涉及应用／入口、可观察的变更摘要、关联需求／Spec／问题、各代码仓库提交，以及简短的研发验证和未完成边界。完整来源按仓库、实际日期和提交人分组，保留各提交哈希；补记或纠错时追加日期与原因。

变更摘要面向业务阅读，一两句话说明新增能力、修复结果或优化效果，代码路径、字段和逐项测试留在 Spec。版本记录描述对应提交时的事实，后续部署或验收结果由原权威台账维护；不能因已有版本号就标为已发布、已开放或业务验收完成，也不把版本条目数加入入口进度统计。

## 7. Git 提交触发与授权

在当前代码／文档任务语境下，以下表达均触发完整 Git 提交流程：

- “提交代码”“提交修改”“提交功能”；
- “提交当前改动”“提交本次改动”“提交到 Git”；
- “commit”；
- 单独说“提交”，且上下文明确指向当前工作区改动。

表单提交、接口提交、审核提交、完工提交等业务术语不触发 Git 操作。`push`、发布、上传、数据库执行和共享历史改写仍需分别明确授权。

一次提交触发授权覆盖当前任务直接关联的代码仓库，以及因此需要同步的 TOTO 文档仓库。执行顺序为：

1. 检查各仓库分支、远端状态和未提交改动，识别团队并发内容。
2. 运行文档影响检查并完成必要更新，按[证据留存规则](#evidence-retention)排除过程产物；Agent 同时按[版本维护规范](#version-info)分析本次新增、修复和优化，自动准备版本记录。
3. 运行与风险相称的代码和文档验证。
4. 只暂存当前任务的关联文档，然后提交代码仓库。
5. 分别提交其他关联代码仓库；符合版本记录条件时补齐实际提交日期、提交人、每日记录及版本来源并重新暂存版本文档，最后单独提交文档仓库。
6. 汇报各仓库提交哈希、验证结果、未提交内容和未推送状态。

任何一个仓库无法安全区分本任务与他人改动时，不得扩大暂存范围；报告冲突并继续处理不受影响的仓库。

## 8. 提交信息中的文档影响

代码提交正文末尾使用以下记录：

```text
Docs-Impact: updated
Docs-Refs: specs/2026-09-10-示例.md, 03-开发管理/04-Web管理后台开发进度.md
```

确无文档影响时使用：

```text
Docs-Impact: none
Docs-Reason: 仅内部重构，不改变接口、数据、权限和用户行为
```

文档仓库使用独立中文提交，例如：

```text
docs(toto): 同步派单功能实现与验证记录
```

`Docs-Impact: none` 不能用于规避缺失的 Spec、迁移说明、权限变化或验收证据。

## 9. 自动检查与团队接入

- 手动或 Agent 检查：`node scripts/check-doc-impact.mjs --working-tree --all`。
- 提交前检查：`node scripts/check-doc-impact.mjs --staged --all`。
- 安装本地共享 Hook：`bash scripts/install-git-hooks.sh`，覆盖文档仓库和已配置的关联代码仓库。脚本不会覆盖仓库已有 Hook；已有 Husky 串联同一检查入口时继续复用。
- 合理的无文档影响提交可使用 `TOTO_DOCS_IMPACT_NONE_REASON='具体原因' git commit ...`；原因至少 8 个字符，并仍需在提交正文写入 `Docs-Impact: none`。
- CI 接入时应在同一工作区检出代码仓库和 `docs/toto`，执行相同的 `--staged` 检查。当前各仓库未发现统一 CI 定义，因此本规范只提供稳定检查入口，不虚构流水线配置。

自动检查识别 Markdown 文档更新及上述证据留存约束；只有图片、日志或 JSON 的修改不算文档更新。纯文档提交同样检查证据留存，`Docs-Impact: none` 不绕过留存规则。检查不能判断业务结论、截图必要性和脱敏是否正确，这些仍由评审和验收负责。

## 10. 并发编辑与评审

- 不整理、重排或顺带修正与当前任务无关的内容。
- 同一段落存在并发修改时，保留双方事实并显式标记待确认，不以最后写入者覆盖前一结论。
- 提交和评审按逻辑意图拆分；文档格式调整不得与业务结论变化混在同一个难以审阅的提交中。
