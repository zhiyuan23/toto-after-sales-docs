## 如何下达任务

| 用户指令 | AI 执行范围 |
| --- | --- |
| “更新测试环境”或未指明环境的“部署” | 测试站完整售后后端、实际聚合宿主、Web主站＋售后子站；成功后顺序上传两个微信开发版，沿用已有授权规则 |
| “更新测试环境，仅Web／后端” | 同一测试站完整Web／后端，使用 `--web-only`，不上传小程序 |
| “更新demo”或“更新demo前后端” | 仅售后子站`ROOT/after-sales`、售后后端及必要宿主增量；默认不重建／替换主站、不更新common、不附带小程序上传 |
| “只更新demo前端” | 仅售后子站`ROOT/after-sales`；主站与common保持，不替换后端、不重启共享Tomcat |
| “只更新demo后端” | 仅售后Core／API及实际需要的宿主增量，不替换前端 |
| “检查测试环境／demo部署条件” | 只读核查目标、分支、工具、凭据可用性、现有部署及空间；不发布制品、改配置、换应用或重启 |
| “上传两端小程序” | 只执行本页[小程序上传](#mini-program-upload)，不顺带部署服务器 |

用户已指定环境及范围后直接推进必要的检查、构建、备份、更新和验证，不重复确认已知地址与目录。只在缺少可用凭据、存在无法自行核实的服务器身份变化、并发发布冲突或超出本次授权时询问。部署任务本身不自动执行Git提交、推送、共享历史改写或业务数据重导。

**能力边界：** 测试站已有经使用的自动部署脚本；demo目前由AI按下文步骤执行，尚无统一的一键事务脚本。不能给出不存在的 `deploy-demo --deploy` 命令，也不能声称demo具备测试脚本的断线续查与自动回退能力。

拆仓与双Jenkins独立发布目前仅保留[详细设计与后续实施手册](../../specs/05-平台集成与公共能力/2026-10-22-售后Web独立仓库与双Jenkins部署拆分方案.md#split-implementation-guide)。用户已于2026-10-22停止本日实施并清理试验分支；现行同仓、完整测试部署及Demo范围不因该方案改变，不调用已撤回的试验路径或把临时19011预览当正式站点。

### 私密来源

- 测试脚本只读取本仓库忽略文件 `.local/test-server.env`，要求0600；键为`TOTO_TEST_SSH_HOST`、`TOTO_TEST_SSH_USER`、`TOTO_TEST_HTTP_URL`、`TOTO_TEST_SSH_PASSWORD`，目标由脚本固定校验。已固定Ed25519指纹为`SHA256:32uCUmbKNWdximqXT8HzyEktQDv7WlZIKkSGxvBdGnI`；首次记录未经独立渠道核验，变化先调查，不能关闭校验。
- demo先复用当前机器已有、经核验的SSH密钥／SSH agent与known_hosts。如使用口令，本工作区统一存入忽略文件 `.local/demo-server.env`（0600）；只供AI的安全连接工具读取，当前没有自动读取该文件的demo部署脚本。可记录`TOTO_DEMO_SSH_HOST=10.1.1.56`、`TOTO_DEMO_SSH_USER=ehsure`、`TOTO_DEMO_SSH_PORT=22`及私密认证项，不在文档填写实值。首次可信指纹须从已授权可靠渠道取得，不能自动信任`ssh-keyscan`结果。源Windows私密目录不是其他机器天然可用的凭据来源；现有密钥和私密文件均不可用时，只询问缺失的认证方式。
- 不把环境文件当shell脚本`source`，不把口令或密钥正文放在命令参数、终端、日志、Git或客户端配置中。Maven认证使用机器既有私密settings中的`repo-ehsure`服务项；原生Windows与本机工具链按实际仓库说明选择。
- 两端微信私钥仍分别通过各仓忽略的`.env.upload.local`指向仓库外文件，本机集中在本仓`.local/wechat-ci/`；目录0700、私钥0600。只校验可读性及AppID对应关系，不打印正文。

### 售后Web高德直连构建输入（2026-10-23）

本地独立启动、测试和Demo的新售后Web统一采用JSAPI直连。构建前成对提供 `VITE_AMAP_DIRECT_JS_KEY`／`VITE_AMAP_DIRECT_SECURITY_CODE` 私密进程环境，或在当前售后检出的 `.local/amap-direct.json` 提供同名JSON字段（macOS／Linux权限600）。本机忽略文件不随Git或新工作树传播。按用户2026-10-23后继确认，缺少显式输入及私密文件的Jenkins／干净Demo检出，在真正Vite启动／构建阶段静态解析同仓主系统 `src/main.ts` 既有JSAPI初始化中的唯一配对字面量，不需新增Jenkins配置、不执行主系统代码。静态检查只注册插件，不依赖凭证。配对值须经售后专用构建常量注入，避免环境解析插件把空默认值写入最终地图代码；产物验证须检查地图调用的完整配对参数，不能只检查整包存在该字符串，详见[空参数修复](../../specs/05-平台集成与公共能力/2026-10-13-外部服务配置与密钥集中管理.md#amap-empty-build-env-20261023)。显式输入单项缺失、已有文件错误或权限过宽均拒绝，主系统也无有效静态配对配置时真正启动／构建失败；真实值不写命令参数、普通日志或Git。安全密钥会进入浏览器制品，属于用户已确认的直连方案，不再要求新增地图根转发或重启共享Tomcat。测试脚本保留 `mapRootReady` 诊断，但不再以它阻断新Web发布；AI／Web服务后端凭证和加密主密钥门禁保留。完整契约及验证见[统一直连](../../specs/05-平台集成与公共能力/2026-10-13-外部服务配置与密钥集中管理.md#unified-direct-amap-20261023)。本段不表示测试／Demo已更新，也不放宽下文源码同步及发布门禁。

## 共用执行规则

1. 记录目标、范围和必要功能Spec；检查涉及仓库的分支、远端差异、暂存及未提交内容，保留并发修改。测试站只更新应用不自动同步Git；Demo必须按下文先刷新远端并完成目标分支集成，Git提交与推送仍遵循明确授权规则。构建期间源码或服务器快照变化，先核实，不能继续覆盖。
2. 按更新范围核对JDK21、Maven、子站锁定Node及pnpm、SSH／Python等工具；只有涉及主站时才核对其工具链。优先复用与锁文件一致的已安装依赖；不因全局pnpm版本不同修改工程约束。构建不启动本地联调服务，也不停止用户已有服务。
3. 检查功能所需结构、权限和外部配置，应用发布不自动重复执行历史迁移。正常功能开发的测试库变更沿用[项目授权边界](../../AGENTS.md#测试环境部署)：先确认测试库、影响、备份／回退，再执行本功能必要迁移与回读。清库、大范围破坏性、跨功能批量修改及生产操作须另有明确授权。
4. 在隔离的发布证据目录保存源码快照、制品和部署前摘要、检查结果及发布清单；原始日志／备份／含配置的WAR只放忽略的私密目录，权限收紧。先完成构建、传输、备份和校验，再进入切换窗口。
5. 必要检查失败时调查处理，不删除断言、修改失败基线或把历史失败说明当作长期放行授权。主系统`common`子仓库保持其既有授权边界，不能随部署擅自修改、提交或回退。
6. 不把数据库迁移、菜单调整、首次数据复制和应用发布混成必做的一套。测试库持续授权不自动覆盖demo的数据操作；demo只有本次功能明确需要且已有授权时才执行对应迁移／权限增量。

## 测试环境：正式部署脚本

从本仓根目录执行，入口为[`scripts/deploy-test.mjs`](../../scripts/deploy-test.mjs)，辅助文件在[`scripts/deploy-test/`](../../scripts/deploy-test/)。支持macOS／Linux标准跨仓工作区；Windows使用WSL或已核验的等价流程，不直接调用当前脚本。脚本需要本机Python3.9+、OpenSSH、Expect，服务器需要Python3.9+、Bash及`flock`，不会自动安装。

```bash
# 单独只读预检；--deploy本身已包含预检，发布时无需重复先check。
node scripts/deploy-test.mjs --check
# 完整Web／后端，成功后上传两端微信开发版本。
node scripts/deploy-test.mjs --deploy
# 明确只更新Web／后端。
node scripts/deploy-test.mjs --deploy --web-only
# 断线或本地等待中断后，把实际输出的发布编号放入TOTO_RELEASE_ID再查询。
node scripts/deploy-test.mjs --status "$TOTO_RELEASE_ID"
```

`--check --web-only`只预检Web／后端。现有脚本没有单独前端／单独后端开关；用户只授权其中一端时，不运行完整发布模式，按已授权范围执行构建、独立备份、替换和验证，不擅自扩大范围。

2026-10-23 本机及共享测试后端单独更新案例见[微信登录协调发布](部署记录/测试环境发布记录.md#personnel-wechat-release-20261023)：共库实例先协调停止，再备份迁移、更新并恢复；共享端按当前运行Core最小覆盖登录类／Mapper，WAR与展开目录一致、前端及其他依赖保持。本次Core／API构建显式指定 `-Drevision=3.0-SNAPSHOT` 以匹配测试宿主依赖，本机启动入口也已同步，避免默认Demo F版本安装成功但运行端仍加载旧3.0包。该案例不改变完整发布入口，不自动授权以增量补丁替代其他任务的必要构建和验证。

### 自动执行及状态含义

- 快照包括售后后端、聚合宿主、Web，以及本次包含上传的两端小程序。构建售后API／Core并装配`gaia-saas-web.war`；发布阶段后端构建沿用`-DskipTests`，本次功能必要后端测试仍须在之前完成并记录，不把打包通过称为全量测试通过。
- Web完整check必须通过；当前`web-test-baseline.json`的`failures=[]`。历史参数`--allow-known-web-failures`不再放行任何失败，日常命令不使用它。主站`productionSAAS`、子站production构建后组合为`dist/after-sales`，检查包体和入口资源再打包。
- 远端保护五份内嵌运行配置、外部售后配置、`WW_verify_*.txt`及`.well-known`；备份并核对原WAR、展开API及ROOT，精确停止目标Tomcat、切换、启动及验证。不要运行`gaia-ui/push.sh`的上传步骤，其既有目标不属于这两套环境。
- 静态资源过渡：暂存新ROOT时，从当前ROOT的`assets/`和`after-sales/assets/`保留带内容哈希或13位以上构建时间戳的旧资源，补齐旧页面后续加载所需的JS／CSS等文件；新入口及同名新资源保持。相同哈希URL出现内容冲突、符号链接或越界路径时，在停服前拒绝发布。暂不自动清理已保留的旧资源。manifest分别记录新资源与`retainedAssets`，服务器及开发机HTTP摘要校验覆盖完整资源目录（含未被入口预加载的懒加载分块）及旧资源。该逻辑于2026-10-22故障后修复，见[旧分块404恢复](部署记录/测试环境发布记录.md#asset-recovery-20261022)。
- 入口缓存与换版：ROOT自带`WEB-INF/web.xml`使用Tomcat内置`ExpiresFilter`，仅对`text/html`设置`max-age=0`；已有不同ROOT描述符时停服前拒绝覆盖。主站`/`、`/index.html`及子站`/after-sales/`、`/after-sales/index.html`均必须回读入口摘要及重新校验响应头；哈希／时间戳资源保留原缓存策略。主站售后容器把本次主站模块入口文件名作为`hostBuild`查询参数，主站换版时改变iframe文档URL，同版本内导航保持稳定。真实主站复验必须核对iframe地址／实际脚本版本、滚动高度及外观传递，首页200不能代替。实现与证据见[入口缓存与换版修复](部署记录/测试环境发布记录.md#entry-cache-release-20261022)。
- 本机证据：`.local/verification-artifacts/deploy-test/<编号>/`；服务端制品与状态：`/yundata/saas_test/packages/<编号>/`；备份：`/yundata/saas_test/backups/<编号>/`。本机及服务端都有发布锁，不自动清理旧备份。 本机已成功发布且过期的重复WAR／静态包可按[本地清理规则](../../local-development.md#local-log-retention)清理，保留最近3次成功发布完整制品及各批次状态／manifest／回读结论；本地规则不删除服务端packages／backups，也不自动解除数据库或配置备份。
- `FAILED`表示切换前失败；`ROLLED_BACK`表示切换后已恢复旧应用并恢复健康；`NEEDS_ATTENTION`表示停止／恢复／健康尚未可靠完成，需按同编号核查。服务端事务脱离SSH运行，断线先`--status`，不要重新发布。
- `COMPLETE`只表示服务端Web／后端校验通过。脚本随后在开发机回读入口资源摘要、公开业务码及匿名拒绝，再逐端上传小程序；本地HTTP验证或单端上传失败必须分别报告，不回退已成功的Web，也不自动重传回执不明的小程序。
- **2026-10-22起，小程序上传辅助入口固定连接demo HTTPS及API租户`demo`，Web／后端仍发布到`10.1.1.53`。** 这是当前实际配置，不能再描述为小程序连接本次测试站。完整测试更新授权仍包括两次开发版上传；用户明确不上传时使用`--web-only`。

### 1. 只读预检与源码准备

#### 目标分支集成门禁（构建前必须完成）

这些分支也供其他人更新测试环境使用，不是售后独占分支。AI负责核对和集成，无需用户手动切换当前开发目录。

| 仓库 | 必须集成并用于构建的目标分支 |
| --- | --- |
| `backend/gaia-after-sales` | `dev/test` |
| `backend/gaia-saas-proj` | `dev/test` |
| `frontend/gaia-ui`（默认仅构建`apps/after-sales`） | `dev_test`；保留目标分支主站与common引用，不因售后发布更新它们 |

1. 检查各仓库约束、远程地址、当前分支及全部已有改动，再执行`git fetch origin`刷新目标引用；获取失败时停止源码准备，不能用缓存的`origin/*`认定已包含同事最新更新。明确本次待发布的功能分支／提交及涉及仓库；仅更新某端时只集成相关仓库，并核对未更新端的兼容性。
2. 优先在隔离工作区以最新`origin/dev/test`或`origin/dev_test`为基线，先吸收目标分支已有更新，再合入本次功能提交。Web只集成本次售后所需提交和构建支持；保留目标分支已有主站与common gitlink，不夹带功能分支中的无关主站／common差异。合入提交混有无关修改时先拆分范围并验证，不直接整树覆盖。不以售后开发分支整树替换目标分支，不回退公共更新。冲突按双方业务意图解决，不能整批选择一方覆盖；无法查明的重大冲突停止该端发布并说明。
3. 完成差异检查及本次必要验证后，按用户明确授权完成目标分支的Git提交和正常推送，不强推。**“更新demo”包含必要的远端核对与集成准备，但不自动授权创建合并提交、commit或push。** 如本轮集成需要提交／推送而尚无授权，先完成可执行的核对、差异整理及验证，说明待同步内容与所缺授权，暂不部署；不得用未同步的临时包绕过门禁。已有对应授权时直接执行，不重复确认。
4. 只有待发布功能已进入对应远端目标分支后，才从该分支的干净检出构建正式制品；未提交源码不得混入。记录每仓功能来源提交、集成后目标提交及远端一致性，确认最新目标基线和待发布功能均被包含；选择性移植时记录对应关系与范围。目标分支已包含本次功能且无需新提交时直接验证并构建，不制造空合并或空提交。

#### 主站与common的默认保护及必要扩围

默认售后独立构建不读取主站业务源码或common，不要求common初始化，不执行`git submodule update --remote`、切分支、拉取或修改其gitlink；gaia-ui集成时保留目标分支已经记录的引用，不能把售后功能分支旧指针带回目标分支。发布记录可记下该gitlink作为源码背景，不能将它当作本次主站／common发布版本。

只有本次功能确实需要主站售后桥接、菜单注册、登录协议或公共依赖配合时，先列明不能在子系统内完成的原因、最小变更和兼容回归，再按已获授权扩大范围；common源码修改／提交继续需要单独明确授权。不能为了跟随common最新提交而扩大本次售后更新。

确需完整主站发布时，分别获取gaia-ui与common对应目标分支，比较主仓gitlink、common远端、功能来源及线上上次引用，确认不回退现有功能后再确定兼容版本、更新必要引用及验证。common分支最新提交不天然兼容主仓；有分叉时不能简单选最新覆盖。必要common集成未获授权或兼容性未解决时停止该扩大范围的发布，已确认兼容且不依赖它的售后独立更新可继续。原始工作区分支和并发修改保持。

### 3. 构建后端及核对增量（只更新前端时跳过）

售后制品使用**未发布过的唯一F版本**，例如`F3.0-demo-<上海日期>.<递增号>`；不能覆盖已发布的`F3.0-demo-20261021.1`。AI将所选版本放入非敏感变量`TOTO_DEMO_VERSION`，本轮证据目录放入`TOTO_DEPLOY_EVIDENCE`。先检查远端仓库可用性和实际Maven插件版本，再执行以下示例；不修改全局settings或泄露认证。

```bash

: "${TOTO_DEMO_VERSION:?必须设置尚未发布的F版本}"
: "${TOTO_DEPLOY_EVIDENCE:?必须设置本轮证据目录}"
# 在本次售后dev/test源码根目录：先跑Reactor测试。
mvn -B -pl gaia-after-sales-api -am clean verify -Drevision="$TOTO_DEMO_VERSION"
# 上一步通过后发布同一批父POM/Core/API及既有sources配置。
mvn -B -pl gaia-after-sales-api -am deploy -Drevision="$TOTO_DEMO_VERSION" -DskipTests
# 用空本地仓库验证父POM及全部传递依赖，避免仅依赖本机缓存。
mvn -B -U -Dmaven.repo.local="$TOTO_DEPLOY_EVIDENCE/maven-clean" dependency:get -Dartifact="com.ehsure.gaia:gaia-after-sales-api:$TOTO_DEMO_VERSION" -Dtransitive=true

```

当前售后 POM 已在 compile 阶段绑定 sources；发布仅执行 `deploy`，不要再额外调用 `source:jar-no-fork`，否则 maven-source-plugin 3.3.0 会因重复 sources 附件终止。若父 POM 已发布而 Core/API 在打包前失败，先核对远端实际内容，再从失败模块恢复，不能覆盖既有 F 制品。

执行前先确认两个变量非空、F版本不存在、证据目录位于本次忽略的私密目录；变量仅为本轮输入，并非已有自动版本选择器。Maven仓库为既有`repo-ehsure`；优先使用POM的`distributionManagement`，只有地址确需覆盖时才按当前deploy插件语法使用参数。宿主打包跳过测试不代替本次Shiro／MVC／装配变更的必要测试。

- 默认替换售后Core／API；按实际变化增补`ShiroConfig.class`、`WebConfig.class`等宿主装配文件。首次“六文件”只是历史清单，不能机械套用。
